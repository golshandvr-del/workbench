# AI Workbench 1.14.4 — اتصال پروژه با آگاهی از Monorepo

## تغییرات نسخهٔ ۱.۱۴.۴

- **Schema نسخهٔ ۲ برای اتصال پروژه:** فیلدهای `workflow_file`، الگوی نام Artifact، کانال انتشار (`dev`، `beta`، `stable`) و metadata همگام‌سازی اضافه شدند. رکوردهای نسخهٔ ۱ به‌صورت idempotent نرمال می‌شوند و پیش از بازنویسی تنظیمات، نسخهٔ پشتیبان زمان‌دار ساخته می‌شود. رکوردهای نامعتبر یا تکراری گزارش می‌شوند و نباید به‌عنوان اتصال معتبر پذیرفته شوند.
- **تنظیمات Binding:** از رابط می‌توان Branch کاری، مسیر Workflow داخل `.github/workflows/`، الگوی Artifact و کانال انتشار را تنظیم کرد. در این نسخه این فیلدها فقط ذخیره می‌شوند؛ اجرای Workflow و دریافت Artifact هنوز به مراحل بعد تعلق دارند.
- **Clone و Initialize & Link:** Clone فقط در مقصد جدید و خالی انجام می‌شود. Initialize & Link یک Branch محلی غیرپایدار از نوع `workbench/initial-sync-*` می‌سازد و پس از تأیید صریح، `origin` را تنظیم می‌کند. هیچ‌کدام به‌طور خودکار فایل‌ها را Stage، Commit یا Push نمی‌کنند.
- **Initial Push Review:** بررسی بدون تغییر وضعیت Git، فهرست فایل‌های tracked/untracked، فایل‌های داخل و خارج از زیرپوشهٔ پروژه، نام‌های مشکوک، الگوهای احتمالی Token/کلید خصوصی و فایل‌های حجیم را نمایش می‌دهد. الگوهای پیشنهادی `.gitignore` صرفاً پیشنهاد هستند؛ محتوای قبلی جایگزین نمی‌شود و افزودن موارد جدید به تأیید جداگانه نیاز دارد. اسکن اسرار تضمین کامل نیست.
- **Git آگاه از Monorepo:** Git root واقعی از مسیر پروژه تفکیک می‌شود؛ تغییرات پروژه‌های خواهر/ریشه در UI با هشدار نمایش داده می‌شوند. Stage و Commit از دکمهٔ Workbench فقط فایل‌های داخل Scope پروژه را هدف می‌گیرند. اگر Index از قبل تغییرات Stage‌شده داشته باشد، Commit متوقف می‌شود تا فایل‌های خارج از Scope ناخواسته وارد Commit نشوند. عملیات Branch و Push همچنان در سطح کل Repository هستند و محافظت Push مستقیم به `main/master` باقی است.
- **اصلاح `.git/info/exclude`:** مسیر exclude از Git root واقعی محاسبه می‌شود، حتی وقتی پروژه در زیرپوشهٔ Monorepo قرار دارد. فایل‌های داخلی `.workbench/` از وضعیت عادی Git پنهان می‌شوند؛ فایل‌های از قبل tracked یا محتوای `.gitignore` کاربر خاموش تغییر نمی‌کنند.
- **آزمون رگرسیون:** مهاجرت و backup تنظیمات، چند پروژه با `repository_id` مشترک، تغییر نام Repository، مرور اولیهٔ بدون mutation، Scope زیرپوشه، و یک آزمون GUI با Git واقعی که اثبات می‌کند Commit پروژهٔ دسکتاپ فایل ریشه/پروژهٔ خواهر را وارد Commit نمی‌کند.

### مرز این نسخه و محدودیت آزمون

این نسخه اتصال پروژه و عملیات محلی آگاه از Monorepo را توسعه می‌دهد. مرور Diff فایل‌به‌فایل، Fetch و Sync Plan، رسیدگی به divergence، Build Center مربوط به GitHub Actions و دانلود Artifact هنوز پیاده‌سازی نشده‌اند. ۲۲۵ آزمون واحد/رگرسیون و ۱۴ جریان GUI در Linux/Xvfb اجرا شده‌اند. نصب واقعی ویندوز، اجرای PowerShell نصب‌کننده، Windows Credential Manager و Clone/API با احراز هویت واقعی در این محیط **اجرا نشده‌اند**؛ برای آن‌ها `WINDOWS_RELEASE_CHECKLIST_v1.14.4.md` را روی Windows 10/11 تکمیل کن.

# AI Workbench 1.14.3 — مرورگر Repository و اتصال پروژه

## تغییرات نسخهٔ ۱.۱۴.۳

- **Repository Browser:** دریافت Repositoryهای حساب متصل‌شده از GitHub REST API با صفحه‌بندی، کنترل تعداد صفحه، حذف شناسه‌های تکراری و اعتبارسنجی metadata. جست‌وجو روی owner/name/description و فیلتر عمومی/خصوصی، Fork و Archived پس از دریافت فهرست اعمال می‌شود.
- **اطلاعات دسترسی:** وضعیت visibility، Branch پیش‌فرض، تاریخ به‌روزرسانی و مجوز `push` فقط در صورت وجود در پاسخ API نمایش داده می‌شود. مشاهدهٔ Repository به معنی مجوز نوشتن یا اجرای Actions نیست.
- **اتصال پروژه به Repository:** اطلاعات binding نسخه‌دار شامل شناسهٔ عددی Repository، حساب Workbench، مسیر Git root، مسیر زیرپوشهٔ Monorepo، Branchها و metadata غیرمحرمانه ذخیره می‌شود. PAT و Remote URL خام در binding نوشته نمی‌شوند.
- **Remote با تأیید صریح:** اگر `origin` وجود نداشته باشد یا به Repository دیگری اشاره کند، Workbench قبل از افزودن/جایگزینی آن تأیید جدا می‌خواهد. Remote هدف به شکل HTTPS بدون Credential ساخته می‌شود. در صورت شکست ذخیره‌سازی binding، برنامه تلاش می‌کند تغییر `origin` را جبران کند.
- **Unlink امن:** قطع پیوند فقط metadata مربوط به Workbench را حذف می‌کند؛ Remote محلی، Commitها و Repository سرور تغییر نمی‌کنند. Link کردن به‌تنهایی فایل را Stage، Commit یا Push نمی‌کند.
- **Monorepo:** پروژه می‌تواند زیرپوشه‌ای از یک Git root مشترک باشد. عملیات Git همچنان روی root واقعی انجام می‌شود و subpath پروژه در binding نگهداری می‌شود.
- **آزمون:** تست‌های صفحه‌بندی API، اعتبارسنجی Remote، مسیرهای Monorepo، rollback، حفظ محرمانگی و جریان GUI اضافه شده‌اند.

### موارد خارج از دامنهٔ این نسخه

Clone، ساخت خودکار Repository، Stage/Commit/Push، همگام‌سازی Branch، GitHub Actions، Build Center و دانلود Artifact هنوز در این نسخه نیستند. اتصال زنده با PAT واقعی و نصب/اجرای native روی Windows 10/11 در محیط ساخت Linux اجرا نشده‌اند. پیش از ادعای تأیید Windows، چک‌لیست `WINDOWS_RELEASE_CHECKLIST_v1.14.3.md` باید روی دستگاه هدف تکمیل شود.

# AI Workbench 1.14.2 — حساب GitHub و ذخیره‌سازی امن PAT

## تغییرات نسخهٔ ۱.۱۴.۲

- سرویس مستقل `aiwb.github` برای اتصال REST API، اطلاعات غیرمحرمانهٔ حساب، اعتبارسنجی PAT و چرخهٔ عمر اتصال اضافه شد.
- ذخیره‌سازی PAT در نسخهٔ ویندوز از Windows Credential Manager استفاده می‌کند؛ هیچ مسیر جایگزینِ فایل متنی وجود ندارد. آزمون‌های Linux فقط با Memory Store تزریق‌شده اجرا می‌شوند و Factory تولیدی هرگز آن را انتخاب نمی‌کند.
- پنل GitHub Accounts در تب Git / GitHub قابلیت‌های Add PAT، Test Connection، Replace Credential، Refresh Accounts و Disconnect را دارد. توکن هنگام ورود مخفی است و پیش از پایان عملیات پس‌زمینه از فیلد رابط پاک می‌شود.
- کلاینت REST API قابل‌آزمون برای `GET /user`، با هدرهای User-Agent، Accept و نسخهٔ API `2026-03-10`، timeout و محدودیت اندازهٔ پاسخ، و بدون دنبال‌کردن redirect برای درخواست دارای credential اضافه شد. خطاهای 401، 403، rate limit، شبکه، timeout، سرور و پاسخ نامعتبر جدا تشخیص داده می‌شوند.
- تنظیمات فقط `credential_ref`، شناسهٔ عددی GitHub، login، زمان اعتبارسنجی، وضعیت و snapshot محافظه‌کارانهٔ قابلیت‌ها را نگه می‌دارند؛ PAT در settings، فایل پروژه، Remote URL یا آرگومان فرمان نوشته نمی‌شود.
- موفقیت `GET /user` فقط هویت حساب را تأیید می‌کند؛ مجوز Repository، نوشتن Git، Actions، dispatch، دانلود Artifact و Release تا بررسی endpoint اختصاصی `not_checked` می‌مانند.
- Disconnect فقط مرجع حساب Workbench و credential API مرتبط را حذف می‌کند؛ پوشه‌ها، Commitها، Remoteها و ورودی‌های Git Credential Manager را حذف یا تغییر نمی‌دهد.
- تست‌های حساب/API، آزمون GUI، بررسی Payload، سند ADR-002 و اسکریپت آزمون Native ویندوز اضافه شدند.

### مرز امنیت و اعتبارسنجی

آزمون بومی Windows Credential Manager و اجرای واقعی نصب‌کننده در محیط Linux انجام نشده است. در Windows 10/11 فایل `test_windows_credential_store.py` را اجرا و چک‌لیست `WINDOWS_RELEASE_CHECKLIST_v1.14.2.md` را تکمیل کن؛ تا آن زمان آزمون بومی وضعیت NOT RUN دارد. PAT را مانند گذرواژه محرمانه نگه دار و در صورت پشتیبانی GitHub از Fine-grained PAT با حداقل Repository و Permission لازم استفاده کن. راهنمای رسمی: https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens

# راهنمای فارسی AI Workbench 1.14.1 — جداسازی سرویس Git

## تغییرات نسخهٔ ۱.۱۴.۱

- کشف Git، اجرای فرمان‌ها، خواندن وضعیت Repository، تجزیهٔ خروجی porcelain و جمع‌آوری مسیرهای تغییریافته به پکیج مستقل `aiwb.git` منتقل شدند؛ این پکیج به Tkinter وابسته نیست.
- مدل‌های تغییرناپذیر `GitStatusEntry` و `GitStatusSnapshot` اضافه شدند. خروجی قدیمی `git_status_info()` و parser قبلی همچنان به‌عنوان adapter سازگاری حفظ شده‌اند تا رابط فعلی بدون بازنویسی پرریسک کار کند.
- اجرای Git از طریق `GitCommandRunner` قابل تزریق و آزمون شده است؛ فرایند با آرگومان‌های مجزا و `shell=False` اجرا می‌شود، prompt تعاملی Git غیرفعال است، timeout دارد و متن خطا از مسیر redaction برنامه عبور می‌کند.
- اجرای `git init` هنگام ساخت پروژه نیز از سرویس مشترک عبور می‌کند؛ دکمهٔ رابط دیگر برای این عملیات مستقیماً `subprocess.run` را صدا نمی‌زند.
- آزمون‌های جدید مسیرهای دارای فاصله، یونیکد و newline، Repository نامعتبر، نبود Git، timeout، آرگومان‌های امن و حذف اسرار از متن خطا را پوشش می‌دهند.

این نسخه فقط زیربنای Git محلی را آماده می‌کند. اتصال PAT، GitHub REST API، مدیریت حساب، Repository Browser، GitHub Actions و دانلود Artifact هنوز اضافه نشده‌اند و طبق نقشه‌راه به نسخه‌های بعدی `1.14.n` تعلق دارند. آزمون نصب/ارتقای واقعی ویندوز نیز در محیط فعلی اجرا نشده است؛ وضعیت آن در `WINDOWS_RELEASE_CHECKLIST_v1.14.1.md` ثبت شده است.

# راهنمای فارسی AI Workbench 1.14.0 — عملیات نوع‌دار و معماری ماژولار

## تغییرات نسخهٔ ۱.۱۴.۰

- **پروتکل `workbench-v3`:** پاسخ JSON مدل می‌تواند عملیات نوع‌دار `write`، `delete`، `rename` و `move` داشته باشد. پروتکل‌های `workbench-v1` و `workbench-v2` برای سازگاری باقی مانده‌اند و فقط نوشتن فایل را می‌پذیرند. حذف، تغییرنام و جابه‌جایی از اعتبارسنجی مسیر، Preview، تأیید صریح، پشتیبان تراکنش و Restore مبتنی بر هش عبور می‌کنند. مقصد موجود هیچ‌وقت بازنویسی نمی‌شود و Rename فقط در همان پوشه مجاز است.
- **رفت‌وبرگشت طرح معماری:** در Wizard پروژه و Project Profile می‌توان طرح `workbench-architecture-v1` را ایجاد، وارد، ویرایش، اعتبارسنجی، ذخیره و صادر کرد. فایل در `.workbench/architecture_plan.json` ذخیره می‌شود و در پرامپت‌های بعدی زمینهٔ اختیاری است؛ طرح به‌خودی‌خود مجوز اعمال فایل نیست.
- **مقایسهٔ Candidateها:** پاسخ‌های متنی/JSON معتبر را محلی ذخیره کن و برای هر مسیر مقصد جداگانه تعیین کن کدام پاسخ انتخاب شود. حالت پیش‌فرض همهٔ مسیرها Skip است؛ خروجی ترکیبی دوباره اعتبارسنجی و Preview می‌شود. فرمان‌های Candidateها عمداً ترکیب نمی‌شوند. ZIPهای دارای باینری ورودی این قابلیت نیستند.
- **Diff معنایی ساختاریافته:** تغییر تعریف‌های Python با AST، تغییر مسیرها/مقادیر JSON و تغییر ستون/ردیف/سلول CSV نمایش داده می‌شود؛ CSV در صورت وجود ستون کلید یکتا، تغییر سلولی را از افزودن/حذف ردیف جدا می‌کند. برای زبان‌های دیگر، تحلیل نمادها heuristic است و Diff متنی محدودشده نیز نمایش داده می‌شود. تحلیل معنایی اختصاصی YAML فعلاً وجود ندارد.
- **Task Playbookها:** گردش‌کارهای آماده برای قابلیت جدید، رفع باگ، بازآرایی معماری، امنیت، کارایی، مستندات/انتشار و پروژه‌های مهندسی/شبیه‌سازی به پرامپت اضافه می‌شوند.
- **Semantic Diff و تحلیل اثر تغییر:** برای Python از AST و برای برخی زبان‌های دیگر از تحلیل ساختاری مبتنی بر heuristic استفاده می‌شود. تحلیل وابستگی، وابستگی‌های مستقیم/غیرمستقیم قابل‌حل و ارجاعات حل‌نشده را نشان می‌دهد؛ این گزارش اثبات کامپایل یا صحت زمان اجرا نیست.
- **ماژولارسازی مرحله‌ای:** سرویس‌های دامنهٔ جدید در بستهٔ `aiwb/` قرار دارند (`architecture_plan`، `candidate_store`، `dependency_analysis`، `semantic_diff` و `task_playbooks`). فایل بزرگ `AI_Workbench.py` در این نسخه نقطهٔ ورود پایدار GUI می‌ماند تا ریسک بازنویسی یک‌باره کم شود. نصب‌کننده اکنون این بستهٔ اجرایی را نیز نصب می‌کند.

### مرز ایمنی و آزمون

هیچ عملیات فایل پیشنهادی مدل بدون اعتبارسنجی، Preview، تأیید صریح کاربر، ثبت پشتیبان و مسیر Restore مبتنی بر هش اعمال نمی‌شود. فرمان‌های پیشنهادی Candidateها ادغام نمی‌شوند و اجرای فرمان همچنان تأیید مستقل لازم دارد. تحلیل استاتیک advisory است. تست‌های Linux/Xvfb جای آزمون نصب واقعی ویندوز را نمی‌گیرند؛ وضعیت ویندوز در `WINDOWS_RELEASE_CHECKLIST_v1.14.0.md` ثبت شده است.

# راهنمای فارسی AI Workbench 1.13.0 — بازبینی انتخابی، Restore و اعتبارسنجی

## تغییرات نسخهٔ ۱.۱۳.۰

- **Selective Apply:** در پنجرهٔ بررسی پاسخ، ستون Apply? برای هر فایل وجود دارد. پیش‌فرض همهٔ فایل‌های معتبر انتخاب شده‌اند؛ می‌توانید همه، فایل‌های جدید، فایل‌های تغییرکرده یا هیچ‌کدام را انتخاب کنید. انتخاب فایل به معنی تأیید فرمان نیست. اگر فرمان احتمالاً به فایل خارج‌شده از Apply وابسته باشد، Workbench هشدار می‌دهد.
- **Restore Manager:** از منوی File می‌توانید یک Apply قبلی را انتخاب کنید و فایل‌های آن را بازگردانید. بازگردانی فقط وقتی مجاز است که Hash فعلی با Hash ثبت‌شده پس از Apply برابر باشد و backup قبل از Apply نیز سالم باشد. تعارض‌ها به‌صورت پیش‌فرض متوقف می‌شوند و گزینهٔ بازنویسی اجباری وجود ندارد. خود Restore نیز تراکنش قابل‌بازگردانی و رویداد تاریخچهٔ جدید می‌سازد.
- **Validation Profiles:** از منوی File پروفایل اعتبارسنجی پروژه را بسازید و ذخیره کنید. مراحل فرمانی از `argv` جداگانه استفاده می‌کنند و به‌طور پیش‌فرض shell اجرا نمی‌کنند. اجرای پروفایل نیازمند تأیید صریح است؛ ابزار مفقود، timeout، خروجی غیرصفر، فایل Log قدیمی و بررسی دستی وضعیت‌های جدا دارند. Passed فقط از شواهد اجرای واقعی به دست می‌آید و به‌معنای صحت دامنه‌ای کامل نیست.
- **Artifactهای باینری در ZIP:** فایل‌های باینری مثل PNG دیگر به‌عنوان فایل متنی تفسیر نمی‌شوند یا بی‌صدا حذف نمی‌شوند. پیش‌نمایش به‌جای Diff جعلی، اندازه و SHA-256 را نشان می‌دهد. Import همچنان فقط Preview است و هیچ فایل باینری اجرا نمی‌شود.
- **Context Planning:** قواعد `.gitignore` و `.workbenchignore` برای حذف پیشنهاد خودکار فایل‌های نامرتبط پشتیبانی می‌شوند. این پیاده‌سازی عمداً ادعای سازگاری کامل با Git ندارد. دکمهٔ «Why these files?» دلیل پیشنهاد و فایل‌های کنارگذاشته‌شده را نشان می‌دهد؛ انتخاب‌های قبلی کاربر هنگام پیشنهاد دوباره حفظ می‌شوند.
- **بستهٔ تشخیصی:** گزینهٔ Export redacted diagnostics در منوی File ابتدا محتوای JSON را برای بازبینی نمایش می‌دهد. به‌طور پیش‌فرض سورس، پرامپت، پاسخ مدل، متن فرمان، خروجی فرایند و مسیر کامل کاربر را وارد نمی‌کند. هیچ داده‌ای به سرور ارسال نمی‌شود؛ بااین‌حال redaction تضمین حذف کامل همهٔ اسرار نیست.

### محدودیت آزمون نسخهٔ ۱.۱۳.۰ (یادداشت تاریخی)

این محدودیت مربوط به انتشار ۱.۱۳.۰ است. برای وضعیت آزمون نسخهٔ فعلی به فایل `WINDOWS_RELEASE_CHECKLIST_v1.14.0.md` و گزارش آزمون نسخهٔ ۱.۱۴.۰ مراجعه کنید؛ آزمون Linux/Xvfb همچنان به‌تنهایی تأیید نصب ویندوز محسوب نمی‌شود.

# راهنمای فارسی AI Workbench 1.12.0 — Context-plan Protocol Repair

## تغییرات نسخهٔ ۱.۱۲.۰ — اصلاح ریشه‌ای قرارداد Context Plan

- **رفع تعارض پرامپت و واردکننده:** در نسخه‌های قبلی ممکن بود پرامپت فقط بگوید `workbench-plan-v1` برگردان، بی‌آنکه ساختار کامل و الزام‌آور فیلدها را ارائه کند؛ در عین حال واردکننده فقط نام‌های جدیدتر فیلدها را می‌پذیرفت. در نتیجه مدل می‌توانست طرحی از نظر معنایی درست بسازد، ولی برنامه آن را پیش از استفاده از مسیرهای درخواستی رد کند. اکنون پرامپت تولیدی یک schema کامل `workbench-plan-v2` دارد که در زمان فقدان سورس ضروری، بر قرارداد خروجیِ پیاده‌سازی، ZIP یا Gemini اولویت دارد.
- **مهاجرت کنترل‌شدهٔ قالب قدیمی:** فیلدهای `requests` و `request`، حالت‌های شناخته‌شدهٔ `whole_file` و `line_range` و درخواست پیوست دستی، همچنین `manual_attachments` و غلط املایی گزارش‌شدهٔ `manual_attechent` به فیلدهای استاندارد تبدیل می‌شوند. `next_steps` و `completion_status` نیز حفظ می‌شوند. این مهاجرت permissive یا ناامن نیست: کلیدهای ناشناخته و فیلدهای تو‌در‌تو نامعتبر همچنان رد می‌شوند و مسیرها دوباره از فیلترهای traversal، فایل حساس و symlink عبور می‌کنند.
- **عیب‌یابی متناسب با نوع پاسخ:** پاسخ Context Plan از پاسخ پیاده‌سازی جدا تشخیص داده می‌شود؛ تعداد فایل، بازهٔ خطوط و پیوست دستی در گزارش نشان داده می‌شود. واردکردن طرح به‌هیچ‌وجه فایل را اعمال یا فرمانی را اجرا نمی‌کند.
- **اعتبارسنجی نوع دادهٔ مقاوم‌تر:** مقدار نامعتبر برای پروتکل، وضعیت، اقدام یا scope با پیام اعتبارسنجی مشخص رد می‌شود، نه با استثنای داخلی پایتون. خطاهای یکسانی که از دو لایه می‌رسند تکراری نمایش داده نمی‌شوند.
- **ثبت و ردیابی پاسخ ردشده:** اگر واردکردن Context Plan ناموفق باشد، پاسخ کاملِ نامعتبر ـ در صورت موفقیت ذخیره‌سازی محلی ـ به گام پرامپت مربوط در تاریخچه متصل می‌شود و رویداد ساختاریافته‌ای در گزارش اجرا ثبت خواهد شد. پیام خطا هش SHA-256 متن فعلی و کلیدهای واقعی سطح بالا را نشان می‌دهد؛ متن خام به گزارش تشخیصی افزوده نمی‌شود.
- **آزمون رگرسیون:** نمونهٔ واقعی `requests`، نام‌های مستعار و غلط املایی، رد مسیر traversal پس از مهاجرت، قرارداد پرامپت‌ها، نوع داده‌های نامعتبر، ذخیرهٔ تلاش ردشده و مسیر کامل GUI برای انتخاب فایل/ذخیرهٔ تاریخچه آزموده شده‌اند.

**اختلافی که در گزارش خطای نمونه دیده می‌شود:** JSON پیوست‌شده کلیدهای `requests` و `manual_attachments` دارد، اما متن خطا `request` و `manual_attechent` را نام می‌برد. اعتبارسنج نسخهٔ قبلی نام کلیدهای ناشناخته را مستقیماً از خود JSON می‌ساخت؛ پس این دو متن دقیقاً از یک پاسخ نیستند، مگر آنکه یکی از آن‌ها هنگام نقل‌کردن دچار غلط تایپی شده باشد. در نسخهٔ ۱.۱۲، هش و کلیدهای ورودی در خطا نشان داده می‌شوند تا چنین اختلافی قابل‌بررسی باشد.

**تفسیر نمونهٔ ارسالی:** چون پرامپت فقط درخت فایل را داشت و متن هیچ فایل موجودی را شامل نمی‌شد، درخواست مدل برای دریافت سورس، رفتار درست بود. خطای اصلی ناسازگاری ساختار پاسخ و رد شدن مهاجرت آن بود. پس از واردکردن طرح، کاربر باید فایل‌های انتخاب‌شده را بازبینی کند، پرامپت مرحلهٔ بعد را بسازد و آن را به همان مکالمهٔ مدل برگرداند. تا وقتی سورس واقعی در اختیار مدل قرار نگرفته و بررسی نشده است، نباید ادعا کرد پیاده‌سازی انجام شده است.

## تغییرات نسخهٔ ۱.۱۱.۰ — بازطراحی تاریخچه و نسخه‌گذاری پروژه

- **ثبت انتخابی پرامپت + پاسخ معتبر:** پس از تحلیل موفق پاسخ مدل، دکمهٔ **Save validated prompt + output to history** فعال می‌شود. این گزینه همان جفت پرامپت/پاسخ را به‌عنوان checkpoint مهم علامت‌گذاری می‌کند، بدون تکثیر بی‌دلیل محتوای بزرگ. اگر بعد از اعتبارسنجی متن پاسخ را تغییر دهید، پیش‌نمایش و مجوز ثبت قبلی فوراً باطل می‌شوند؛ پاسخ جدید را دوباره تحلیل کنید.
- **دو لایهٔ مرتبط تاریخچه:** تمام پرامپت‌ها، پاسخ‌های مدل، پاسخ‌های نامعتبر و خطاهای دستی در تاریخچهٔ مکالمه/ممیزی محلی ذخیره می‌شوند. checkpointهای ستاره‌دار گام‌هایی‌اند که کاربر عمداً به‌عنوان نقطهٔ مهم انتخاب کرده است. داده‌ها در پوشهٔ همان پروژه و زیر `.workbench/` باقی می‌مانند: گام‌های پرامپت/پاسخ در `.workbench/conversation_history/` و دفتر نسخه‌ها و snapshot پاسخ در `.workbench/project_versions/`. این اطلاعات به نصب برنامه وابسته نیستند و با بازکردن مجدد همان پوشهٔ پروژه بارگذاری می‌شوند.
- **دفتر ثبت نسخهٔ پروژه:** تنها پس از تأیید صریح کاربر و اعمال موفق فایل‌ها، اگر هش درخت فایل واقعاً تغییر کرده باشد نسخهٔ جدید ایجاد می‌شود. رکورد شامل نسخهٔ والد، فهرست فایل‌های تغییرکرده، فهرست و هش فایل‌های پروژه، شناسهٔ گام تاریخچه، هش پرامپت/پاسخ و در صورت امکان snapshot مستقل پاسخ است. در درخت History نسخه کنار همان گام دیده می‌شود و پنجرهٔ **Project versions…** امکان بازکردن پرامپت/پاسخ دقیق سازنده را می‌دهد.
- **سیاست SemVer:** در **Project versions…** می‌توان افزایش بعدی را `patch` (پیش‌فرض)، `minor` یا `major` تعیین کرد. تنظیم فقط روی اولین تغییر واقعی فایل‌ها اعمال می‌شود؛ `minor` بخش patch را صفر و `major` بخش‌های minor و patch را صفر می‌کند. اعمال بدون تغییر فایل، این تنظیم را مصرف نمی‌کند. این دفتر ثبت شامل منشأ و inventory است؛ Git، نسخهٔ کامل قابل‌بازگردانی یا اثبات پاس‌شدن تست‌ها نیست.
- **کنترل درخت با راست‌کلیک:** تغییر نام و فراداده، ویرایش پرامپت به‌صورت revision جدید، ستاره‌دار/حذف checkpoint، تعیین والد، انتقال به ریشهٔ تسک، تورفتگی/خروج از تورفتگی، جابه‌جایی بین خواهرها و حذف گام وجود دارد. حذف والد، فرزندان را به سطح والد منتقل می‌کند و رابطهٔ شکسته باقی نمی‌گذارد؛ ایجاد چرخهٔ والد/فرزند رد می‌شود.
- **افزودن تاریخچه به پرامپت:** در مرحلهٔ تولید پرامپت می‌توان افزودن تاریخچه را روشن کرد یا **Add history to prompt** را زد. اگر پاسخ برنامه‌ریزی مدل محدودهٔ تاریخچه را درخواست کند، scope و شناسهٔ گام‌ها ذخیره شده و در پرامپت بعدی لحاظ می‌شوند. تاریخچه به‌طور خودکار به چت GPT/Gemini ارسال نمی‌شود؛ فقط اگر در پرامپت تولیدشده قرار گرفت و کاربر آن را کپی/ارسال کرد منتقل می‌شود.
- **نوار پیشرفت و حذف پنجره‌های مشکی موقت:** اسکن اولیهٔ پروژه، به‌روزرسانی Git و هش‌گیری نسخه در workerهای همراه با نشانگر پیشرفت اجرا می‌شوند. ثبت نسخه پشت عملیات پس‌زمینهٔ فعال صف‌بندی می‌شود تا تازه‌سازی هم‌زمان Git نتواند رکورد نسخه را بی‌صدا جا بیندازد. برای فرایندهای فرزند ویندوز تا حد پشتیبانی پنجرهٔ کنسول پنهان می‌شود، اما خطاها همچنان ثبت و نمایش داده می‌شوند.

## تغییرات نسخهٔ ۱.۱۰.۰ — رفع ریشه‌ای تشخیص و واردسازی پاسخ مدل

- **پذیرش JSON با قالب‌بندی متداول‌تر:** اگر مدل یک شیء JSON معتبر را با توضیح کوتاه یا حصار Markdown احاطه کند، Workbench می‌تواند همان شیء را تشخیص دهد. اگر چند شیء پروتکلی متعارض وجود داشته باشد، برنامه حدس نمی‌زند و آن را رد می‌کند. خطای JSON ناقص نیز با پیام عمومیِ نامرتبط جایگزین نمی‌شود.
- **رفع ابهام کدبلاک‌ها با `body="raw"`:** قالب جدید Gemini در سرآیند هر فایل حالت خام را صریح مشخص می‌کند. بنابراین اگر خود فایل با سه‌بک‌تیک Markdown شروع یا تمام شود، آن متن دقیقاً حفظ می‌شود و با حصار بسته‌بندی اشتباه گرفته نمی‌شود. قالب حصاردار قدیمی برای سازگاری هنوز پشتیبانی می‌شود.
- **جلوگیری از ادغام خاموش دو فایل:** اگر نشانگر پایان یک فایل قبل از سرآیند فایل بعدی فراموش شده باشد، کل پاسخ رد می‌شود و خطای دقیق دربارهٔ نشانگر مفقود اعلام می‌گردد؛ فایل دوم دیگر اشتباهاً به محتوای فایل اول اضافه نمی‌شود.
- **پیام خطای قابل‌اقدام:** توضیح متنی، Diff بدون مسیر مقصد، کد بدون نام فایل و جمله‌ای مانند «ZIP پیوست شد» بدون فایل واقعی، به‌عنوان فایل قابل‌واردسازی پذیرفته نمی‌شوند. در GPT، اگر فایل ZIP واقعاً دانلود شده است با **Load response / ZIP…** انتخابش کنید؛ در غیر این صورت خروجی JSON کامل را درخواست کنید. در Gemini، تمام بلوک‌های `AIWB_FILE` و نشانگر پایان هر بلوک را عیناً کپی کنید.
- **مدل امن بازبینی حفظ شده است:** تحلیل پاسخ هیچ فایلی را نمی‌نویسد. برای اعمال فایل‌ها پیش‌نمایش Diff و تأیید صریح لازم است و فرمان پیشنهادی مدل نیز مسیر تأیید جداگانه دارد.

قالب جدید بلوک فایل:

```text
<<<AIWB_FILE path="README.md" action="write" body="raw">>>
# محتوای کامل فایل
<<<AIWB_END_FILE>>>
```

نکته: یک خط که دقیقاً برابر نشانگر پایان AIWB باشد نمی‌تواند بدون ابهام در بدنهٔ فایل قرار بگیرد؛ برای چنین فایل‌هایی از JSON استفاده کنید.

## تغییرات نسخهٔ ۱.۹.۰ — اتصال چرخهٔ پرامپت و پاسخ

- **تاریخچهٔ مکالمهٔ محلی هر پروژه:** هر پرامپت تولیدشده به‌صورت `Start` و سپس `Step 1`، `Step 2` و... همراه با شناسهٔ تسک، مرحله، قالب پاسخ، نسخهٔ Workbench و ارتباط با گام قبلی ذخیره می‌شود. در تب **Prompt History** می‌توان پرامپت، پاسخ مدل، خطا و درخواست اطلاعات تکمیلی را در درخت لینک‌شده مشاهده کرد و با فیلتر فراداده بین گام‌های زیاد جست‌وجو کرد. عنوان، بخش/ویژگی، نسخهٔ پروژه و یادداشت‌ها قابل ویرایش‌اند و حذف هر ورودی با اقدام صریح کاربر انجام می‌شود. برای ویرایش خود متن پرامپت از **Edit prompt as new revision…** استفاده کنید؛ یک گامِ کپی و مرتبط ساخته می‌شود و پرامپت/پاسخ اصلی بازنویسی نمی‌شود.
- **گزارش دستی خطای واقعی:** اگر Workbench نتوانست خطای اجرا، کامپایل، تست، شبیه‌سازی یا نصب را تشخیص دهد، از **Report manual runtime / test error…** یا **Report error…** استفاده کنید. پیام خطا/رفتار نادرست، فایل درگیر و مراحل بازتولید ثبت می‌شوند و پرامپت تعمیر به‌عنوان گام بعدیِ مرتبط ساخته می‌شود.
- **درخواست هوشمند فایل و بازهٔ خطوط:** مدل در پاسخ برنامه‌ریزی می‌تواند کل فایل‌های متنی محلی، بازه‌های دقیق شماره‌خط ۱مبنا (هر بازه حداکثر ۵۰۰ خط) یا فایل‌هایی را درخواست کند که باید کاربر دستی در همان گفت‌وگوی GPT/Gemini پیوست کند. فایل کامل در درخت پروژه انتخاب می‌شود؛ بازه‌ها پس از کنترل مسیر، اندازه و احتمال وجود اسرار به پرامپت بعدی افزوده می‌شوند. Workbench خودش فایل را به چت مدل آپلود نمی‌کند و برای فایل‌های باینری/بزرگ/غیرمتنی چک‌لیست واضح نشان می‌دهد.
- **ادامه‌کار متصل به تاریخچه:** handoff ادامه‌کار شامل خلاصهٔ گام‌های اخیر و خطا/درخواست‌های مربوط به مرحلهٔ فعال است؛ در نتیجه شروع، پیاده‌سازی، پاسخ مدل، گزارش خطای دستی و تعمیر از هم جدا و بی‌ارتباط نمی‌مانند.
- **ذخیره‌سازی محدود و قابل‌ردیابی:** فایل‌های تاریخچه در `.workbench/conversation_history/` با نوشتن اتمیک و سقف اندازه/تعداد ذخیره می‌شوند. اگر ذخیرهٔ تاریخچه شکست بخورد، برنامه هشدار می‌دهد و ادعا نمی‌کند که پرامپت با موفقیت بایگانی شده است.

انتقال پرامپت و پاسخ به چت عادی GPT/Gemini همچنان دستی است. ZIP خروجی برای نوشتن فایل‌هاست و فایل‌های باینری مجاز را به‌صورت بایت دقیق حفظ می‌کند؛ برای Delete/Rename/Move از JSON نوع‌دار `workbench-v3` استفاده کن. تاریخچه و Candidateهای محلی ممکن است حاوی کد یا اطلاعات حساس باشند؛ پیش از اشتراک‌گذاری پوشهٔ پروژه آن را بررسی کن. اجرای واقعی نصب‌کننده در ویندوز با آزمون‌های لینوکس تأیید نشده است.

در نسخهٔ 1.8.0، چند مسیر کلیدی برای بالا بردن کیفیت کار روی پروژه‌های چندفایلی و اجرای ابزارها اصلاح شده است:

- **تحویل ZIP برای GPT:** پرامپت می‌تواند از GPT بخواهد در صورت پشتیبانی رابط چت، یک فایل ZIP واقعی و قابل‌دریافت شامل تمام فایل‌های نهایی، `README.md`، نقشهٔ مسیر فایل‌ها و روش نصب/اجرا/تست بسازد. فایل کنترل `AIWB_RESPONSE.json` نیز در ریشهٔ ZIP قرار می‌گیرد؛ اگر فرمانی پیشنهاد نمی‌شود، آرایهٔ `actions` خالی می‌ماند؛ Workbench آن را به‌عنوان فراداده می‌خواند و داخل پروژه نمی‌نویسد. اگر GPT نتواند فایل دانلودی بسازد، باید به JSON ساختاریافته برگردد.
- **ورود امن ZIP:** با گزینهٔ **Load response / ZIP…** آرشیو مستقیم استخراج نمی‌شود. مسیرهای ناامن، لینک‌های نمادین، مسیرهای تکراری با تفاوت حروف بزرگ/کوچک، مقصدهای حساس، فایل‌های بیش‌ازحد بزرگ و محتوای غیر UTF-8 رد می‌شوند. فایل‌های معتبر وارد همان درخت تغییرات و Diff قبلی می‌شوند و نوشتن فایل نیازمند تأیید جداگانه است. نبودن یا خالی‌بودن README ریشه نیز به‌صورت هشدار بازبینی نمایش داده می‌شود.
- **محدودسازی خروجی Runner در حین اجرا:** خروجی `stdout` و `stderr` به‌صورت هم‌زمان خوانده می‌شود و فقط بخش محدود و انتهایی در حافظه نگه داشته می‌شود؛ بنابراین محدودسازی خروجی دیگر فقط بعد از انباشته‌شدن تمام آن انجام نمی‌شود. در Timeout نیز برنامه تلاش می‌کند فرایندهای فرزند را متوقف کند.
- **ثبت منشأ ZIP:** Snapshot پاسخ، نام فایل ZIP، SHA-256، اندازه و تعداد فایل‌های واردشده را ثبت می‌کند؛ مسیر مطلق محلی ذخیره نمی‌شود.

یادداشت تاریخی: نسخه‌های پیش از ۱.۱۳ ZIP را فقط متنی می‌خواندند. نسخهٔ فعلی فایل‌های باینری مجاز را به‌صورت بایت دقیق، همراه اندازه و SHA-256، در مسیر Preview/Apply/Restore نگه می‌دارد. ZIP همچنان مسیر نوشتن است؛ برای Delete/Rename/Move از JSON `workbench-v3` استفاده کن. آزمون Linux جای نصب واقعی ویندوز نیست.

## تغییرات نسخهٔ ۱.۵.۰

۱. **مانیفست زندهٔ توانمندی‌های Workbench:** هر پرامپت تولیدشده شامل نسخهٔ برنامه، وضعیت/فهرست فعلی پروژه، قالب پاسخ انتخاب‌شده، قالب‌های قابل‌قبول، محدودیت اندازه/تعداد فایل و فرمان، قواعد مسیر و امنیت، شیوهٔ تأیید اجرا و تفاوت بین اعمال فایل، اجرای تست و تأیید نهایی است. در مرحلهٔ برنامه‌ریزی، مانیفست قالب JSON را اعلام می‌کند؛ در پیاده‌سازی، قالب انتخاب‌شده را.

۲. **عیب‌یابی واردسازی:** قالب پاسخ، تعداد فایل‌ها و فرمان‌ها، تعداد نشانگرهای آغاز/پایان، مسیرهای شناسایی‌شده و خطاهای اعتبارسنجی نمایش داده می‌شوند. گزارش ساختاریافته در عیب‌یابی Import نگهداری می‌شود؛ متن پاسخ واردشده نیز، در محدودهٔ مجاز تاریخچه، به گام مربوط در Prompt History متصل می‌شود. اگر تشخیص اولیه فرمت شکست بخورد، وارد مسیر اعتبارسنجی و عیب‌یابی می‌شود، نه اینکه فقط پیام وضعیت بدهد.

۳. **درخت فایل و Diff جداگانه برای هر فایل:** پنجرهٔ بازبینی مسیر، وضعیت ایجاد/جایگزینی و اندازهٔ هر فایل را نشان می‌دهد. با انتخاب هر مسیر، Diff مخصوص همان فایل در سمت مقابل دیده می‌شود؛ فرمان‌های پیشنهادی و گام‌های بعدی در برگه‌ای مستقل هستند. شروع تحلیل پاسخ جدید، پیش‌نمایش قبلی را غیرفعال می‌کند تا تغییر قدیمی به‌اشتباه اعمال نشود.

۴. **ماشین حالت تسک:** وضعیت‌ها به‌صورت صریح از Draft تا Prompt Ready، Response Received، Validated، Files Applied، Actions Completed، Tests Run و Verified دنبال می‌شوند. شکست واردسازی، شکست اعمال فایل، شکست فرمان و حالت Blocked نیز جداگانه ثبت می‌شوند. تغییر وضعیت‌ها زمان‌دار و در تاریخچه ثبت می‌شود. برنامه هیچ‌وقت صرفاً به‌دلیل ادعای مدل یا موفقیت نوشتن فایل، وضعیت Verified نمی‌دهد؛ تأیید نهایی با تأیید صریح کاربر است.

۵. **پرامپت تعمیر مبتنی بر خطای واقعی:** خطاهای واردسازی، اعمال فایل یا اجرای تست/فرمان به پرامپتی قابل‌ارسال تبدیل می‌شوند که شواهد ثبت‌شده و قالب اصلاح را مشخص می‌کند. در پنجرهٔ Import diagnostics گزینهٔ **Copy repair prompt…** و در Run & Report گزینهٔ **Repair prompt from latest failure…** وجود دارد. متن خام پاسخ نامعتبر به‌طور پیش‌فرض در پرامپت تعمیر کپی نمی‌شود.

قابلیت‌های نسخهٔ 1.4.1 و قبل از آن—از جمله Snapshot و SHA-256 پاسخ، صف فرمان‌های نیازمند تأیید، تاریخچهٔ اجرا، handoff ادامه‌کار، پرامپت‌های Batch-first، نصب/به‌روزرسانی Git و جلوگیری از اعمال بدون ثبت تاریخچه—حفظ شده‌اند.

رابط خود برنامه انگلیسی است. AI Workbench یک برنامهٔ محلی ویندوز برای مدیریت چند پروژه و استفاده از چت عادی GPT و Gemini با انتقال دستی پرامپت/پاسخ است. به API key مدل احتیاج ندارد و سایت‌های هوش مصنوعی را اسکرپ نمی‌کند.

## تغییرات نسخهٔ ۱.۴

- **ثبت دقیق پاسخ مدل:** هر پاسخ معتبر در `.workbench/latest_model_response.json` ذخیره می‌شود؛ شامل Snapshot نرمال‌شده، SHA-256 پاسخ، مسیر فایل‌ها، هش و اندازهٔ فایل‌ها. شناسهٔ تسک ساخته‌شده توسط Workbench معتبر می‌ماند و شناسه‌ای که مدل ادعا می‌کند جدا ثبت می‌شود.
- **اقدامات پیشنهادی مدل:** پرامپت می‌تواند از مدل بخواهد علاوه بر فایل‌های کامل، چند فرمان تست/Build مستقل و مرتب‌شده را یکجا تولید کند. فرمان‌ها ابتدا اعتبارسنجی و در پنجرهٔ Diff نمایش داده می‌شوند؛ بعد از تأیید تغییر فایل به صف می‌روند. واردکردن پاسخ به‌تنهایی هیچ فرمانی را اجرا نمی‌کند و برای اجرا تأیید جداگانه در تب **Run & Report** لازم است.
- **تاریخچه و بازیابی اجرا:** فایل‌های `action_queue.json`، `execution_history.json` و `task_state.json` داخل `.workbench` وضعیت صف، شروع/پایان، Exit Code، Timeout، زمان اجرا، خروجی و خطاها را ذخیره می‌کنند. اگر برنامه هنگام اجرای فرمان بسته شود، وضعیت آن `Interrupted` ثبت می‌شود؛ چون ممکن است فرمان بخشی از کار را انجام داده باشد. برنامه آن را خودکار تکرار نمی‌کند.
- **پرامپت ادامه‌کار مبتنی بر شواهد:** با **Build continuation handoff** گزارشی شامل وضعیت واقعی فایل‌ها، مقایسهٔ هش، خروجی و کد خروجی فرمان‌ها و گام بعدی ساخته می‌شود. در صورت نیاز می‌توان محتوای کامل آخرین فایل‌های تولیدشده را نیز به گزارش افزود؛ خروجی بزرگ‌تر می‌شود.
- **پرامپت‌های تسک بلندمدت:** حالت **Batch first (minimize interruptions)** از مدل می‌خواهد تا جای ممکن پیاده‌سازی و تست‌های قابل‌پیش‌بینی را در یک پاسخ جمع کند. فقط وقتی نتیجهٔ واقعی اجرا مسیر تصمیم را تغییر دهد، لازم است مکالمه در مرحلهٔ بعد ادامه پیدا کند.
- **نصب و به‌روزرسانی Git:** در تب **Git / GitHub** گزینه‌های **Check Git**، **Install Git** و **Update Git** وجود دارند. نصب/به‌روزرسانی با `winget` و پس از تأیید کاربر انجام می‌شود؛ اگر `winget` موجود نباشد، برنامه می‌تواند صفحهٔ رسمی دانلود Git for Windows را باز کند.
- **جلوگیری از اعمال بدون تاریخچه:** اگر ذخیرهٔ Snapshot دقیق پاسخ یا تاریخچه شکست بخورد، برنامه اجازهٔ نوشتن فایل یا صف‌کردن فرمان را نمی‌دهد تا پاسخ مجدداً پس از رفع مشکل تحلیل و ثبت شود.

## اجرای فایل پروژه و شبیه‌سازی

در تب **Run & Report**، مسیر نسبی فایل را وارد کن یا با **Browse…** انتخابش کن، آرگومان‌های اختیاری و Timeout را تنظیم کن و سپس **Run / simulate selected file…** را بزن. پیش از اجرا، متن فرمان و هشدار دسترسی محلی نمایش داده می‌شوند و باید جداگانه تأیید شوند. برای شماتیک LTspice، برنامه در صورت پیدا کردن LTspice اجرای Batch را پیشنهاد می‌کند و لاگ تغییرکرده را جمع‌آوری می‌کند. اگر LTspice پیدا نشد، نصب یا تنظیم مسیر `LTSPICE_EXE` لازم است. برنامه فقط پسوندهای مشخص را Runner داخلی دارد؛ برای سایر ابزارها از فرمان دستیِ بازبینی‌شده استفاده کن.

## روش کار پیشنهادی

۱. در تب **Projects** یک پروژه بساز یا پوشهٔ موجود را اضافه کن.
۲. **Project Profile** و وظیفهٔ **Workspace & Prompt** را تنظیم کن.
۳. قالب خروجی و استراتژی اجرا را انتخاب کن. برای کارهای طولانی، **Batch first (minimize interruptions)** معمولاً انتخاب مناسبی است.
۴. فایل‌های Context را بازبینی کن، پرامپت را بساز و به چت عادی GPT یا Gemini منتقل کن.
۵. برای GPT چندفایلی، ZIP دانلودشده را با **Load response / ZIP…** باز کن؛ برای Gemini پاسخ کامل را در **AI Response** Paste کن و **Paste & detect format** را انتخاب کن. اگر قالب رد شد، **Import diagnostics** دلیل را نشان می‌دهد و می‌توانی پرامپت تعمیر را کپی کنی. تمام مسیرهای فایل را در درخت فایل و Diff هر فایل بازبینی کن.
۶. تغییرات فایل را تأیید کن تا فایل‌ها با Backup اعمال و فرمان‌ها فقط به صف اضافه شوند. این مرحله فرمانی اجرا نمی‌کند.
۷. در **Run & Report** فرمان‌ها، مسیر اجرا و Timeout را بازبینی کن و اجرای آن‌ها را جداگانه تأیید کن. فرمان‌ها به‌ترتیب اجرا می‌شوند و اولین شکست باعث توقف دسته می‌شود.
۸. برای اجرای یک فایل پروژه یا شبیه‌سازی شماتیک، در **Run & Report** از **Run / simulate selected file…** استفاده کن؛ فرمان دقیق، مسیر و Timeout را پیش از تأیید بررسی کن. این قابلیت Sandbox نیست.
۹. خروجی واقعی و Exit Code را بررسی کن. با **Build continuation handoff** گزارش ادامه‌کار را بساز و در همان مکالمهٔ مدل Paste کن. این گزارش از تاریخچهٔ محلی تولید می‌شود، نه از ادعای مدل.
۱۰. وضعیت مرحلهٔ تسک را در AI Response ببین. فقط پس از بررسی واقعی تغییرات و نتایج تست، **Mark Verified** را تأیید کن. سپس وضعیت Git را بررسی کن و پس از آماده‌شدن، روی Branch کاری Commit و Push کن.
۱۱. تاریخچهٔ **Prompt History** را برای مشاهدهٔ `Start` و `Step N` باز کن. عنوان، بخش/ویژگی، نسخه و یادداشت هر گام قابل ویرایش است؛ محتوای اصلی پرامپت/پاسخ برای حفظ سابقه با ویرایش فراداده تغییر نمی‌کند.
۱۲. اگر خطای واقعی در خودکارسازی تشخیص داده نشد، از **Report manual runtime / test error…** استفاده کن؛ گزارش ذخیره و پرامپت تعمیر به‌عنوان گام مرتبط ساخته می‌شود.
۱۳. اگر مدل بازهٔ خطوط یا فایلی را درخواست کرد، **Import context plan** را اجرا کن. بازه‌ها در پرامپت بعدی افزوده می‌شوند؛ فایل‌هایی که اپ نمی‌تواند امن در متن بگنجاند باید خودت به همان چت GPT/Gemini پیوست کنی.

## قالب‌های خروجی

### ZIP قابل‌دانلود GPT

برای پروژه‌های چندفایلی GPT، قالب **GPT downloadable ZIP + usage guide** را انتخاب کن. آرشیو باید فایل‌های پروژه را مستقیماً در ریشه داشته باشد، `README.md` شامل روش راه‌اندازی/اجرا و نقشهٔ فایل‌ها داشته باشد و یک فایل کنترل ریشهٔ `AIWB_RESPONSE.json` با پروتکل `workbench-v2` داشته باشد؛ حتی اگر فرمان پیشنهادی وجود ندارد، `actions` خالی می‌ماند. این مسیر ZIP برای نوشتن فایل است؛ اگر حذف/تغییرنام/جابه‌جایی لازم است، از JSON سخت‌گیرانهٔ `workbench-v3` استفاده کن. Workbench این فایل کنترل را وارد پروژه نمی‌کند؛ فقط فراداده و فرمان‌ها را اعتبارسنجی می‌کند. ZIP را از چت دانلود و با **Load response / ZIP…** انتخاب کن. اگر GPT نتواند فایل ضمیمه تولید کند، پاسخ باید به JSON سخت‌گیرانه برگردد.

### `workbench-v3` — JSON با عملیات نوع‌دار

از این قالب وقتی استفاده کن که پاسخ باید فایل را حذف، تغییرنام یا جابه‌جا کند. شیء بالادستی دارای آرایهٔ `operations` است. نوع `write` مسیر نسبی و محتوای کامل UTF-8 می‌گیرد؛ `delete` مسیر موجود؛ `rename` مسیر مبدأ و مقصد در همان پوشه؛ و `move` مسیر مبدأ و مقصد متفاوت. هر عملیات شناسهٔ یکتا دارد و مقصد باید وجود نداشته باشد. خروجی ادغام‌شده و خروجی مستقیم هر دو از اعتبارسنجی، Preview، تأیید Apply، پشتیبان و Restore مبتنی بر هش عبور می‌کنند.

پروتکل‌های `workbench-v1` و `workbench-v2` و بلوک‌های Gemini همچنان برای نوشتن فایل سازگار هستند.

### `workbench-v2` — JSON سازگار برای نوشتن فایل


پاسخ باید یک شیء JSON با کلیدهای `protocol`، `task_id`، `summary`، `files`، `actions`، `next_steps` و `completion_status` باشد. محتوای هر فایل باید نسخهٔ کامل نهایی متن UTF-8 با مسیر نسبی باشد. هر action شناسه، هدف، یک فرمان، پوشهٔ کاری نسبی و Timeout دارد. حداقل یکی از آرایه‌های `files` یا `actions` باید یک مورد داشته باشد. اقدامات فقط بعد از اعتبارسنجی و بازبینی کاربر صف می‌شوند.

### بلوک‌های فایل و فرمان Gemini

فایل‌ها با نشانگر `<<<AIWB_FILE path="src/main.py" action="write">>>`، Code Fence شامل محتوای کامل و `<<<AIWB_END_FILE>>>` برگردانده می‌شوند. هر فرمان نیز در بلوک `<<<AIWB_COMMAND ...>>>` با یک خط `Purpose:` و یک فرمان غیرتعاملی مجزا در Code Fence، و سپس `<<<AIWB_END_COMMAND>>>` می‌آید. برای قالب دقیق و همهٔ محدودیت‌ها همیشه از پرامپتی استفاده کن که Workbench تولید کرده است. قالب قدیمی `workbench-v1` برای Manifest فایل پشتیبانی می‌شود. پروتکل رسمی برنامه‌ریزی Context اکنون `workbench-plan-v2` است؛ طرح‌های قدیمی `workbench-plan-v1` با نام‌های مستعار شناخته‌شده مانند `requests`، `request` و `manual_attachments` پیش از اجرای همان اعتبارسنجی سخت‌گیرانهٔ مسیر و ساختار، به قالب استاندارد مهاجرت داده می‌شوند.

## امنیت و محدودیت‌ها

- حساب‌های عادی GPT/Gemini مستقیماً به فایل‌های محلی دسترسی ندارند؛ پرامپت و پاسخ را دستی بین چت و Workbench جابه‌جا می‌کنی.
- فایل‌هایی که در پرامپت قرار می‌دهی ممکن است پس از Paste برای سرویس ابری ارسال شوند؛ محتوای محرمانه را وارد نکن.
- **فرمان تأییدشده با مجوزهای همان حساب ویندوز اجرا می‌شود.** اسکنر فرمان، بررسی ایستا و مبتنی بر الگو است؛ Sandbox کامل نیست و نمی‌تواند همهٔ فرمان‌های خطرناک را تشخیص دهد. فرمانی را که نمی‌فهمی اجرا نکن.
- فرمان‌های مدل هنگام Paste/Import اجرا نمی‌شوند. صف فرمان، بازبینی مستقل و تأیید صریح اجرا دارد.
- زنجیره‌کردن فرمان‌ها، برخی Pipe/Redirectionها و الگوهای مخرب/حذف/انتشار خارجی/مدیریت سیستمی رد یا علامت‌گذاری می‌شوند؛ این‌ها کاهش ریسک‌اند، نه مرز امنیتی کامل.
- فرمان Failed یا `Interrupted` ممکن است بخشی از فایل‌ها یا وضعیت خارجی را تغییر داده باشد؛ پیش از تلاش مجدد، وضعیت پروژه را بررسی کن.
- تشخیص Secret کامل نیست. `.workbench` برای داده‌های محلی Workbench رزرو شده و نوشتن مدل/انتخاب Commit روی آن مسدود است.
- Workbench توکن GitHub را دریافت یا ذخیره نمی‌کند و Push مستقیم به `main`/`master` را مسدود می‌کند.
- هیچ تماس API برای انتقال پرامپت/پاسخ به مدل انجام نمی‌شود؛ انتقال همچنان دستی است.
