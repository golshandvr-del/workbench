## ۰. دستورالعمل مهم برای برنامه‌نویس

این سند را به‌عنوان نقشه‌راه توسعهٔ محصول در نظر بگیر، نه مجوز بازنویسی کل برنامه. پیش از تغییر کد، وضعیت واقعی نسخهٔ 1.14، ساختار ماژول‌ها، migrationهای موجود و مشخصات GitHub/Monorepo که اکنون در حال پیاده‌سازی است بررسی شود. اگر قابلیتی از این سند هم‌اکنون وجود دارد، آن را دوباره از صفر نساز؛ پوشش آزمون، اشکال‌ها و سازگاری آن را بررسی و فقط بخش ناقص را تکمیل کن.

**اصل تغییرناپذیر محصول:** AI Workbench برای استفاده از حساب‌های معمولی رایگان یا پولی مدل‌ها طراحی شده است. کاربر پرامپت را داخل اپ تولید می‌کند، آن را در چت معمولی مدل انتخابی کپی می‌کند، خروجی را از آن چت به Workbench برمی‌گرداند و نتیجه یا پرامپت مرحلهٔ بعد را دریافت می‌کند. در این نقشه‌راه:

- ورود به حساب ChatGPT، Gemini یا سایر مدل‌ها به‌عنوان نیازمندی محصول تعریف نمی‌شود.
- اتصال مستقیم به API مدل‌ها، API Key مدل، فراخوانی خودکار مدل یا جایگزین‌کردن چت معمولی مدل‌ها جزو هدف نیست.
- «Agent» در Workbench یک نقش/پروفایل قابل‌تعریف با مسئولیت، دستورالعمل، قرارداد ورودی و قرارداد خروجی است؛ لزوماً یک فرایند نرم‌افزاری خودمختار یا سرویس آنلاین نیست.
- هماهنگ‌سازی Agentها از طریق تولید پرامپت، کپی دستی، واردکردن پاسخ، بررسی و ساخت Handoff انجام می‌شود.
- GitHub می‌تواند برای نگهداری سورس و انتشار وضعیت پروژه استفاده شود؛ این موضوع به معنی اتصال Workbench به حساب مدل یا ارسال خودکار پیام به چت مدل نیست.
- انتشار وضعیت پروژه در GitHub به معنی آن نیست که مدل به‌صورت خودکار از تغییر مطلع می‌شود. مدل هنگام تعامل بعدی باید بتواند وضعیت منتشرشده را بخواند؛ اگر دسترسی نداشت، Workbench باید خلاصهٔ لازم را داخل پرامپت قرار دهد.
- از طراحی سیستمی که خروجی مدل را بدون بررسی اجرا کند، تغییرات پروژه را بی‌تأیید اعمال کند یا گردش‌کار خودمختارِ بی‌توقف ایجاد کند، خودداری شود.

هدف این است که کپی/پیست باقی بماند، اما اطراف آن—ساخت زمینه، تشخیص پاسخ، مدیریت تلاش‌ها، تقسیم تسک، پیگیری شواهد، انتشار وضعیت و تولید پرامپت بعدی—هوشمند، قابل‌اعتماد و کم‌اصطکاک شود.

## ۱. چشم‌انداز محصول

AI Workbench باید سه مسئلهٔ متصل را حل کند:

1. **کاهش خطا و بار ذهنی در کار روزانه:** کاربر بداند چه کاری باید انجام دهد، خروجی مدل را راحت وارد کند، خطا را بفهمد و بدون ازدست‌دادن پاسخ بتواند ادامه دهد.
2. **مدیریت پروژهٔ چندعاملی (هدف اصلی V2):** چند نقش Agent، حتی وقتی با مدل‌های متفاوت در چت‌های جداگانه اجرا می‌شوند، بتوانند روی یک پروژهٔ مشترک همکاری کنند. Workbench هدف، تسک‌ها، وابستگی‌ها، تصمیم‌ها، Handoffها و شواهد واقعی را نگه می‌دارد و پرامپت مناسب هر مرحله را تولید می‌کند.
3. **رابط کاربری دوحالته:** کاربر مبتدی فقط قدم بعدی روشن را ببیند؛ کاربر حرفه‌ای بتواند Agentها، گراف وابستگی، Revisionها، شواهد، GitHub Publish و سیاست‌ها را با جزئیات مدیریت کند.

### ۱.۱. تعریف موفقیت

موفقیت پروژه با تعداد دکمه‌ها یا Agentهای تعریف‌شده سنجیده نمی‌شود. معیارهای اصلی عبارت‌اند از:

- کاربر کمتر به علت فرمت خروجی یا خطای Import مجبور به شروع از ابتدا شود.
- هیچ پاسخ دریافتی به علت خطای Parse از دست نرود.
- هر پاسخ به تلاش و تسک درست متصل شود یا پیش از اتصال اشتباه هشدار داده شود.
- یک مدل بتواند خروجی مدل دیگری را بدون نیاز به خواندن کل چت قبلی ادامه دهد، زیرا Handoff اطلاعات لازم را منتقل می‌کند.
- مدیر پروژه از یک Snapshot قابل‌ردیابی استفاده کند، نه از حافظهٔ نامطمئن چت یا خلاصهٔ دست‌ساز.
- ادعاهای مدل از شواهد واقعی Workbench جدا باشند.
- کاربر همیشه بداند قدم بعدی چیست و چرا.
- حالت ساده و پیشرفته از یک مدل داده و منطق واحد استفاده کنند؛ دو پیاده‌سازی جدا و ناسازگار ایجاد نشود.

## ۲. سه فاز محصول و نسبت آن‌ها

### فاز اول — هوشمندسازی گردش‌کار و رفع سردرگمی

تمرکز: به‌ویژه مرحلهٔ دریافت و واردکردن خروجی مدل. این فاز باید پاسخ خام را حفظ کند، مشکلات را دقیق توضیح دهد، بازیابی از خطا را آسان کند و شناسه‌ها/Revisionهایی را معرفی کند که فاز دوم روی آن‌ها ساخته می‌شود.

### فاز دوم — V2: برنامه‌ریزی پروژه و همکاری چند Agent

**این فاز مهم‌ترین هدف پروژه است و باید بیشترین دقت طراحی و سهم توسعه را دریافت کند.** شامل قرارداد Agent/Task، گراف وابستگی، Handoff بین مدل‌های متفاوت، وضعیت و شواهد پروژه، مدیر پروژهٔ دستی، پیشنهادهای ساختاریافته، انتشار خودکار Project State در GitHub و اعتبارسنجی کار قبل از تکمیل Task است.

فاز دوم را به زیرمرحله‌های کوچک و قابل‌آزمایش تقسیم کن؛ ولی آن را به چند قابلیت پراکنده تبدیل نکن. تمام اجزا باید در یک سناریوی انتهابه‌انتها با هم کار کنند.

### فاز سوم — رابط کاربری دوحالته و پالایش تجربه

تمرکز: حالت ساده و پیشرفته، نمایش واضح قدم بعدی، مدیریت تراکم اطلاعات، سازگاری اصطلاحات و زیباسازی گرافیک. این فاز نباید برای شروع اصلاح خطاهای مهم یا طراحی قراردادهای فاز دوم به تعویق انداخته شود؛ اصول UI از ابتدا رعایت می‌شوند، اما بازطراحی بصری گسترده پس از تثبیت مدل کاربری انجام می‌شود.

## ۳. اصول معماری مشترک

این اصول در هر سه فاز الزامی‌اند:

### ۳.۱. Workbench مرجع وضعیت محلی است

پایگاه دادهٔ محلی و سرویس‌های معتبر Workbench منبع اصلی وضعیت کاربر، تسک‌ها و نتایج مشاهده‌شده‌اند. GitHub یک Projection/Snapshot منتشرشده از وضعیت است. چت مدل و پاسخ مدل منبع نهایی وضعیت نیستند.

اگر GitHub موقتاً در دسترس نباشد، کار محلی باید ادامه پیدا کند و انتشار در صف بماند. اگر مدل ادعا کند Task تکمیل شده، این ادعا به‌تنهایی وضعیت داخلی Task را به `done` تغییر نمی‌دهد.

### ۳.۲. وضعیت واقعی از ادعای مدل جداست

این سه مفهوم با هم یکی نیستند:

- «مدل گزارش کرده که تست را اجرا کرده است»؛
- «Workbench فرمان تست را واقعاً اجرا کرده و کد خروج/Log را ثبت کرده است»؛
- «معیار پذیرش پروژه با شواهد تعریف‌شده تأیید شده است».

هر سه باید به‌صورت جدا ثبت شوند. نبود شواهد یعنی `unknown` یا `not_verified`، نه موفقیت.

### ۳.۳. همه چیز Revision و ID پایدار دارد

پروژه، Agent، Task، Task Revision، Attempt، Handoff، Decision، Evidence و State Snapshot شناسهٔ پایدار داشته باشند. نام و عنوان برای نمایش است؛ شناسه مرجع پیوند بین داده‌هاست.

### ۳.۴. نتیجهٔ هر Attempt حفظ شود

اگر یک Task پنج مرتبه به مدل ارسال شود، پنج Attempt در تاریخچه باقی بمانند. پاسخ جدید پاسخ قبلی را بازنویسی نکند. وضعیت فعلی Task از روی رویدادهای معتبر و تصمیم‌ها محاسبه شود.

### ۳.۵. Parse، Review، Apply، Validation و Publish مراحل متمایزند

دریافت پاسخ هیچ فایل یا تنظیمی را تغییر نمی‌دهد. Parse موفق به معنی پذیرفته‌شدن پاسخ نیست. پذیرفته‌شدن پاسخ به معنی Apply نیست. Apply به معنی Validation موفق نیست. تغییر محلی به معنی Publish موفق نیست.

### ۳.۶. عملیات تکراری باید idempotent باشند

اگر کاربر دوبار روی Import، Apply یا Publish کلیک کرد یا برنامه بعد از شکست مجدداً عملیات را اجرا کرد، نتیجهٔ تکراری/خراب ایجاد نشود. برای هر عملیات شناسه، وضعیت و نتیجه ثبت شود.

### ۳.۷. قراردادها نسخه‌گذاری شوند

تمام Schemaهای پایدار یک `schema_version` داشته باشند. داده‌های قدیمی با migration صریح و تست‌شده منتقل شوند. فیلد اجرایی ناشناخته نباید حدس زده شود. پاسخ‌های فعلی/Legacy همچنان باید از مسیر Import سازگار پشتیبانی شوند.

# فاز اول — هوشمندسازی و کاهش خطای گردش‌کار

## ۴. هدف فاز اول

بیشترین مشکل گزارش‌شده در مرحلهٔ واردکردن خروجی مدل بوده است. بنابراین این مرحله باید پیش از گسترش تعداد Agentها، مسیر واردکردن خروجی را به یک جریان روشن، قابل‌بازیابی و قابل‌تشخیص تبدیل کند.

معیار طراحی: وقتی Import شکست می‌خورد، کاربر نباید بپرسد «حالا چه شد؟»، «پاسخم از بین رفت؟» یا «باید از مدل دوباره بپرسم؟». برنامه باید دقیقاً بگوید چه چیزی دریافت شد، چه چیزی فهمیده شد، چه چیزی نامعتبر بود و سریع‌ترین اقدام امن چیست.

## ۵. Response Inbox: ورودی یکپارچه برای همهٔ پاسخ‌ها

### ۵.۱. پاسخ خام همیشه حفظ شود

هنگام Paste، Drag & Drop یا انتخاب فایل، ابتدا ورودی خام را با شناسهٔ `response_id` ذخیره کن؛ سپس Parse را در یک مرحلهٔ جدا انجام بده. هرگز قبل از ذخیرهٔ پاسخ خام، Normalize، حذف Markdown، تغییر encoding یا استخراج فایل انجام نده.

داده‌های پیشنهادی برای ورودی خام:

- `response_id` و زمان دریافت؛
- `project_id` در صورت انتخاب؛
- `task_id`, `task_revision`, `attempt_id` اگر قابل تعیین باشند؛
- روش دریافت (`clipboard`, `file`, `zip`, `manual` و غیره)؛
- نوع ورودی و اندازهٔ محلی؛
- Hash محتوای خام؛
- وضعیت Parse و خطاها؛
- پیوند به فایل خام یا محل امن ذخیره‌سازی.

پاسخ خام نباید با دادهٔ Parseشده یکی باشد. اگر Parse خراب شد، کاربر باید بتواند همان پاسخ را دوباره با Parser یا حالت Import متفاوت بررسی کند.

### ۵.۲. تشخیص نوع پاسخ

پیش از Parse، یک مرحلهٔ Classification سبک اجرا شود که پاسخ را به یکی از دسته‌های احتمالی هدایت کند:

- پاسخ متنی عادی؛
- بلوک ساختاریافتهٔ AIWB؛
- JSON؛
- خروجی چندفایلی Markdown؛
- ZIP؛
- Patch/Diff؛
- گزارش مدیر پروژه یا Planner؛
- Handoff یک Agent؛
- محتوای ناشناخته.

این تشخیص فقط پیشنهاد Parser است، نه مجوز اجرای عملیات. اگر اطمینان کافی نیست، چند گزینهٔ قابل انتخاب نمایش داده شود. برنامه نباید صرفاً به خاطر وجود کلمه‌ای مثل `FILE:` یک خروجی را قطعاً چندفایلی فرض کند.

### ۵.۳. Pipeline واردکردن

منطق را به مراحل مشخص جدا کن:

1. **Capture:** ذخیرهٔ ورودی خام.
2. **Classify:** پیشنهاد نوع پاسخ.
3. **Parse:** استخراج دادهٔ ساختاریافته و Artifactها.
4. **Validate:** اعتبارسنجی Schema، مسیرها، Hashها و فایل‌های مورد انتظار.
5. **Reconcile:** تطبیق پاسخ با Task/Attempt و Revision مبنا.
6. **Preview:** نشان‌دادن برداشت Workbench.
7. **Decision:** پذیرش، رد، اصلاح دستی یا نگه‌داری به‌عنوان پاسخ خام.
8. **Apply/Record:** اجرای عملیات تأییدشده یا ثبت تحویل/گزارش.

هر مرحله باید نتیجه و خطای مستقلی داشته باشد. شکست یک مرحله نباید باعث تکرار یا انجام ناخواستهٔ مراحل قبل شود.

### ۵.۴. خروجی ناقص را نجات بده

اگر پاسخ شامل پنج فایل مورد انتظار است ولی چهار فایل پیدا شده، چهار فایل را از دست نده. نتیجه را به تفکیک نشان بده:

- فایل‌های کامل و معتبر؛
- فایل‌های ناقص یا مبهم؛
- فایل‌های غایب؛
- بخش‌های متنی دریافت‌شده؛
- اقدام پیشنهادی برای دریافت یا اصلاح بخش ناقص.

پرامپت تکمیل خروجی باید فقط فایل‌ها یا بخش‌های مفقود را درخواست کند و شناسهٔ Attempt و فهرست کامل مورد انتظار را به مدل یادآوری کند. اگر برای جلوگیری از ناسازگاری لازم است فایل کامل دوباره ارائه شود، Workbench این علت را توضیح دهد.

### ۵.۵. تشخیص پاسخ قدیمی یا اشتباه

هر Prompt Export شده باید `attempt_id` و Revision تسک را ثبت کند. در صورت امکان این شناسه‌ها داخل قالب خروجی مدل هم قرار گیرند.

اگر پاسخ به Attempt قدیمی وصل شد:

- پاسخ خام ذخیره شود؛
- برچسب `stale_response` یا `attempt_mismatch` نمایش داده شود؛
- Apply خودکار ممنوع باشد؛
- کاربر بتواند آن را به Attempt قدیمی متصل یا برای بررسی مستقل نگه دارد.

اگر شناسه در پاسخ نبود، کاربر بتواند Attempt مقصد را انتخاب کند. عدم وجود شناسه نباید باعث رد همهٔ خروجی‌های Legacy شود.

## ۶. خطاهای قابل‌فهم و راهکارهای بازیابی

### ۶.۱. ساختار پیام خطا

هر خطا باید این اطلاعات را در صورت وجود ارائه دهد:

1. **چه اتفاقی افتاده؟** شرح کوتاه و بدون اصطلاح مبهم.
2. **کدام بخش مشکل دارد؟** نام بلوک، فایل، مسیر یا شمارهٔ خط.
3. **چه چیزی سالم مانده؟** مشخص شود پاسخ خام یا بخشی از Artifactها حفظ شده است.
4. **علت محتمل چیست؟** علت قطعی از حدس جدا باشد.
5. **چه اقدام‌هایی ممکن‌اند؟** Reparse، ورود دستی، کپی متن تشخیصی، درخواست تکمیل از مدل یا لغو.
6. **چه اتفاقی بعد از انتخاب رخ می‌دهد؟** برای جلوگیری از ابهام، اثر هر اقدام قبل از اجرا بیان شود.

نمونهٔ مناسب: «چهار فایل از پنج فایل مورد انتظار شناسایی شد. پاسخ خام ذخیره شده و چهار فایل معتبر از دست نرفته‌اند. `src/restore_ui.py` پیدا نشد. می‌توانی فقط همان فایل را از مدل درخواست کنی، یا واردسازی را به‌عنوان تحویل ناقص ثبت کنی.»

از پیام‌هایی مانند `Invalid output`, `Unexpected error` یا `Import failed` بدون راهکار استفاده نکن؛ خطای فنی کامل می‌تواند در بخش جزئیات باشد.

### ۶.۲. خطاهای استاندارد

حداقل دسته‌های خطا:

- `format_unrecognized`
- `schema_invalid`
- `json_incomplete`
- `expected_artifact_missing`
- `artifact_duplicate`
- `path_invalid`
- `path_conflict`
- `unsafe_archive`
- `attempt_mismatch`
- `stale_base_revision`
- `content_encoding_error`
- `partial_parse`
- `github_unavailable`
- `github_auth_failed`
- `github_conflict`
- `validation_not_run`
- `operation_interrupted`

کد خطا در برنامه پایدار بماند و متن قابل‌نمایش قابل‌ویرایش/ترجمه باشد. پیام UI به متن exception خام وابسته نباشد.

### ۶.۳. Repair Prompt هوشمند

وقتی Import یا Validation شکست می‌خورد، Workbench باید یک Repair Prompt متناسب با خطای واقعی بسازد. پرامپت باید شامل این موارد باشد:

- هدف و شناسهٔ Task؛
- Attempt/Revision مربوطه؛
- خروجی مورد انتظار؛
- بخش معتبر دریافت‌شده؛
- خطا یا اختلاف دقیق؛
- آنچه نباید دوباره تولید یا تغییر کند؛
- قالب دقیق پاسخ اصلاحی.

پرامپت نباید به مدل بگوید تستی موفق بوده که اجرا نشده، و نباید دادهٔ حساس یا مسیرهای محلی خصوصی را بی‌دلیل شامل شود. اگر خروجی شامل فایل‌های سالم و ناقص است، از مدل بخواه فقط موارد مشخص را تکمیل کند، مگر اینکه ادامه با فایل جداگانه ناسازگار شود.

### ۶.۴. Diagnostics محلی

ثبت کند که Parser کدام مرحله را اجرا کرده، چه تعداد Artifact تشخیص داده شده و خطا در کجا رخ داده است. به‌صورت پیش‌فرض پاسخ خام و اطلاعات حساس به سرور خارجی ارسال نشوند. اگر در آینده گزارش تشخیصی قابل‌اشتراک ساخته شود، کاربر باید قبل از Export محتوایش را ببیند.

### ۶.۵. معیارهای پذیرش فاز اول

- پاسخ خام پیش از Parse ذخیره می‌شود.
- شکست Parser هیچ پاسخ یا Artifact سالمی را حذف نمی‌کند.
- پاسخ ناقص به‌صورت جزئی قابل‌بازیابی است.
- کاربر می‌فهمد کدام مرحله شکست خورده، چه چیزی سالم است و قدم بعدی چیست.
- پاسخ قدیمی بی‌صدا جایگزین پاسخ جاری نمی‌شود.
- Import به‌تنهایی فایل نمی‌نویسد و فرمان اجرا نمی‌کند.
- Repair Prompt بر اساس خطا و Attempt واقعی ساخته می‌شود.
- تست‌های رگرسیون برای JSON ناقص، ZIP مخرب، مسیر نامعتبر، Markdown مبهم، چند فایل، پاسخ تکراری و لغو عملیات وجود دارد.

## ۷. پیش‌نیازهای داده‌ای فاز دوم که باید از همین فاز آماده شوند

فاز اول هنوز یک سیستم کامل Agent نمی‌سازد، اما باید زمینهٔ فنی آن را فراهم کند:

- شناسهٔ مستقل برای Task/Attempt/Response؛
- ذخیرهٔ Raw Response و Parse Result به‌صورت جدا؛
- `schema_version` برای پاسخ ساختاریافته؛
- تمایز ادعای مدل از شاهد اجرای برنامه؛
- ثبت Revision مبنای پروژه؛
- API داخلی/سرویس برای ایجاد پیام خطا و Repair Prompt؛
- قابلیت Reparse بدون دریافت مجدد پاسخ از مدل.

این موارد را به شکل سرویس‌های قابل‌استفادهٔ مجدد پیاده‌سازی کن؛ از ساخت منطق مخصوص هر نوع Agent در UI جلوگیری شود.

# فاز دوم — V2: سیستم مدیریت پروژه با چند Agent

## ۸. هدف اصلی فاز دوم

فاز دوم باید این امکان را بدهد که کاربر یک پروژه را تعریف کند، یک Agent را به‌عنوان مدیر پروژه انتخاب کند، چند نقش دیگر را برای مأموریت‌های مشخص به‌کار بگیرد و با انتقال دستی پرامپت و پاسخ بین چت‌های مختلف، پروژه را به‌صورت منظم پیش ببرد.

مدیر پروژه ممکن است در یک چت GPT باشد؛ معمار یا برنامه‌نویس در چت Gemini؛ بازبین نیز می‌تواند با مدل دیگری اجرا شود. Workbench قرار نیست وارد هیچ‌یک از این حساب‌ها شود یا از طرف آن‌ها پیام بفرستد.

Workbench باید:

- پروژه و مرجع وضعیت آن را نگه دارد؛
- Agentها را به‌صورت نقش‌های قابل‌تعریف مدیریت کند؛
- طرح پروژه و گراف وابستگی تسک‌ها را نگه دارد؛
- برای هر Agent Prompt/Handoff صحیح بسازد؛
- پاسخ را به Task/Attempt صحیح وصل کند؛
- پیشنهادهای مدل را از تغییرات تأییدشده جدا نگه دارد؛
- شواهد واقعی فایل و تست را ثبت کند؛
- وضعیت پروژه را با Revision مشخص در GitHub منتشر کند؛
- به مدیر پروژه اجازه دهد در تعامل بعدی بر اساس Snapshot منتشرشده برنامه‌ریزی کند؛
- در هر لحظه قدم بعدی روشن را به کاربر نشان دهد.

### ۸.۱. تعریف صریح «اتمام V2»

V2 زمانی قابل‌قبول است که یک سناریوی واقعی کامل از ابتدا تا انتها قابل اجرا باشد: تعریف پروژه → ایجاد/تأیید طرح → ایجاد چند Task وابسته → اجرای دستی حداقل دو نقش با دو چت/مدل متفاوت → دریافت و پذیرش Handoff → ثبت شواهد → انتشار Project State در GitHub → ساخت گزارش برای مدیر پروژه → دریافت پیشنهاد تغییر برنامه → Review و پذیرش/رد پیشنهاد → ادامهٔ کار بدون گم‌شدن تاریخچه.

تکمیل پنجرهٔ Agentها یا ساخت یک نمودار تسک به‌تنهایی به معنی تحقق V2 نیست.

## ۹. معماری مفهومی فاز دوم

مسیر اصلی داده:

`Project Definition → Agent/Task Plan → Task Attempt → Prompt/Handoff → Manual Model Chat → Response Inbox → Parse/Reconcile → Review → Apply/Validation → Evidence/State Update → GitHub Snapshot → Manager Update Prompt → Proposal Review`

تمام مسیرها از سرویس‌های داخلی قابل‌آزمون بگذرند. UI نباید خودش Taskها را تغییر دهد یا مستقیماً GitHub را بنویسد. Parser نباید فایل Apply کند. Publisher نباید از پاسخ خام مدل، وضعیت پروژه را خودش حدس بزند.

### ۹.۱. اجزای سرویس پیشنهادی

نام فایل‌ها قابل‌تغییر است؛ مسئولیت‌ها باید جدا باشند:

- `agent_registry`: نگهداری پروفایل نقش‌های Agent.
- `task_service`: Task، Revision، وابستگی‌ها و اعتبارسنجی گراف.
- `attempt_service`: تلاش‌های مستقل مدل و وضعیت آن‌ها.
- `handoff_service`: ساخت/اعتبارسنجی Handoff و Prompt مربوطه.
- `response_inbox`: پاسخ خام، Parse، Reconcile و بازیابی خطا.
- `decision_ledger`: تصمیم‌های پیشنهادی/تأییدشده/ردشده/جایگزین‌شده.
- `evidence_service`: ثبت شواهد واقعی و اتصال آن‌ها به Task/Attempt/Commit.
- `project_state_service`: محاسبهٔ Snapshot از یک وضعیت محلی سازگار.
- `github_state_publisher`: انتشار Snapshot، صف و مدیریت تعارض.
- `proposal_review_service`: تبدیل پاسخ مدیر پروژه به پیشنهادهای ساختاریافته و بازبینی آن‌ها.
- `next_action_service`: محاسبهٔ اقدام پیشنهادی بعدی و دلیل آن.

اگر پروژه در حال حاضر سرویس‌هایی مشابه دارد، همان‌ها توسعه داده شوند؛ از ساخت نسخهٔ موازی و دو منبع حقیقت اجتناب شود.

## ۱۰. قرارداد پایهٔ اول: Agent و Task

### ۱۰.۱. Agent یک نقش است، نه یک حساب/مدل

هر Agent باید شناسهٔ پایدار و پروفایل قابل‌ویرایش داشته باشد. مدل ترجیحی تنها یک پیشنهاد برای کاربر است؛ تعویض مدل نباید شناسه یا هویت نقش را تغییر دهد.

فیلدهای حداقلی Agent:

- `agent_id`: شناسهٔ پایدار.
- `name`: نام نمایشی.
- `role`: مانند `project_manager`, `architect`, `implementer`, `reviewer`, `researcher`.
- `purpose`: مسئولیت و محدودهٔ نقش.
- `instructions`: دستورالعمل پایدار نقش.
- `preferred_model_label`: مدل ترجیحی به‌صورت متن/برچسب؛ بدون اتصال به حساب مدل.
- `input_contract`: اطلاعاتی که باید در ورودی مأموریت حاضر باشند.
- `output_contract`: داده‌ها/Artifactهای مورد انتظار.
- `allowed_task_types`: انواع تسکی که Agent برای آن مناسب است.
- `review_policy`: الزامات بازبینی خروجی.
- `escalation_rules`: شرایطی که Agent باید سؤال یا مانع را به کاربر برگرداند.
- `revision`, `created_at`, `updated_at`, `enabled`.

Agentهای پایه به‌صورت Template ارائه شوند؛ کاربر بتواند نسخهٔ شخصی بسازد، کپی کند یا دستورالعمل را اصلاح کند. تغییر Template پیش‌فرض نباید پروفایل‌های موجود کاربر را بی‌صدا بازنویسی کند.

### ۱۰.۲. Task یک شیء مستقل از مکالمه است

Task باید هدف، محدوده و معیار پذیرش داشته باشد و مستقل از چت قابل پیگیری باشد.

فیلدهای حداقلی Task:

- `task_id`, `task_revision`, `project_id`;
- `title`, `objective`, `context_refs`;
- `owner_agent_id` و نقش‌های کمکی/بازبین در صورت وجود؛
- `depends_on`;
- `scope.include` و `scope.exclude`؛
- `acceptance_criteria`؛
- `deliverables`؛
- `base_state_revision`, `base_commit_sha`, و در صورت نیاز Hash فایل‌های مرجع؛
- `priority`, `risk_level`, `required_approvals`;
- `status`, `created_at`, `updated_at`;
- `origin`: دستی، پیشنهاد مدیر پروژه، Playbook یا مهاجرت.

شرح Task بعد از آغاز Attempt نباید بی‌صدا تغییر کند. تغییر هدف، Scope یا معیار پذیرش یک Revision جدید ایجاد کند. Attempt قدیمی به Revision قبلی باقی بماند تا معلوم باشد مدل در زمان تولید پاسخ چه دستورالعملی داشته است.

### ۱۰.۳. Task و Attempt ماشین وضعیت جدا دارند

وضعیت‌های پیشنهادی Task:

- `draft`: تعریف اولیه.
- `proposed`: پیشنهادشده، منتظر تأیید در صورت نیاز.
- `ready`: پیش‌نیازهای لازم برآورده شده و آمادهٔ شروع است.
- `in_progress`: یک Attempt فعال دارد.
- `blocked`: مانع مشخصی دارد.
- `needs_decision`: تصمیم انسانی یا معماری لازم است.
- `in_review`: تحویل آمادهٔ بازبینی است.
- `validation_pending`: نیازمند تست/بررسی است.
- `done`: تمام معیارهای الزامی طبق سیاست Task با شواهد کافی برآورده شده‌اند.
- `cancelled`: لغوشده با حفظ تاریخچه.
- `superseded`: با Task/Revision جدید جایگزین شده.

وضعیت‌های پیشنهادی Attempt:

- `created`, `prompt_ready`, `exported`, `waiting_response`, `response_received`, `parse_failed`, `parsed`, `reconciliation_required`, `ready_for_review`, `accepted`, `rejected`, `stale`, `abandoned`.

وضعیت‌ها و انتقال مجازشان در یک سرویس مرکزی تعریف شوند. UI نباید آزادانه هر enum را هر زمان تغییر دهد.

### ۱۰.۴. اعتبارسنجی گراف وابستگی

قبل از پذیرش یک طرح مدیر پروژه:

- Task نمی‌تواند به خودش وابسته باشد.
- چرخه‌های وابستگی شناسایی و رد شوند.
- شناسهٔ Task ناموجود به‌عنوان وابستگی پذیرفته نشود.
- حذف یا لغو پیش‌نیاز، Task وابسته را خودکار آزاد نکند؛ باید آن را مسدود یا نیازمند بازبرنامه‌ریزی کند.
- Task فقط وقتی `ready` باشد که تمام پیش‌نیازهای الزام‌آور آن طبق سیاست پروژه برآورده شده باشند.
- اگر معیار پذیرش/Scope یک Task تغییر کرده، Taskهای وابستهٔ مرتبط علامت‌گذاری شوند تا بررسی شوند.

### ۱۰.۵. موازی‌سازی محدود و مبتنی بر وابستگی

Workbench در ابتدا نباید سعی کند همهٔ Taskها را موازی کند. پیشنهاد موازی‌سازی فقط زمانی نمایش داده شود که:

- پیش‌نیازهای هر دو Task تکمیل‌اند؛
- محدودهٔ فایل‌ها یا خروجی‌هایشان هم‌پوشانی خطرناک ندارد؛
- قرارداد مشترک تثبیت شده است؛
- اگر خروجی مشترکی لازم است، مالک و معیار ادغام مشخص‌اند.

اگر دو Task فایل مشترک یا مسئولیت معماری مشترک دارند، به‌صورت پیش‌فرض هم‌زمان آماده نشوند؛ یا یکی مالک باشد و دیگری فقط پیشنهاد تغییر بدهد، یا یک مرحلهٔ هماهنگی قبل از پیاده‌سازی تعریف شود.

در نسخهٔ اول V2، موازی‌سازی یعنی چند Task مستقل بتوانند هم‌زمان در وضعیت‌های متفاوت باشند؛ این به معنی اجرای خودکار چند مدل در پس‌زمینه نیست. کاربر همچنان پرامپت‌ها را دستی به چت‌ها می‌برد.

## ۱۱. قرارداد پایهٔ دوم: Handoff Protocol

### ۱۱.۱. هدف

Handoff سازوکار رسمی انتقال کار و زمینه از Agent/Attempt مبدأ به Agent/Attempt مقصد است. این پروتکل باید کاری کند که GPT بتواند خروجی Gemini را ادامه دهد یا برعکس، بدون اینکه کاربر ناچار شود تاریخچهٔ طولانی هر دو چت را دستی خلاصه کند.

### ۱۱.۲. محتویات Handoff

هر Handoff حداقل شامل سه بخش است:

**الف) مأموریت مقصد:** Task و Revision، هدف، Scope، معیار پذیرش، محدودیت‌ها و خروجی مورد انتظار.

**ب) زمینهٔ معتبر:** خلاصهٔ پروژهٔ موردنیاز، تصمیم‌های تأییدشدهٔ مرتبط، خروجی Taskهای وابسته، Artifactهای انتخاب‌شده و Revision مبنا.

**ج) تحویل مبدأ:** گزارش کار انجام‌شده، فایل‌های تحویل‌شده، موارد ناقص، فرض‌ها، یافته‌های بازبین، شواهد واقعی، ادعاهای تأییدنشده و سؤال‌هایی که نیاز به تصمیم دارند.

### ۱۱.۳. فیلدهای حداقلی Handoff

- `handoff_id`, `schema_version`, `project_id`;
- `task_id`, `task_revision`, `attempt_id`;
- `from_agent_id`, `to_agent_id`;
- `created_at`;
- `base_state_revision`, `base_commit_sha`, و در صورت نیاز `base_artifact_hashes`;
- `outcome`: `complete`, `partial`, `blocked`, `needs_decision`, `failed`؛ این مقدار فقط گزارش وضعیت تحویل است، نه وضعیت نهایی Task.
- `summary`, `completed_items`, `unresolved_items`, `assumptions`, `decision_requests`;
- `artifact_refs` شامل `artifact_id`, مسیر منطقی، Hash، نوع و منشأ؛
- `validation_claims` برای ادعاهای مدل؛
- `verified_evidence_ids` برای شواهد ثبت‌شده توسط Workbench؛
- `recommended_next_action`؛
- `source_response_id` و منشأ داده.

### ۱۱.۴. قالب پرامپت Handoff

پرامپت تولیدشده باید بخش‌های مشخص و قابل‌تشخیص داشته باشد:

1. شناسه و نقش Agent مقصد؛
2. مأموریت فعلی؛
3. معیارهای پذیرش و محدودیت‌ها؛
4. خلاصهٔ تأییدشدهٔ پروژه؛
5. Handoff قبلی؛
6. فهرست فایل‌ها/اسناد مرتبط و روش استفاده از آن‌ها؛
7. تعارض‌ها و مواردی که نباید فرض گرفته شوند؛
8. قالب تحویل مورد انتظار؛
9. دستور صریح برای تفکیک کار انجام‌شده، پیشنهادی، اجرا‌نشده و نیازمند تصمیم.

مدل مجبور نباشد کل پاسخ را JSON کند. توضیحات انسان‌خوان و فایل‌ها می‌توانند با قالب‌های موجود برگردند، اما یک بخش Manifest ساختاریافته باید در صورت امکان شناسه‌ها، فهرست Artifactها، وضعیت ادعاشده و موارد ناقص را ارائه کند. Parser باید حالت Legacy و Import دستی را حفظ کند.

### ۱۱.۵. چرخهٔ وضعیت Handoff

`prepared → prompt_exported → response_received → parsed → reconciled → accepted/rejected/superseded`

این وضعیت‌ها نباید به‌عنوان یک فرایند خودکار مدل تعبیر شوند. هر کدام نشان‌دهندهٔ وضعیت واقعی داخل Workbench‌اند.

- اگر خروجی ناقص است، Handoff می‌تواند `partial` باشد و Artifactهای سالم حفظ شوند.
- اگر Revision مبنا قدیمی است، `reconciliation_required` یا `stale` شود؛ Apply خودکار انجام نشود.
- اگر پاسخ به Attempt دیگری تعلق دارد، همان Response حفظ شود ولی Handoff جاری را تکمیل نکند.
- اگر کاربر Handoff را رد کند، دلیل رد و پاسخ اصلی بمانند و Attempt جدید تولید شود.

### ۱۱.۶. معیار پذیرش Handoff

- یک Task می‌تواند از GPT به Gemini و سپس به یک Agent بازبین منتقل شود بدون گم‌شدن ID و تاریخچه.
- خروجی مدل دوم به Revision و Handoff ورودی قابل‌ردیابی باشد.
- Artifactها Hash داشته باشند و منشأ هر فایل معلوم باشد.
- ادعای مدل دربارهٔ تست از Evidence واقعی جدا بماند.
- پاسخ ناقص یا قدیمی باعث رد بی‌دلیل تمام پاسخ نشود، اما به‌صورت امن از Apply خودکار جلوگیری کند.
- کاربر بتواند بستهٔ Handoff و پرامپت نهایی را قبل از Copy مشاهده و ویرایش کند.

## ۱۲. قرارداد پایهٔ سوم: Project State، Decision Ledger و Evidence

### ۱۲.۱. مرجع وضعیت و Snapshot

وضعیت محلی Workbench منبع اصلی است. GitHub یک Projection منتشرشده و قابل‌خواندن است. مدل مدیر پروژه می‌تواند این Projection را بخواند، اما نمی‌تواند با ادعای خود وضعیت داخلی را مستقیماً تغییر دهد.

`Project State Snapshot` باید از یک Revision محلی سازگار تولید شود، نه از خواندن پراکندهٔ چند جدول در زمان‌های متفاوت. Snapshot پس از ساخته‌شدن immutable باشد؛ تغییر بعدی یک Revision جدید بسازد.

### ۱۲.۲. فیلدهای Manifest

حداقل:

- `schema_version`;
- `project_id`, `state_revision`, `generated_at_utc`;
- `previous_snapshot_hash` یا ارجاع قبلی؛
- `source.repository_id`, `source.repository`, `source.branch`, `source.commit_sha`;
- `source.local_changes_pending` و در صورت نیاز تعداد/فهرست محدود فایل‌های تغییرکرده، بدون افشای محتوای سورس؛
- هدف/خلاصهٔ تأییدشدهٔ پروژه و فاز جاری؛
- شمارش تسک‌ها که توسط Workbench محاسبه شده باشد؛
- شناسه‌های Taskهای فعال، مسدود و نیازمند تصمیم؛
- شناسهٔ تصمیم‌های باز؛
- آخرین Evidence معتبر و وضعیت Validation؛
- اقدام پیشنهادی بعدی که Workbench از وضعیت واقعی محاسبه کرده یا کاربر تأیید کرده است؛
- آخرین وضعیت Publish و اطلاعات منشأ.

Manifest نباید توسط مدل تولید شود. مدل می‌تواند Patch پیشنهادی ارائه کند، اما Manifest نهایی از داده‌های معتبر محلی ساخته می‌شود.

### ۱۲.۳. Decision Ledger

هر تصمیم مهم یک رکورد مستقل داشته باشد:

- `decision_id`, `revision`, عنوان و مسئله؛
- گزینه‌های بررسی‌شده؛
- تصمیم پذیرفته‌شده و دلیل؛
- وضعیت: `proposed`, `accepted`, `rejected`, `superseded`؛
- منشأ پیشنهاد؛
- تأییدکننده و زمان تأیید؛
- Taskها/قراردادهای متأثر؛
- ارجاع به تصمیم قبلی که جایگزین شده است.

تصمیم ردشده حذف نشود. این کار مانع پیشنهاد مکرر یک گزینهٔ ردشده و فراموش‌شدن دلیل تصمیم می‌شود.

### ۱۲.۴. Evidence Ledger

هر Evidence حداقل شامل این موارد باشد:

- `evidence_id`, نوع، زمان مشاهده؛
- موضوع مرتبط: Task، Handoff، Artifact، Commit یا عملیات؛
- منشأ مشاهده: اجرای واقعی Workbench، GitHub Actions، تأیید کاربر یا گزارش مدل؛
- Revision/Commit مرتبط؛
- نتیجه و خلاصه؛
- مسیر/URL/Log مرجع در صورت وجود؛
- `verified` و روش تأیید؛
- Hash یا شناسهٔ Artifact در صورت کاربرد.

انواع مهم:

- `model_report`: ادعای مدل، بدون اثبات خودکار؛
- `file_change`: تغییر مشاهده‌شدهٔ فایل؛
- `test_run`: فرمان تست واقعاً اجراشده و نتیجه؛
- `build_run`: Build واقعی و Commit سازنده؛
- `git_operation`: نتیجهٔ Pull/Commit/Push/Merge؛
- `manual_review`: تصمیم یا تأیید انسان؛
- `external_artifact`: فایل واقعی دریافت‌شده از CI.

### ۱۲.۵. محاسبهٔ وضعیت نهایی Task

سرویس مرکزی باید وضعیت Task را بر اساس قرارداد و Evidence محاسبه/اعتبارسنجی کند. مثال:

- Agent گزارش می‌کند پیاده‌سازی تمام شده؛ Task می‌تواند به `in_review` برود، نه مستقیم `done`.
- Diff پذیرفته و اعمال شده؛ Task هنوز ممکن است `validation_pending` باشد.
- تست تعریف‌شده موفق شده و تأییدهای لازم کامل‌اند؛ Task می‌تواند `done` شود.
- تست اجرا نشده یا ابزار موجود نیست؛ وضعیت باید `not_verified`/`validation_pending` یا مانع مشخص باشد.
- معیار پذیرش صرفاً مستلزم Artifact و تأیید انسانی است؛ Workbench باید همان سیاست ثبت‌شده را رعایت کند، نه اینکه برای همهٔ Taskها الزام تست کدنویسی فرض کند.

### ۱۲.۶. Publish به GitHub

انتشار وضعیت باید از یک Publisher واحد انجام شود. هیچ UI یا Agent مستقیماً فایل Snapshot را به GitHub ننویسد.

تنظیمات هر پروژه:

- GitHub repository binding;
- مقصد انتشار وضعیت: Branch اختصاصی پیش‌فرض مانند `aiwb-state`؛ گزینهٔ قابل‌تنظیم برای مخزن/Branch جدا یا مسیر دیگر، در صورت نیاز؛
- مسیر فایل‌های Status؛
- سیاست انتشار رویدادمحور و دوره‌ای؛
- فهرست بخش‌ها/فایل‌های مجاز برای انتشار؛
- سیاست نگهداری و Ignore؛
- وضعیت آخرین Snapshot و صف Publish.

**نکتهٔ سازگاری مدل:** بعضی چت‌ها/ابزارهای GitHub ممکن است فقط Branch پیش‌فرض را راحت بخوانند. هنگام راه‌اندازی باید قابلیت خواندن Branch وضعیت به‌صورت عملی بررسی شود. اگر مدل نتوانست آن را بخواند، گزینهٔ fallback یکی از این‌هاست: قرار دادن یک خلاصهٔ خواندنی و کم‌حجم در مسیر قابل‌دسترسی Branch پیش‌فرض، استفاده از مخزن وضعیت مستقل، یا قرار دادن خلاصهٔ لازم داخل پرامپت. در هیچ حالت فرض نکن همهٔ مدل‌ها به مخزن خصوصی/Branch خاص دسترسی دارند.

### ۱۲.۷. Event-driven + periodic fallback

حالت پیشنهادی Auto-Publish:

- **رویدادمحور:** پس از تغییر مهم، یک Snapshot برای انتشار علامت‌گذاری شود؛ مثلاً تأیید تصمیم، تغییر وضعیت Task، ثبت Evidence مهم یا پذیرش Handoff.
- **Debounce/Coalesce:** چند تغییر نزدیک به هم در یک Snapshot جمع شوند تا برای هر تغییر کوچک Commit جدا ساخته نشود.
- **دوره‌ای:** بازهٔ کاربر انتخاب کند، مثلاً 5/15/30/60 دقیقه، به‌عنوان بررسی پشتیبان. این Timer فقط وقتی Workbench در حال اجراست فعال است؛ اگر اجرای هنگام بسته‌بودن برنامه لازم شد، آن را به‌عنوان قابلیت جدا و با Windows Task Scheduler طراحی کن، نه اینکه وعدهٔ اجرای پس‌زمینهٔ ناموجود بدهی.
- **No-op:** اگر Hash محتوای Snapshot با آخرین Snapshot منتشرشده برابر است، Commit جدید ساخته نشود.
- **Queue:** در قطعی اینترنت/خطای موقت، آخرین Revision لازم در صف بماند.
- **Retry:** با Backoff افزایشی و احترام به Retry-After/rate limit. درخواست‌های نوشتن هم‌زمان و تکراری انجام نشوند.
- **Conflict:** پیش از نوشتن، آخرین SHA/نسخهٔ مقصد بررسی شود. در تعارض، Force Push ممنوع؛ Snapshot محلی حفظ و تصمیم/تطبیق لازم نمایش داده شود.
- **Idempotency:** هر Publish یک `publish_id` و `state_revision` دارد؛ تکرار عملیات نباید چند Snapshot یکسان تولید کند.

برای به‌روزرسانی چند فایل وضعیت، از یک Commit اتمیک/منطقی استفاده کن؛ از نوشتن جداگانهٔ هر فایل به روشی که نصف Snapshot جدید و نصف Snapshot قدیمی برای لحظه‌ای قابل‌مشاهده شود اجتناب کن. در صورت استفاده از Git Data API، Tree/Commit یا روش هم‌ارز باید کل تغییرات Snapshot را یکجا ثبت کند. اگر عملیات Git محلی استفاده می‌شود، Branch/Worktree ایزوله و اعتبارسنجی قبل از Push لازم است.

### ۱۲.۸. وضعیت کد و وضعیت پروژه دو جریان‌اند

دو تنظیم مستقل تعریف شود:

- `Project State Auto-Publish`: انتشار Manifest، خلاصه، تصمیم‌ها، Taskها و Evidenceهای مجاز.
- `Code Auto-Sync`: Commit/Push سورس واقعی.

در نسخهٔ اول Auto-Publish وضعیت می‌تواند خودکار باشد؛ Push کد نباید صرفاً به علت Timer وضعیت انجام شود. وضعیت پروژه می‌تواند به‌روز باشد در حالی که سورس هنوز تغییر محلی منتشرنشده دارد. Snapshot باید `source_commit_sha` و `local_changes_pending` را صریحاً نشان دهد.

### ۱۲.۹. حریم خصوصی و محتوای منتشرشده

به‌صورت پیش‌فرض به GitHub منتشر نشوند:

- API Token، رمز، کلید امضا، cookie یا هر Secret؛
- محتوای کامل پاسخ خام مدل یا همهٔ Promptها؛
- محتوای سورس یا فایل‌های خصوصی صرفاً به این دلیل که در زمینهٔ Prompt بوده‌اند؛
- مسیرهای مطلق محلی و اطلاعات شخصی غیرضروری؛
- Logهایی که ممکن است Secret یا دادهٔ حساس داشته باشند.

Project State باید خلاصه، ID، وضعیت، تصمیم‌های تأییدشده و ارجاع‌های کنترل‌شده باشد. اگر کاربر بخواهد گزارش خام یا Artifact مشخصی منتشر شود، باید تنظیم صریح داشته باشد و Preview انتشار را ببیند. Redaction به‌تنهایی تضمین حذف تمام اطلاعات حساس نیست.

### ۱۲.۱۰. شکست Publish

- GitHub قطع است: وضعیت محلی معتبر باقی بماند، صف و زمان آخرین تلاش نشان داده شود.
- Token نامعتبر/منقضی است: توقف و پیام روشن؛ retry تهاجمی انجام نشود.
- Rate limit: زمان مجاز retry رعایت شود؛ تا آن زمان عملیات نوشتن متوقف باشد.
- Branch جلوتر است: Fetch/مقایسه؛ نه Force Push.
- Snapshot قدیمی‌تر از وضعیت فعلی است: انتشار قدیمی لغو/جایگزین شود و آخرین Revision محلی بعداً منتشر شود.
- نوشتن برخی فایل‌ها موفق و بقیه ناموفق است: معماری انتشار باید کل Snapshot را اتمیک کند؛ اگر API/روش انتخابی این تضمین را نمی‌دهد، Publisher باید از روش Commit چندفایلی استفاده کند.
- Workbench بسته می‌شود: صف Publish و شناسهٔ Snapshot پایدار ذخیره شوند و در بازشدن بعدی بازیابی شوند.
- دو دستگاه Publish می‌کنند: نسخهٔ مبنای مقصد چک شود؛ تعارض به‌صورت امن حل یا به کاربر گزارش شود.

### ۱۲.۱۱. معیار پذیرش Project State

- Snapshot از داده‌های محلی معتبر و یک Revision سازگار تولید می‌شود.
- وضعیت Taskها از شمارش و سیاست مشخص محاسبه می‌شود، نه از متن مدل.
- Snapshot شامل Commit مبنا و وضعیت تغییرات محلی است.
- Publish مجدد بدون تغییر معنادار، Commit تکراری نمی‌سازد.
- قطع اینترنت به گم‌شدن وضعیت منجر نمی‌شود.
- تعارض با Remote به Force Push یا بازنویسی خام منجر نمی‌شود.
- مدل مدیر پروژه می‌تواند در حالت دسترسی GitHub از مسیر منتشرشده استفاده کند؛ اگر دسترسی ندارد، fallback پرامپت کار می‌کند.
- Auto-Publish وضعیت از Auto-Sync کد جداست.
- Prompt خام و Secretها به‌صورت پیش‌فرض منتشر نمی‌شوند.

## ۱۳. مدیر پروژه (Project Manager Agent)

### ۱۳.۱. مدیر پروژه یک نقش با Workflow مشخص است

کاربر می‌تواند از Template مدیر پروژه شروع کند و نقش را به مدل/چت انتخابی خود بسپارد. Workbench نام/برچسب مدل را صرفاً برای راهنمایی کاربر ثبت می‌کند؛ اتصال حساب یا ارسال خودکار انجام نمی‌شود.

وظایف مدیر پروژه:

- کمک به تعریف هدف، محدوده و معیار پذیرش پروژه؛
- پیشنهاد معماری و تقسیم کار؛
- پیشنهاد Taskها و وابستگی‌ها؛
- شناسایی ریسک‌ها و تصمیم‌های باز؛
- تحلیل گزارش پیشرفت مبتنی بر Snapshot/Evidence؛
- پیشنهاد بازبرنامه‌ریزی؛
- درخواست شواهد تکمیلی از Agentها؛
- ارائهٔ گزارش دوره‌ای و اقدام بعدی پیشنهادی.

مدیر پروژه نباید منبع قطعی وضعیت، اجراکنندهٔ فایل یا نویسندهٔ مستقیم Project State باشد.

### ۱۳.۲. New Project Planning

پرامپت آغازین مدیر پروژه شامل فرم هدف، مخاطب، محدودیت‌ها، محیط اجرا، قابلیت‌های موجود، معیارهای موفقیت و اطلاعات مرجع لازم باشد. نتیجهٔ مدیر پروژه باید به‌صورت **Plan Proposal** دریافت شود، نه بلافاصله Manifest نهایی.

Plan Proposal شامل:

- هدف و Non-goals؛
- معماری پیشنهادی؛
- فرض‌ها و سؤال‌های باز؛
- Agentهای موردنیاز؛
- Taskها، Scope، معیار پذیرش و وابستگی‌ها؛
- ریسک‌ها و روش Validation؛
- پیشنهاد Playbook یا سیاست هماهنگی.

Workbench ابتدا Schema و گراف را اعتبارسنجی کند و سپس طرح را در UI نشان دهد. کاربر بتواند هر Task، Agent، وابستگی و تصمیم را ویرایش کند. فقط پس از تأیید، داده‌ها به پروژهٔ واقعی اضافه شوند.

### ۱۳.۳. Manager Update Prompt

دکمهٔ `Prepare Manager Update` باید یک پرامپت دوره‌ای/درخواستی بسازد، اما مدل را اجرا نکند. پرامپت شامل:

- Revision و زمان Snapshot؛
- لینک/مسیر Repository و State Snapshot در صورت انتشار؛
- دستور مراجعه به وضعیت منتشرشده و درخواست اعلام صریح اگر دسترسی ندارد؛
- خلاصهٔ ضروری برای fallback؛
- رویدادهای مهم پس از گزارش قبلی؛
- وضعیت تسک‌های فعال/مسدود/منتظر بررسی؛
- Evidenceهای جدید و نتایج واقعی؛
- تصمیم‌های باز؛
- قالب پیشنهادهای جدید.

اگر پروژه State Snapshot جدیدی پس از آخرین گزارش مدیر دارد، آن را مشخص کن. اگر GitHub در دسترس نیست، دادهٔ محلی آخرین وضعیت را وارد پرامپت کن و صریحاً بگو که مدل نباید ادعا کند Snapshot آنلاین را خوانده است.

Auto-Publish به معنی ارسال خودکار گزارش به چت مدیر نیست. کاربر همچنان پرامپت را کپی می‌کند و پاسخ را برمی‌گرداند.

### ۱۳.۴. Manager Proposal Protocol

خروجی مدیر پروژه می‌تواند متن قابل‌خواندن به‌علاوهٔ یک بلوک ساختاریافته از پیشنهادها باشد. انواع Proposal حداقل:

- `create_task`;
- `update_task`;
- `add_dependency` / `remove_dependency`;
- `assign_agent`;
- `propose_decision`;
- `reorder_priority`;
- `split_task`;
- `close_or_cancel_task` به‌صورت پیشنهاد، نه اجرای مستقیم;
- `request_more_evidence`;
- `change_scope`;
- `report_risk`.

هر Proposal باید به `base_state_revision` و ترجیحاً Revisionهای Task مرتبط اشاره کند. Workbench هنگام Import بررسی کند که وضعیت فعلی با نسخهٔ مبنا فرق نکرده باشد. اگر فرق کرده، Proposal باید به‌عنوان `stale_proposal` بازبینی/تطبیق شود، نه اینکه خودکار اعمال شود.

Workbench `proposal_id` را خودش تولید کند؛ به ID پیشنهادی یا تکراری مدل اعتماد نکند. Proposalها ابتدا در Review نمایش داده شوند و بعد از تأیید به Task Graph/Decision Ledger تبدیل شوند.

### ۱۳.۵. مدیر پروژه نباید وضعیت را با لحن قطعی جعل کند

در دستورالعمل مدیر پروژه صریحاً تفکیک شود:

- اطلاعاتی که از Snapshot خوانده؛
- اطلاعاتی که از گزارش مدل دریافت کرده؛
- استنباط/پیشنهاد خودش؛
- اطلاعاتی که ندارد یا باید تأیید شوند.

اگر نتوانست GitHub را بخواند، باید بگوید. اگر Evidence برای تکمیل Task موجود نیست، نباید Task را `done` اعلام کند. Workbench در هر حال پاسخ مدیر را به‌عنوان Proposal/Analysis وارد می‌کند، نه به‌عنوان تغییر مستقیم وضعیت.

## ۱۴. Next Action: کاربر در هر لحظه بداند چه کند

داشبورد V2 باید به‌جای نمایش صرفاً یک جدول بزرگ، یک بخش `Next Action` داشته باشد که مهم‌ترین اقدام بعدی را با علت نشان دهد.

مثال‌ها:

- «پاسخ Agent برنامه‌نویس دریافت شده؛ آن را Import کن.»
- «چهار فایل از پنج فایل مورد انتظار شناسایی شد؛ فایل مفقود را درخواست کن یا تحویل ناقص را ثبت کن.»
- «Task به دلیل تغییر قرارداد نیازمند تصمیم است.»
- «فایل‌ها اعمال شده‌اند؛ تست لازم هنوز اجرا نشده است.»
- «Project State محلی از آخرین Snapshot منتشرشده جدیدتر است.»
- «مدیر پروژه برای بازبرنامه‌ریزی به گزارش جدید نیاز دارد.»
- «پیشنهاد مدیر پروژه با Revision فعلی Taskها همخوانی کامل ندارد.»

`next_action_service` باید از وضعیت داخلی و سیاست‌ها نتیجه بگیرد، نه صرفاً از جملهٔ پاسخ مدل. هر اقدام شامل نوع، علت، مراجع مرتبط، نیاز یا عدم نیاز به تأیید و پیش‌شرط‌ها باشد.

در صورت وجود چند اقدام، یک اقدام اصلی برجسته و بقیه در فهرست قرار گیرند. انتخاب اقدام نباید تسک‌های دیگر را مخفی کند.

## ۱۵. حلقهٔ بازبینی و اصلاح محدودشده

V2 باید بتواند پاسخ بازبین یا خطای تست را به Task اصلاحی مرتبط کند، اما نباید در حلقهٔ نامحدود اصلاح گیر کند.

- هر چرخهٔ اصلاح یک Attempt جدید باشد.
- یافتهٔ بازبین به فایل/معیار/شاهد مرتبط شود.
- اصلاحات فقط در Scope مجاز Task انجام شوند، مگر Scope جدید تأیید شود.
- تعداد چرخه‌های اصلاح خودکار/پیشنهادی قابل‌تنظیم باشد؛ بعد از مقدار پیش‌فرض محافظه‌کارانه (مثلاً 3 چرخهٔ ناموفق پیاپی) Task به `needs_decision` برود. مقدار نهایی به‌صورت تنظیم پروژه‌ای قابل‌تغییر باشد.
- خروجی مدل نباید به‌صورت بی‌نهایت یک Repair Prompt دیگر ایجاد کند.
- خلاصهٔ بازکاری شامل علت هر شکست و اینکه چه چیزی واقعاً تغییر کرده باشد.

چون مدل مستقیماً اجرا نمی‌شود، محدودیت چرخه‌ها در واقع تعداد Attemptهای پی‌درپی و درخواست‌های اصلاحی مدیریت‌شده توسط Workbench را کنترل می‌کند؛ نه اجرای خودمختار در پس‌زمینه.

## ۱۶. مدیریت هم‌زمانی، تعارض و خروجی‌های دیررس

### ۱۶.۱. چند Task در حال پیشرفت

Workbench اجازه می‌دهد چند Task هم‌زمان در حالت‌های متفاوت باشند، اما هر Attempt به نسخهٔ مبنا و Scope وصل باشد. اگر Taskها در فایل‌ها/قراردادها هم‌پوشانی داشته باشند، UI هشدار بدهد.

### ۱۶.۲. کار روی فایل‌های مشترک

در نسخهٔ اول، خروجی هر Agent به‌صورت Candidate/Change Set مستقل نگه داشته شود و تا زمان بازبینی روی فایل پروژه نوشته نشود. اگر دو Candidate یک فایل را تغییر دهند، ادغام خودکار انجام نشود. کاربر باید انتخاب، مقایسه یا بازبینی صریح انجام دهد.

### ۱۶.۳. پاسخ دیررس

اگر Attempt قدیمی پس از Attempt جدید پاسخ دریافت کند، آن را حفظ کن اما Active Attempt را خودکار عوض نکن. پاسخ دیررس می‌تواند برای مقایسه مفید باشد، ولی باید وضعیت `stale` داشته باشد.

### ۱۶.۴. Revision پروژه تغییر کرده است

قبل از Apply، بررسی کن که فایل‌ها/قراردادهای مرتبط از زمان ساخت Prompt تغییر نکرده باشند. اگر فقط بخش‌های نامرتبط تغییر کرده‌اند، امکان Reconcile دستی وجود داشته باشد؛ در غیر این صورت Apply متوقف و علت نشان داده شود.

### ۱۶.۵. دو دستگاه و دو Writer

در صورت وجود چند دستگاه، شناسهٔ دستگاه/Publisher و Revision پایهٔ State ثبت شود. تعارض وضعیت با مقایسه و تطبیق حل شود؛ Force Push یا last-write-wins خام مجاز نیست. در نسخهٔ اولیه می‌توان یک Publisher فعال برای هر پروژه را پیش‌فرض کرد و پشتیبانی چندنویسنده‌ای را بعداً توسعه داد.

## ۱۷. مسیر پیاده‌سازی فاز دوم به‌صورت برش‌های انتهابه‌انتها

ترتیب زیر داخل فاز دوم پیشنهاد می‌شود. این ترتیب از قراردادها شروع می‌کند، اما هر مرحله به‌سرعت به یک سناریوی قابل‌اجرا متصل می‌شود.

### برش 2A — مدل داده و Migration

کارها:

- تعریف Schema نسخه‌دار Agent، Task، Attempt، Handoff، Decision، Evidence، Snapshot و Proposal.
- طراحی شناسه‌های پایدار و Revisionها.
- migration داده‌های موجود؛ دادهٔ قدیمی حذف نشود.
- تعریف انتقال‌های مجاز وضعیت در سرویس مرکزی.
- تست بازیابی از دیتابیس قدیمی، دیتابیس ناقص و اجرای دوبارهٔ migration.

خروجی: مدل داده و تست‌ها؛ هنوز نیاز نیست UI بزرگ Agent ساخته شود.

معیار پذیرش:

- پروژه‌های قبلی باز می‌شوند و تاریخچهٔ آن‌ها سالم است.
- migration قابل‌تکرار یا دارای guard مناسب است.
- Attempt و Response قدیمی می‌توانند به Taskهای ایجادشده متصل شوند یا به‌صورت legacy باقی بمانند.
- هیچ دادهٔ تاریخی فقط به دلیل نبود فیلد جدید حذف نمی‌شود.

### برش 2B — Agent Registry و Task Graph

کارها:

- UI پایه برای ایجاد/ویرایش/کپی/غیرفعال‌کردن Agent Template.
- فرم ایجاد Task با Scope، معیار پذیرش، خروجی و وابستگی.
- نمایش گراف/فهرست وابستگی‌ها.
- اعتبارسنجی چرخه و وابستگی ناموجود.
- نشان‌دادن Taskهای آماده، مسدود و نیازمند تصمیم.
- پذیرش Plan Proposal مدیر پروژه فقط از مسیر Preview/Approve.

معیار پذیرش:

- یک پروژه بتواند چند Agent تعریف کند و Taskها را به آن‌ها تخصیص دهد.
- Agent قابل‌تعویض باشد بدون تغییر Task ID.
- گراف ناسالم پیش از ذخیره رد شود.
- تغییر معیار پذیرش Revision جدید بسازد.

### برش 2C — Handoff و اتصال به Response Inbox

کارها:

- ساخت Handoff از Task/Attempt و آخرین اطلاعات معتبر.
- ساخت Prompt برای Agent مقصد.
- کپی پرامپت، ثبت اینکه Export شده و انتظار پاسخ.
- Import پاسخ و اتصال آن به Attempt/Handoff.
- Parse/Reconcilation با Revision/ID.
- ثبت Artifactها، موارد ناقص و پیشنهاد قدم بعدی.

معیار پذیرش:

- GPT می‌تواند یک طرح/تحویل بسازد و Gemini می‌تواند بر اساس Handoff آن را ادامه دهد.
- پاسخ ناقص حفظ می‌شود.
- پاسخ قدیمی یا برای Task اشتباه، بی‌صدا به Task جاری وصل نمی‌شود.
- هیچ عملیات فایل به‌خاطر صرف Import/Parse اجرا نمی‌شود.

### برش 2D — Decision Ledger و Evidence

کارها:

- ثبت تصمیم پیشنهادی، تأییدشده، ردشده و جایگزین‌شده.
- ثبت Evidence واقعی از Apply/Validation/Git/Build و گزارش مدل به‌صورت نوع جدا.
- اتصال شواهد به Task/Attempt/Commit.
- محاسبهٔ وضعیت Task بر اساس Acceptance Policy.
- نمایش تفاوت Reported و Verified.

معیار پذیرش:

- ادعای مدل دربارهٔ تست به‌عنوان تست اجراشده ثبت نمی‌شود.
- تصمیم ردشده در تاریخچه می‌ماند.
- Task بدون شواهد الزامی Done نمی‌شود.
- شواهد قدیمی به Commit یا Revision جدید نسبت داده نمی‌شوند.

### برش 2E — Project State Snapshot و Auto-Publish

این بخش وابسته به زیرسیستم GitHub/Monorepo است که در حال پیاده‌سازی قرار دارد. سرویس اتصال GitHub، Credential، Repository Binding و عملیات Git موجود/در دست توسعه را از نو نساز؛ `github_state_publisher` باید از همان زیرسیستم استفاده کند.

کارها:

- تولید Snapshot محلی سازگار.
- Manifest JSON و گزارش Markdown خواندنی.
- انتشار به مقصد انتخابی و Branch وضعیت.
- صف Publish، retry، no-op و Conflict Handling.
- بازهٔ دوره‌ای قابل تنظیم و رویدادهای trigger.
- تشخیص Snapshot قدیمی و ارتباط به Commit سورس.
- UI نمایش آخرین Publish موفق و Pending.
- Preview و قواعد انتشار داده/حریم خصوصی.

معیار پذیرش:

- تغییر Task مهم، Snapshot محلی جدید می‌سازد.
- حالت رویدادمحور و دوره‌ای با هم کار می‌کنند و Commit تکراری نمی‌سازند.
- قطعی اینترنت موجب ازدست‌رفتن State نمی‌شود.
- Commit وضعیت با Commit سورس اشتباه گرفته نمی‌شود.
- Publisher به‌طور ناخواسته روی Branch کد Force Push نمی‌کند.
- اگر Branch وضعیت برای چت مدل قابل‌خواندن نیست، مسیر fallback تعریف‌شده قابل‌استفاده است.

### برش 2F — Manager Update و Proposal Review

کارها:

- Template مدیر پروژه با دستورالعمل واضح.
- دکمهٔ `Prepare Manager Update`.
- پرامپت شامل Snapshot/URL/Revision و fallback محلی.
- Import پاسخ مدیر به Response Inbox.
- استخراج پیشنهادهای Task/Decision/Dependency.
- نمایش Diff پیشنهادها نسبت به وضعیت فعلی.
- Accept/Reject انتخابی، جلوگیری از Proposal stale و اعتبارسنجی گراف بعد از اعمال.

معیار پذیرش:

- مدیر می‌تواند طرح/تغییر برنامه پیشنهاد دهد بدون اینکه وضعیت محلی مستقیماً با متن خام تغییر کند.
- پیشنهاد stale قبل از اعمال شناسایی می‌شود.
- کاربر می‌تواند بخشی از پیشنهادها را بپذیرد و بخشی را رد کند.
- پیشنهاد دارای چرخهٔ وابستگی یا ID ناسالم رد می‌شود.
- Workbench پس از پذیرش، State جدید را محاسبه و در صورت فعال‌بودن سیاست، Publish می‌کند.

### برش 2G — Next Action و سناریوی کامل V2

کارها:

- `next_action_service` از وضعیت معتبر نتیجهٔ اقدام بعدی را محاسبه کند.
- داشبورد خلاصهٔ Taskها و موارد منتظر اقدام را نشان دهد.
- اجرای سناریوی انتهابه‌انتها با حداقل دو مدل/چت دستی متفاوت.
- تست همهٔ حالات خطا و recovery.
- مستندات کاربر و برنامه‌نویس.

معیار پذیرش:

یک سناریوی واقعی باید بدون دست‌کاری مستقیم DB یا فایل‌های داخلی از تعریف پروژه تا گزارش مدیر و پذیرش پیشنهاد بعدی اجرا شود. در هر لحظه UI باید نشان دهد چه چیزی در انتظار کاربر است و چرا.

## ۱۸. سناریوی مرجع انتهابه‌انتها برای تأیید V2

این سناریو باید به Test Plan ثابت پروژه تبدیل شود.

1. کاربر پروژه‌ای جدید ایجاد می‌کند و هدف/محدودیت‌ها را وارد می‌کند.
2. Workbench پرامپت مدیر پروژه را تولید می‌کند.
3. کاربر آن را به چت معمولی GPT می‌برد و پاسخ را Paste می‌کند.
4. Workbench Plan Proposal را Parse می‌کند، Taskها و وابستگی‌ها را اعتبارسنجی می‌کند و به کاربر نمایش می‌دهد.
5. کاربر طرح را تأیید می‌کند؛ Taskها و Agentها Revision/ID پایدار می‌گیرند.
6. Workbench برای Agent معمار پرامپت می‌سازد؛ کاربر خروجی را از چت Gemini برمی‌گرداند.
7. پاسخ به Handoff صحیح متصل، Parse و Review می‌شود؛ تصمیم معماری پس از تأیید ثبت می‌شود.
8. Workbench دو Task مستقل پیشنهاد می‌کند؛ کاربر Scope/وابستگی را تأیید می‌کند.
9. یک Task به Agent برنامه‌نویس GPT و Task دیگر به Agent موبایل Gemini تخصیص می‌یابد. پرامپت‌ها به‌صورت دستی ارسال و پاسخ‌ها جداگانه وارد می‌شوند.
10. یکی از پاسخ‌ها ناقص است. Workbench چهار Artifact از پنج Artifact موردانتظار را حفظ می‌کند و Repair Prompt مختص فایل مفقود می‌سازد.
11. خروجی‌ها به Candidate/Change Set تبدیل و بازبینی می‌شوند؛ Apply فقط با تأیید کاربر انجام می‌شود.
12. Validation اجرا می‌شود؛ یک Task شواهد موفق و دیگری `Not Verified` می‌گیرد.
13. State Snapshot شامل Commit مبنا، وضعیت تسک‌ها، Evidenceها و مانع ایجاد می‌شود و به GitHub منتشر می‌شود.
14. کاربر Manager Update را تولید و به چت مدیر پروژه ارسال می‌کند. مدیر پیشنهاد می‌دهد تسک دوم تا تکمیل تست مسدود بماند و یک تست تکمیلی اضافه شود.
15. پاسخ مدیر وارد Workbench می‌شود؛ پیشنهادها ساختاریافته و در UI بازبینی می‌شوند. Workbench گراف را اعتبارسنجی می‌کند؛ کاربر تغییرات موردنیاز را می‌پذیرد.
16. Snapshot بعدی منتشر می‌شود؛ گزارش نشان می‌دهد کدام اطلاعات تغییر کرده‌اند و مدیر پروژه از کدام Revision باید در تعامل بعدی استفاده کند.

سناریو باید همین‌طور در شرایط شکست آزمایش شود: قطع اینترنت، Token نامعتبر، پاسخ دیررس، Revision قدیمی، دو تغییر هم‌زمان، فایل مفقود، شکست Validation و رد بخشی از Proposal.

# فاز سوم — رابط کاربری ساده و پیشرفته

## ۱۹. اصول فاز سوم

طراحی بصری نباید به دو سیستم داده یا دو منطق عملیاتی منجر شود. حالت ساده و پیشرفته تنها دو نمای متفاوت روی همان Task/Agent/Handoff/State هستند.

### حالت ساده

مناسب کاربری که می‌خواهد سریع کار را پیش ببرد:

- هدف فعلی پروژه؛
- اقدام بعدی؛
- دکمهٔ تولید پرامپت؛
- دکمهٔ Copy؛
- بخش Paste/Import پاسخ؛
- توضیح نتیجه و خطای قابل‌فهم؛
- وضعیت سادهٔ Task؛
- هشدارهای ضروری و تصمیم‌های موردنیاز.

در این حالت کاربر نباید مجبور شود مفهوم Attempt، Schema، Evidence Ledger یا Revision را یاد بگیرد؛ اما این مفاهیم همچنان در دادهٔ داخلی ثبت می‌شوند.

### حالت پیشرفته

برای کاربر حرفه‌ای:

- Agent Registry و ویرایش نقش‌ها؛
- گراف وابستگی Task؛
- Task Revision و Attempt History؛
- Handoff Viewer؛
- Decision Ledger و Evidence Ledger؛
- Context و فایل‌های ورودی هر Prompt؛
- State Revision، Source Commit و GitHub Publish History؛
- صف Proposalهای مدیر پروژه؛
- سیاست‌های Validation و Publish؛
- جزئیات Parse/Diagnostics.

### ۱۹.۱. Next Action در هر دو حالت ثابت باشد

بخش اقدام بعدی در Simple و Advanced یک معنای واحد داشته باشد. در Advanced می‌توان علت، وابستگی‌ها و شواهد را باز کرد؛ در Simple فقط خلاصه و عملیات اصلی نمایش داده شوند.

### ۱۹.۲. خطاها واضح و اولویت‌دار باشند

از Dialogهای متعدد و نامفهوم اجتناب شود. خطاهای قابل‌بازیابی به‌شکل توضیح و اقدام بعدی نمایش داده شوند؛ خطاهای مخرب/تعارضی نیازمند توقف واضح باشند. دکمهٔ پیش‌فرض نباید ناخواسته عملیات حساس را تأیید کند.

### ۱۹.۳. وضعیت‌ها رنگ تنها نداشته باشند

هر وضعیت همراه متن و در صورت نیاز Icon نمایش داده شود تا رنگ به‌تنهایی حامل معنا نباشد. `Done`, `Reported`, `Verified`, `Blocked` و `Not Run` بصری و معنایی از هم قابل‌تشخیص باشند.

### ۱۹.۴. ترجمه و واژگان یکپارچه

واژگان فارسی و انگلیسی باید در یک فرهنگ اصطلاحات تعریف شوند. از چند ترجمه برای یک وضعیت یا مفهوم اجتناب شود. متن خطاها در فایل‌های localization نگه‌داری شوند؛ در منطق برنامه به رشته‌های فارسی شرط ننویس.

### ۱۹.۵. معیار پذیرش فاز سوم

- کاربر ساده می‌تواند چرخهٔ Prompt → Copy → Paste → Review را بدون دیدن مفاهیم داخلی کامل کند.
- کاربر پیشرفته تمام اطلاعات مربوط به Task/Attempt/Handoff/State را دارد.
- تغییر حالت UI هیچ داده‌ای را تغییر نمی‌دهد.
- تمام عملیات در هر دو حالت از سرویس‌های مشترک استفاده می‌کنند.
- تست GUI برای هر دو حالت وجود دارد.

# تست‌های سراسری و سناریوهای شکست

## ۲۰. Failure Register الزامی

این جدول باید به تست‌ها و در صورت نیاز شناسهٔ Issue تبدیل شود. رفتار نهایی هر مورد باید مشخص و تکرارپذیر باشد.

| سناریو | رفتار لازم |
|---|---|
| پاسخ مدل فرمت ناشناخته دارد | Raw Response حفظ شود؛ Import دستی/Parser انتخابی نمایش داده شود |
| JSON ناقص است | محل خطا و Raw Response حفظ شود؛ امکان اصلاح یا درخواست مجدد فقط بخش لازم وجود داشته باشد |
| بخشی از فایل‌ها مفقود است | Artifactهای معتبر حفظ؛ خروجی ناقص ثبت؛ Repair Prompt تولید شود |
| پاسخ دیررس از Attempt قدیمی است | ذخیره شود ولی Active Attempt/Task را بازنویسی نکند |
| Handoff از Revision قدیمی آمده | Stale/Reconciliation؛ Apply تا بررسی متوقف شود |
| دو Task یک فایل را تغییر می‌دهند | Candidateها جدا؛ ادغام خودکار ممنوع؛ تعارض واضح نمایش داده شود |
| مدیر پروژه Task را Done اعلام می‌کند | صرف ادعا کافی نیست؛ معیار پذیرش/Evidence بررسی شود |
| مدیر پروژه Proposal ناسالم می‌دهد | Schema و گراف اعتبارسنجی؛ Proposal رد یا به اصلاح برگردد |
| Proposal بر اساس Snapshot قدیمی است | حالت stale و Preview اختلافات؛ اعمال خام ممنوع |
| GitHub قطع می‌شود | کار محلی ادامه؛ Publish در صف با خطای واضح |
| GitHub rate limit می‌دهد | Backoff/Retry-After؛ تلاش‌های موازی نوشتن متوقف شوند |
| Branch وضعیت از راه دور جلوتر است | Fetch/Compare؛ تعارض بدون Force Push |
| Publish تکراری انجام می‌شود | idempotent/no-op؛ Commit تکراری ساخته نشود |
| برنامه وسط Publish بسته می‌شود | Publish ID و Queue پایدار؛ در اجرای بعد وضعیت بررسی شود |
| State جدیدتر از Source Commit است | `local_changes_pending` یا اطلاعات Commit mismatch نشان داده شود |
| Token در لاگ/پرامپت ظاهر می‌شود | تست امنیتی باید شکست بخورد؛ Credential از UI/log/prompt redacted بماند |
| دادهٔ خام حاوی Secret است | به‌طور پیش‌فرض به GitHub Publish نشود؛ Preview/Policy لازم باشد |
| چند دستگاه State را منتشر می‌کنند | Revision/Head conflict؛ بدون overwrite کور |
| Timer وقتی اپ بسته است اجرا نمی‌شود | UI روشن کند زمان‌بندی فقط هنگام اجرای Workbench فعال است، مگر OS scheduler جداگانه نصب شده باشد |
| Migration میان نسخه‌ها شکست می‌خورد | Backup/Recovery و گزارش خطا؛ دادهٔ قدیمی پاک نشود |
| فایل دیتابیس/Manifest ناقص است | آخرین Snapshot سازگار حفظ شود؛ وضعیت ناقص به‌عنوان معتبر Publish نشود |
| آزمون اجرا نشده | `Not Run`؛ هرگز `Passed` نشان داده نشود |
| Agent اصلاح‌های بی‌پایان پیشنهاد می‌دهد | محدودیت Attempt/Review؛ سپس `needs_decision` |

## ۲۱. تست‌های واحد و یکپارچهٔ قراردادها

برای هر Schema مجموعهٔ Fixtureهای مثبت و منفی داشته باش:

- Agent معتبر و Agent فاقد فیلد لازم؛
- Task بدون وابستگی، Task با dependency ناموجود و گراف چرخه‌ای؛
- Task Revision قدیمی و جدید؛
- Handoff کامل، ناقص و دارای Artifact تکراری؛
- Proposal با Revision جاری و Proposal stale؛
- Evidence مدل در برابر Evidence اجرای واقعی؛
- Snapshot با Source Commit معتبر و Snapshot دارای local changes؛
- State Publish بدون تغییر و با تغییر؛
- پاسخ قدیمی که بعد از Attempt جدید دریافت شده است.

تست Schema نباید تنها بررسی کند که JSON parse می‌شود. باید قواعد معنایی، پیوند IDها، وضعیت مجاز و سازگاری Revisionها را بررسی کند.

## ۲۲. تست‌های یکپارچگی GUI

جریان‌های ضروری:

1. ایجاد پروژه و Agent؛
2. تولید Prompt و Copy؛
3. Import پاسخ معتبر؛
4. Import پاسخ ناقص و Repair؛
5. ساخت و تأیید Plan Proposal؛
6. Handoff بین دو Agent؛
7. رد Proposal ناسالم؛
8. تغییر حالت Simple/Advanced بدون تغییر داده؛
9. Publish وضعیت و شکست شبکه؛
10. بازشدن دوبارهٔ برنامه و بازیابی صف؛
11. نمایش Last Published در برابر Local Revision؛
12. ایجاد و بازبینی Task مسدود/نیازمند تصمیم.

## ۲۳. تست‌های GitHub State Publisher

- Repository و Branch مقصد درست انتخاب می‌شوند.
- Publisher هیچ‌گاه به‌خاطر State Auto-Publish به Branch کد Force Push نمی‌کند.
- Snapshot چندفایلی اتمیک/منسجم منتشر می‌شود.
- دو Publish هم‌زمان با Revision متفاوت به تعارض امن می‌رسند.
- No-op هیچ Commit جدید نمی‌سازد.
- Retry پس از شبکه/Rate limit مطابق سیاست انجام می‌شود.
- یک Snapshot قدیمی بعد از Snapshot جدیدتر منتشر نمی‌شود.
- Publish result به State Revision و Commit مقصد قابل‌ردیابی است.
- در مخزن/Branch خصوصی یا غیرقابل‌خواندن، fallback Prompt Pack جواب می‌دهد.
- Workflow Build با تغییرات صرفاً وضعیت بی‌جهت اجرا نمی‌شود و Required Checks در حالت Pending گیر نمی‌کنند.

## ۲۴. امنیت و ایمنی گردش‌کار

این برنامه متن و فایل تولیدشده توسط مدل را غیرقابل‌اعتماد فرض می‌کند. الزام‌ها:

- مدل نمی‌تواند از طریق پاسخ، Agent/Task مجوز اجرایی بیشتری به دست آورد.
- مدل نمی‌تواند Token یا Secret را از تنظیمات Workbench بخواند.
- محتوای پرامپت تولیدشده شامل Credential نباشد.
- Publish Status و Code Push دو عملیات مستقل باشند.
- Force Push برای Auto-Publish ممنوع باشد.
- GitHub Workflowها با حداقل permission لازم اجرا شوند و تغییر Workflow توسط خروجی مدل نیازمند Review باشد.
- واردکردن پاسخ، Parse یا Preview کد/فرمان را اجرا نکند.
- عملیات فایل از سرویس امن Apply عبور کند.
- Snapshot و Diagnostic پیش از انتشار از سیاست‌های Secret/Ignore بگذرند.

# Definition of Done و Release Gates

## ۲۵. Definition of Done برای هر قابلیت

هر قابلیت فقط زمانی Done است که:

1. Schema/قرارداد آن تعریف و نسخه‌گذاری شده باشد.
2. منطق کسب‌وکار از UI جدا باشد.
3. مسیر موفق، مسیر لغو و شکست‌های مهم تعریف شده باشند.
4. دادهٔ خام/قدیمی در صورت خطا حفظ شود.
5. Migration برای دادهٔ موجود داشته باشد، در صورت نیاز.
6. تست واحد و رگرسیون نوشته شده باشد.
7. جریان GUI مربوطه آزمایش شده باشد.
8. شواهد واقعی از عملیات ثبت شوند و ادعای مدل به‌جای آن‌ها ننشینند.
9. مستندات معماری و رفتار کاربر به‌روز شوند.
10. در CHANGELOG تغییر و ناسازگاری‌های احتمالی نوشته شوند.
11. اجرای واقعی روی محیط هدف، و نه صرفاً Mock/تست ایستا، برای موارد حیاتی ثبت شود.
12. کاربر بداند پس از شکست چه چیزی حفظ شده و قدم بعدی چیست.

## ۲۶. Release Gate فاز اول

فاز اول قابل انتشار است وقتی:

- هیچ پاسخ خام با شکست Parser از دست نمی‌رود؛
- خطاهای Import مهم کد تشخیصی و مسیر بازیابی دارند؛
- پاسخ ناقص را می‌توان نجات داد؛
- Attempt و Response IDها به شکل پایدار ثبت می‌شوند؛
- تست‌های Regression مربوط به Import در محیط واقعی اجرا می‌شوند.

## ۲۷. Release Gate فاز دوم — مهم‌ترین دروازهٔ پروژه

V2 تا زمان برآورده‌شدن همهٔ موارد زیر کامل اعلام نشود:

- سه قرارداد Agent/Task، Handoff و Project State/Evidence مستند و تست شده‌اند.
- Task Graph از نظر وابستگی/چرخه اعتبارسنجی می‌شود.
- حداقل دو Agent با نقش متفاوت و دو چت/مدل متفاوت در یک پروژهٔ واقعی کار کرده‌اند.
- انتقال کار بدون نیاز به دسترسی به تاریخچهٔ چت قبلی امکان‌پذیر است.
- پاسخ قدیمی، ناقص یا متعلق به Task دیگر درست مدیریت می‌شود.
- مدیر پروژه می‌تواند State Snapshot را تحلیل و Proposal تولید کند.
- Proposal پیش از اعمال Review می‌شود و نسخهٔ stale تشخیص داده می‌شود.
- Evidence واقعی از گزارش مدل جداست.
- Auto-Publish وضعیت GitHub صف، no-op، Retry، conflict و Snapshot/Commit reference دارد.
- اگر مدل GitHub را نتواند بخواند، مسیر fallback داخل Prompt کار می‌کند.
- هیچ Task فقط به‌دلیل ادعای مدل Done نمی‌شود.
- سناریوی انتهابه‌انتها در بخش ۱۸ بدون دست‌کاری دستی DB یا فایل داخلی با موفقیت اجرا می‌شود.

## ۲۸. Release Gate فاز سوم

- حالت Simple و Advanced هر دو روی یک منطق و داده کار می‌کنند.
- کاربر تازه‌کار می‌تواند قدم بعدی را بدون شناخت مدل داخلی Agent/Task انجام دهد.
- کاربر پیشرفته تمام اطلاعات لازم برای ردیابی و عیب‌یابی را می‌بیند.
- GUI هیچ رفتار جدیدی ایجاد نمی‌کند که در سرویس مرکزی تعریف نشده باشد.
- آزمون‌های GUI در هر دو حالت موفق باشند.

# ترتیب کار پیشنهادی

این بخش ترتیب توسعه است، نه زمان‌بندی تقویمی. در هر برش فقط زمانی ادامه بده که معیارهای پذیرش آن برآورده شده باشند.

1. **بازبینی نسخهٔ 1.14 و تغییرات جاری GitHub/Monorepo:** قابلیت موجود را دوباره نساز؛ نقطهٔ اتصال سرویس‌ها را مشخص کن.
2. **فاز اول، Response Inbox و بازیابی خطا:** Raw Response، Pipeline، خطاهای قابل‌فهم، Attempt ID و Repair Prompt.
3. **قراردادهای داده و migration:** Agent/Task، Handoff، Project State/Evidence و وضعیت‌های مجاز.
4. **Agent Registry + Task Graph:** تعریف نقش‌ها و Taskها، وابستگی‌ها و Plan Proposal.
5. **Handoff واقعی بین دو مدل:** یک Task از مدل اول به مدل دوم منتقل شود و خروجی به همان Task وصل بماند.
6. **Evidence/Decision Ledger:** وضعیت واقعی و تصمیم‌ها مستقل از پاسخ مدل ثبت شوند.
7. **Project State Snapshot + GitHub Auto-Publish:** Event + Timer، صف پایدار، Revision/Commit mapping و conflict safety.
8. **Project Manager Workflow:** ساخت Plan، Manager Update، Proposal Review و بازبرنامه‌ریزی.
9. **Next Action و سناریوی انتهابه‌انتها:** کاربر از داشبورد تا تکمیل و گزارش مدیر را با دو مدل واقعی انجام دهد.
10. **فاز سوم UI:** Simple/Advanced Mode و پالایش بصری پس از تثبیت رفتارهای V2.

ترتیب فوق باید به شکل تدریجی اجرا شود. اگر پیاده‌سازی یک زیرمرحله نشان داد قرارداد نیازمند تغییر است، Schema را با migration و تست نسخه‌گذاری‌شده اصلاح کن؛ از اصلاح خام و شکستن داده‌های موجود خودداری کن.

## تصمیم نهایی

**فاز دوم هدف اصلی AI Workbench است؛ فاز اول باید داده و تجربهٔ قابل‌اعتماد آن را فراهم کند و فاز سوم باید همان قدرت را ساده و قابل‌فهم نمایش دهد.**

سه قرارداد مرکزی که نباید از طراحی حذف شوند:

1. **Agent/Task Contract:** نقش‌ها، Taskها، Revisionها، وابستگی‌ها و معیارهای پذیرش.
2. **Handoff Contract:** بستهٔ استاندارد برای انتقال مأموریت، زمینه، خروجی و موارد حل‌نشده میان چت‌ها/مدل‌های مستقل.
3. **Project State/Evidence Contract:** وضعیت محلی معتبر، تصمیم‌های تاریخچه‌دار، شواهد واقعی، Snapshot نسخه‌گذاری‌شده و انتشار کنترل‌شده در GitHub.

GitHub در این معماری حافظهٔ خواندنی و مشترک پروژه برای مدل‌هاست، اما مرجع نهایی وضعیت محلی نیست. مدیر پروژه می‌تواند از آن بخواند و برنامه‌ریزی کند؛ پیشنهادهای او باید وارد Workbench، اعتبارسنجی و تأیید شوند. مدل‌ها با چت عادی و روش دستی پرامپت/پاسخ استفاده می‌شوند؛ Workbench کار هماهنگی، ردیابی، بررسی و بازیابی را انجام می‌دهد.

مهم‌ترین معیار تصمیم‌گیری در تمام توسعه این است: آیا این قابلیت کمک می‌کند چند مدل مستقل با زمینهٔ کمترِ تکراری، خطای کمتر و وضعیت قابل‌اعتمادتر روی یک پروژه همکاری کنند؟ اگر نه، در اولویت فاز دوم نیست.

# ضمیمه B — حداقل ساختار فایل‌های منتشرشده در GitHub

ساختار نهایی باید configurable باشد، اما قرارداد پیش‌فرض می‌تواند این شکل را داشته باشد:

- `.aiwb/project-state.json`: Manifest ماشینی آخرین Snapshot؛
- `.aiwb/PROJECT_STATUS.md`: خلاصهٔ خواندنی برای انسان و مدل؛
- `.aiwb/decisions/DEC-xxxx.json`: تصمیم‌های تأییدشده و ارجاع به تاریخچه؛
- `.aiwb/tasks/TASK-xxxx.json`: فقط اطلاعات ضروری Taskهای فعال/منتخب برای مصرف بیرونی؛
- `.aiwb/evidence/index.json`: فهرست/ارجاع شواهد منتشرشدنی، نه الزاماً خود Logهای خام؛
- `.aiwb/schemas/`: نسخه‌های Schemaای که برای خوانندهٔ خارجی لازم‌اند.

در نسخهٔ اول لازم نیست برای هر Task یک فایل مجزا منتشر شود؛ اگر Manifest و گزارش Markdown برای نیاز واقعی کافی‌اند، همان را نگه‌دار. هدف ساخت انبوه فایل نیست، هدف این است که مدیر پروژه بتواند وضعیت قابل‌اعتماد و تازه را پیدا کند.

## B.1. محتوای PROJECT_STATUS.md

این فایل را از Manifest و داده‌های محلی بساز؛ نویسندهٔ آن مدل نیست. حداقل شامل:

- هدف و محدودهٔ پروژه؛
- آخرین State Revision و زمان UTC؛
- Branch و Commit سورس مرتبط؛
- اینکه تغییرات محلی منتشرنشده وجود دارد یا نه؛
- خلاصهٔ Taskهای فعال، مسدود، نیازمند تصمیم و تکمیل‌شده با شواهد؛
- تصمیم‌های باز؛
- موانع و خطاهای مهم؛
- آخرین Validationها و Commit/Build مربوط؛
- اقدام بعدی پیشنهادی Workbench و علت آن؛
- هشدار که گزارش فقط تا Revision و Commit ذکرشده معتبر است.

## B.2. Compatibility Probe برای خواندن توسط مدل

هنگام راه‌اندازی مدیر پروژه، یک تست دستی کوتاه طراحی کن: Workbench لینک دقیق Repository/Branch/فایل وضعیت را آماده کند و پرامپتی بسازد که از مدل بخواهد فقط یک مقدار مشخص از Snapshot (مثلاً `state_revision`) را گزارش دهد و مشخص کند واقعاً به فایل دسترسی پیدا کرده یا خیر. کاربر جواب را برمی‌گرداند و نتیجه را ثبت می‌کند.

این تست نباید برای احراز هویت مدل یا اتصال حساب استفاده شود؛ فقط قابلیت دسترسی از همان چت معمولی‌ای را که کاربر انتخاب کرده بررسی می‌کند. اگر دسترسی شکست خورد، حالت `GitHub-first with fallback` باید خلاصهٔ لازم را در پرامپت قرار دهد. مدل نباید بتواند به‌طور صوری ادعا کند Snapshot را خوانده؛ پاسخ تست باید با محتوای واقعی موردانتظار مقایسه شود.
