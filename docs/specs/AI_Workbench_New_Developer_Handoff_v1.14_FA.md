## ۰. دستورالعمل مهم برای مطالعه و کار با این سند

این سند زمینهٔ محصول، مسائل تجربهٔ کاربری، اصول معماری و هدف نهایی پروژه را یکجا توضیح می‌دهد. این سند به‌تنهایی جایگزین سورس، تست‌ها، مستندات فنی موجود یا بازبینی رفتار واقعی نسخهٔ فعلی نیست.

پیش از تغییر کد:

1. سورس واقعی نسخهٔ v1.14 که مالک پروژه ارائه می‌کند، بررسی شود. سورس v1.11.0 که در گذشته برای بررسی در اختیار بوده، مرجع قابل‌اعتماد برای تشخیص وضعیت فعلی v1.14 نیست.
2. `README.md`، `README_FA.md`، `ARCHITECTURE.md`، `CHANGELOG.md`، تست‌ها و migrationهای واقعی نسخهٔ جاری بررسی شوند.
3. مشخص شود کدام قابلیت‌های این سند از قبل پیاده‌سازی شده‌اند، کدام ناقص‌اند و کدام صرفاً ایده یا طراحی آینده‌اند.
4. قابلیت موجود دوباره از صفر ساخته نشود. ابتدا کد، تست و رفتار جاری بررسی و سپس کوچک‌ترین تغییر لازم طراحی شود.
5. سند یکپارچه‌سازی GitHub/Monorepo و نقشه‌راه قبلی نیز به‌عنوان ورودی‌های طراحی مطالعه شوند؛ اما هر اختلاف میان سند و سورس باید ثبت و تصمیم‌گیری شود.
6. هیچ بخش از این سند به معنی مجوز بازنویسی کامل برنامه یا کنارگذاشتن جریان کاری فعلی نیست.

### اصل غیرقابل‌مذاکرهٔ محصول

**AI Workbench برای مدیریت کار با چت معمولی مدل‌های هوش مصنوعی طراحی شده است.** جریان هدف چنین است:

1. کاربر در Workbench پروژه/تسک را تعریف می‌کند.
2. Workbench پرامپت مناسب، همراه زمینه و دستورالعمل‌های لازم را می‌سازد.
3. کاربر پرامپت را کپی می‌کند و خودش آن را در چت عادی GPT، Gemini یا مدل دیگر قرار می‌دهد.
4. کاربر پاسخ متن/فایل مدل را دستی به Workbench برمی‌گرداند.
5. Workbench پاسخ را حفظ، تحلیل، اعتبارسنجی و به کاربر نشان می‌دهد.
6. Workbench اقدام بعدی یا پرامپت اصلاح/ادامه را آماده می‌کند.
7. کاربر دوباره آن را به چت مدل می‌دهد. چرخه تکرار می‌شود.

برای این جریان به API مدل، API Key مدل، ورود به حساب ChatGPT/Gemini یا دسترسی مستقیم Workbench به تاریخچهٔ چت مدل نیاز نیست و چنین چیزی هدف محصول نیست. نباید معماری را به سمتی برد که استفاده از اشتراک رایگان/پولی معمولی مدل‌ها را کنار بگذارد.

این اصل به معنای ممنوع‌بودن API گیت‌هاب نیست. اتصال به GitHub یک زیرسیستم مستقل برای مخزن، Commit/Push و انتشار وضعیت پروژه است؛ هیچ مجوزی برای اتصال به حساب‌های مدل یا ارسال خودکار پرامپت به چت ایجاد نمی‌کند.

## ۱. AI Workbench چیست؟

AI Workbench یک محیط ویندوزی برای سازمان‌دهی تعامل با مدل‌های زبانی در توسعهٔ پروژه‌هاست. ارزش آن فقط ساخت پرامپت یا ذخیرهٔ پاسخ نیست؛ باید فاصلهٔ بین تعریف هدف، گرفتن خروجی از مدل، واردکردن آن، اعمال تغییرات معتبر، بررسی نتیجه و تصمیم‌گیری دربارهٔ قدم بعدی را مدیریت کند.

در چشم‌انداز نهایی، کاربر می‌تواند یک پروژه را با چند نقش Agent پیش ببرد. هر Agent از طریق پرامپت و پاسخ دستی در یک چت معمولی اجرا می‌شود. یکی می‌تواند مدیر پروژه باشد، دیگری معمار، برنامه‌نویس یا بازبین. حتی می‌توان نقش‌ها را میان GPT، Gemini و مدل‌های دیگر تقسیم کرد. Workbench هدف، تسک‌ها، قراردادها، تصمیم‌ها، تحویل‌ها، شواهد و وضعیت پروژه را نگه می‌دارد تا مدل بعدی بتواند از کار قبلی ادامه دهد.

**AI Workbench خود مدل نیست و هدف آن ساخت یک عامل خودمختار متصل به API نیست؛ AI Workbench هماهنگ‌کنندهٔ گردش‌کار انسانی بین مدل‌هاست.**

### ۱.۱. کاربر هدفمند کیست؟

دو گروه اصلی باید پشتیبانی شوند:

- **کاربر عادی/مبتدی:** هدف کلی خود را توضیح می‌دهد؛ انتظار دارد برنامه سؤال‌های ضروری را بپرسد، پرامپت آماده کند، خروجی را بررسی کند و مشخص کند قدم بعدی چیست. او نباید مجبور باشد مفهوم Handoff، Revision، Evidence یا Task Graph را از ابتدا بفهمد.
- **کاربر حرفه‌ای:** می‌خواهد Agentها، قراردادها، گراف وابستگی، Scope، Revisionها، شواهد، تنظیمات GitHub، وضعیت انتشار و تصمیم‌های پروژه را با جزئیات کنترل کند.

هر دو حالت باید از یک مدل داده و منطق اصلی استفاده کنند. نباید حالت ساده و پیشرفته به دو پیاده‌سازی جدا و ناسازگار تبدیل شوند.

### ۱.۲. تعریف موفقیت محصول

محصول موفق است اگر:

- کاربر پس از دریافت پاسخ مدل نداند کمتر که «حالا باید چه‌کار کنم؟» و برنامه قدم بعدی روشنی پیشنهاد دهد.
- خطای Import باعث از دست‌رفتن پاسخ یا شروع دوباره از ابتدا نشود.
- پاسخ همیشه به Task و تلاش (Attempt) درست متصل شود یا اتصال مشکوک پیش از ادامه هشدار داده شود.
- کاربر بتواند پروژه را گسترش دهد، بدون اینکه Task تکمیل‌شده را بی‌دلیل باز نگه دارد یا تسک جدیدی را به جای اصلاح همان تسک بسازد.
- چت جدید یا تغییر مدل باعث از دست‌رفتن زمینهٔ پروژه نشود.
- مدل بتواند از خروجی مدل دیگری ادامه دهد، چون Handoff دادهٔ کافی و استاندارد ارائه می‌کند.
- مدیر پروژه وضعیت را بر اساس Snapshot و شواهد بررسی کند، نه صرفاً از حافظه یا ادعای چت.
- اطلاعات واقعی Workbench از گزارش/ادعای مدل جدا باشد.
- کاربر همیشه بفهمد چه چیزی رخ داده، چه چیزی هنوز نامعلوم است و قدم بعدی چیست.
- استفاده از GitHub روند اشتراک وضعیت و ساخت نرم‌افزار را ساده کند، نه اینکه با آن وضعیت‌های جدید و مبهم ایجاد کند.

## ۲. وضعیت شناخته‌شدهٔ پروژه و حدود اطمینان

مالک پروژه اعلام کرده که نسخهٔ جاری برنامه v1.14 است. قبلاً سورس نسخهٔ 1.11.0 برای بررسی در دسترس بوده و در ادامه اسناد طراحی بر اساس آن سورس/مستندات و بحث‌های بعدی تهیه شده‌اند. بنابراین:

- هر قابلیتی که در اسناد قبلی «موجود» توصیف شده باید با سورس v1.14 دوباره تأیید شود.
- هر قابلیت پیشنهادی در اسناد قبلی ممکن است در v1.12، v1.13 یا v1.14 از قبل پیاده شده باشد.
- قبل از توسعه، برنامه‌نویس باید یک **Capability Audit** تهیه کند: موجود و کامل / موجود اما ناقص / موجود اما نیازمند تست / غایب / منسوخ یا تکراری.
- سند GitHub/Monorepo قبلی بر مبنای v1.13 عنوان‌گذاری شده؛ مالک گفته نسخهٔ محصول بعداً به v1.14 رسیده است. هیچ‌یک از این اسناد جای بررسی واقعی کد جاری را نمی‌گیرد.
- در گذشته گزارش شده بود که تست‌های نسخهٔ قدیمی در Linux/Xvfb اجرا شده‌اند، اما نصب واقعی Windows و اجرای واقعی بعضی ابزارها کامل تأیید نشده بود. بررسی native Windows برای نسخهٔ جاری باید جداگانه انجام شود.

### ۲.۱. قابلیت‌های قدیمی که در اسناد نسخهٔ 1.11.0 دیده شده بودند

موارد زیر در گزارش بررسی نسخهٔ قدیمی مطرح شده‌اند؛ وضعیت واقعی هر مورد در v1.14 باید تأیید شود:

- تاریخچهٔ محلی پروژه و ارتباط پرامپت/پاسخ، Attemptها و checkpointهای انتخابی.
- نسخه‌گذاری پروژه و ثبت منشأ تغییرات.
- دریافت پاسخ از چند پروتکل/فرمت، از جمله JSON، بلوک‌های AIWB، Markdown به‌شکل best-effort و ZIP متنی.
- حفظ/بررسی پاسخ خام و Preview/Diff قبل از Apply.
- اعتبارسنجی مسیر فایل و تلاش تراکنشی برای بازگشت در صورت شکست Apply.
- صف فرمان‌ها با تأیید جداگانه و ثبت stdout/stderr/شواهد اجرا.
- Context Planning و پیشنهاد فایل/بازهٔ مرتبط.
- Prompt تعمیر بر اساس خطاهای ثبت‌شده.
- Git integration اولیه و ثبت وضعیت/نسخه.
- New Project Wizard و امکانات تعریف پروژه.

از روی این فهرست نتیجه نگیرید که تمام رفتارها کامل، امن، تست‌شده یا در v1.14 موجود هستند. این فهرست صرفاً راهنمای شروع ممیزی است.

## ۳. مشکل تجربهٔ واقعی کاربر که باید حل شود

جریان تست‌شدهٔ کاربر تا اینجا چنین بوده است:

1. برنامه را باز می‌کند.
2. پروژه و مشخصات کلی موردنظر را وارد می‌کند.
3. در تب Prompt، تسک را در حد یک یا دو خط تعریف می‌کند.
4. پرامپت تولیدشده را به Gemini یا مدل دیگری می‌دهد.
5. پاسخ مدل را به Workbench برمی‌گرداند.

تا مرحلهٔ پنجم برنامه می‌تواند مفید به نظر برسد، اما پس از آن کاربر در چند حالت گیج می‌شود:

### مشکل A — خروجی مدل ایراد دارد

کاربر نمی‌داند باید همان تسک را اصلاح کند، تسک جدید بسازد، پاسخ را دوباره وارد کند، Repair Prompt بگیرد یا اطلاعاتی به مدل بدهد. اگر Import شکست خورده باشد نیز ممکن است نداند پاسخ خراب است یا فقط قالب آن پشتیبانی نمی‌شود.

### مشکل B — خروجی خوب است، اما پروژه باید گسترش پیدا کند

کاربر می‌خواهد قابلیت تازه‌ای اضافه کند، اما محل روشنی برای تعریف «کار بعدی» نمی‌بیند. ممکن است تسک قبلی را بی‌دلیل ادامه دهد یا از صفر یک پروژهٔ جدید بسازد.

### مشکل C — مدل جدید یا چت جدید زمینه ندارد

چت جدید فایل‌ها، تصمیم‌ها و پاسخ‌های قبلی را نمی‌داند. کاربر نمی‌داند چه مقدار از تاریخچه را باید کپی کند یا چه فایل‌هایی را دوباره ارائه دهد.

### مشکل D — مدل به فایل یا بخشی از کد نیاز دارد

مدل ممکن است بگوید «فایل اصلی را بفرست» یا «کد این تابع را لازم دارم»، اما Workbench درخواست را به‌وضوح تبدیل به اقدام نمی‌کند. کاربر نمی‌داند کدام فایل/خطوط را پیدا کند و چگونه به مدل برگرداند.

### مشکل E — مدل از توانایی‌های Workbench خبر ندارد

مدل به‌صورت پیش‌فرض نمی‌داند برنامه می‌تواند فایل استخراج کند، ZIP بسازد، کد خطوط مشخصی را وارد پرامپت کند یا خروجی چندفایلی بگیرد. پس ممکن است نیازش را مبهم بیان کند یا قالب نامناسب تولید کند.

### نتیجهٔ محصولی

مسئله صرفاً وجود دکمه‌های کم یا زیاد نیست. مسئله این است که برنامه پس از هر رویداد، **اقدام مناسب بعدی را روشن نمی‌کند**. UI و منطق باید وضعیت‌محور شوند؛ نه اینکه تمام قابلیت‌ها هم‌زمان در معرض کاربر باشند.

## ۴. مدل ذهنی ساده برای کاربر

در هر لحظه کاربر باید بتواند به سه سؤال جواب دهد:

1. **دارم روی چه چیزی کار می‌کنم؟** پروژهٔ جاری، هدف بزرگ و Task فعال کدام است؟
2. **تا الان چه اتفاقی افتاده؟** چه پاسخی گرفته شده، چه فایل‌هایی اعمال شده‌اند، چه چیزی بررسی شده و چه چیزی هنوز نامعلوم است؟
3. **حالا چه کاری باید انجام بدهم؟** اصلاح، بررسی، Apply، ارسال اطلاعات بیشتر به مدل، انتخاب مدل/نقش دیگر، یا تعریف کار بعدی؟

صفحهٔ اصلی پروژه باید این سه سؤال را برجسته کند. «Next Action» باید یک اقدام اصلی و دلیل آن را نمایش دهد، نه فهرستی طولانی از دکمه‌های هم‌اهمیت.

نمونهٔ پیام‌ها:

- «پاسخ Agent برنامه‌نویس دریافت شده؛ برای ادامه آن را بررسی کن.»
- «چهار فایل از پنج فایل مورد انتظار شناسایی شد؛ فایل مفقود را درخواست کن یا تحویل ناقص را ثبت کن.»
- «خروجی ساختار معتبر دارد، اما تست هنوز اجرا نشده است.»
- «مدل به دو فایل پروژه نیاز دارد؛ بستهٔ زمینه آماده است.»
- «این پاسخ بر اساس Revision قدیمی پروژه تولید شده؛ قبل از Apply باید سازگاری بررسی شود.»
- «Task فعلی تکمیل شده است؛ می‌توانی کار بعدی را تعریف کنی.»
- «پروژه از آخرین Snapshot منتشرشده جدیدتر است؛ انتشار وضعیت در انتظار انجام است.»

اگر وضعیت مبهم است، برنامه باید یک سؤال کوتاه و مشخص بپرسد؛ نباید به خاطر ابهام، کاربر را به چند تب نامرتبط بفرستد.

## ۵. سه فاز کلان محصول

### فاز اول — هوشمندسازی، کاهش بار کاربر و رفع خطا

این فاز پایهٔ UX و قابلیت اعتماد است. بیشترین تمرکز باید روی Response Inbox و واردکردن خروجی مدل باشد، چون این نقطه بیشترین سردرگمی گزارش‌شده را ایجاد کرده است.

اهداف اصلی:

- پاسخ خام قبل از Parse همیشه حفظ شود.
- تشخیص نوع پاسخ و انتخاب Parser مناسب انجام شود.
- Parse، Validation، Reconciliation، Preview، Apply و Validation نهایی مراحل جدا باشند.
- اگر خروجی بخشی معتبر و بخشی نامعتبر است، قسمت‌های معتبر از بین نروند.
- خطا به زبان روشن بگوید چه اتفاقی افتاده و کاربر چه گزینه‌هایی دارد.
- Repair Prompt بر اساس خطا، Task/Attempt واقعی و زمینهٔ مربوط ساخته شود.
- پاسخ قدیمی، تلاش اشتباه یا پاسخ مربوط به تسک دیگر شناسایی شود.
- درخواست فایل/کد از مدل به Context Request قابل‌بررسی تبدیل شود.
- Capability Manifest به مدل بگوید Workbench واقعاً چه عملیات‌هایی را پشتیبانی می‌کند.
- زیرساخت شناسه و Revision برای فاز دوم آماده شود.

### فاز دوم — V2: برنامه‌ریزی پیشرفته و مدیریت چند Agent

**این مهم‌ترین هدف پروژه است و باید هستهٔ طراحی بلندمدت باشد.** Workbench به کاربر اجازه می‌دهد یک نقش Project Manager تعریف کند، چند نقش دیگر را برای کارهای مشخص به‌کار بگیرد و با انتقال دستی پرامپت و پاسخ میان چت‌های جداگانه، پروژه را پیش ببرد.

نمونه: GPT مدیر پروژه است، Gemini معماری یا کدنویسی را انجام می‌دهد، مدل دیگری بازبین است. چت‌ها به هم متصل نیستند؛ Workbench اطلاعات مشترک و معتبر را نگه می‌دارد و در پرامپت بعدی به مدل مقصد منتقل می‌کند.

شامل:

- Agent Registry و پروفایل‌های قابل‌تعریف.
- Task مستقل از مکالمه، Revision و Attemptهای مستقل.
- Task Graph با وابستگی‌ها و جلوگیری از چرخه.
- Handoff Protocol برای انتقال کار بین Agentهای متفاوت.
- Project State، Decision Ledger و Evidence Ledger.
- Project Manager Prompt/Update و Manager Proposal Protocol.
- بازبینی پیشنهادهای مدیر پروژه پیش از تغییر واقعی وضعیت.
- انتشار خودکار/دوره‌ای Project State به GitHub و صف انتشار قابل‌بازیابی.
- تشخیص خروجی قدیمی، تعارض Agentها، Scope و نیاز به تصمیم کاربر.
- Next Action که کاربر را در هر لحظه راهنمایی کند.

**V2 با ظاهرشدن لیست Agentها تمام نمی‌شود.** یک سناریوی کامل باید از تعریف پروژه تا تقسیم وظیفه، Handoff بین دو مدل، دریافت و بررسی خروجی، ثبت شاهد، Publish وضعیت و ادامهٔ برنامه‌ریزی مدیر پروژه کار کند.

### فاز سوم — رابط کاربری ساده/پیشرفته و زیباسازی

رابط ساده باید کاربر را از مسیر طبیعی کار هدایت کند. رابط پیشرفته همان منطق را با دسترسی به جزئیات Agent، Task Graph، Revision، شواهد، تصمیم‌ها، GitHub Publish و تنظیمات تخصصی ارائه می‌کند.

حالت ساده و پیشرفته باید روی یک مدل داده و سرویس‌های مشترک سوار باشند. «ساده» به معنی حذف کنترل ایمنی یا پنهان‌کردن شکست نیست؛ به معنی نمایش اطلاعات در زمان مناسب و با واژگان قابل‌فهم است.

## ۶. قواعد طراحی مشترک و مرجع حقیقت

این اصول در تمام فازها الزامی‌اند.

### ۶.۱. منبع حقیقت

- وضعیت محلی Workbench و سرویس‌های معتبرش، مرجع اصلی Taskها، Attemptها، تصمیم‌ها، شواهد و وضعیت جاری است.
- GitHub حاوی Snapshot/Projection منتشرشده است؛ اگر قدیمی یا در دسترس نباشد، وضعیت محلی از بین نمی‌رود.
- چت مدل و متن پاسخ مدل مرجع نهایی وضعیت پروژه نیست.
- کد روی دیسک و Git Commitها وضعیت واقعی سورس را نشان می‌دهند؛ Project State Snapshot توضیح می‌دهد پروژه از نظر مدیریت کار در چه وضعی است. این دو یکسان نیستند.

### ۶.۲. ادعا با شاهد فرق دارد

- `model_report`: مدل ادعا کرده کاری انجام شده است.
- `file_change`: Workbench تغییر فایل را واقعاً مشاهده کرده است.
- `test_run`: Workbench فرمان تست را اجرا و نتیجه را ثبت کرده است.
- `build_run`: Build مشخص از Commit مشخص تولید شده است.
- `manual_review`: کاربر تصمیم یا تأییدی داده است.
- `external_artifact`: خروجی واقعی از CI دریافت شده است.

اگر تست اجرا نشده یا ابزار در دسترس نیست، وضعیت باید `not_verified`, `blocked` یا مشابه باشد، نه `passed`.

### ۶.۳. مراحل مجزا

این‌ها مترادف نیستند: دریافت پاسخ، Parse، اعتبارسنجی، Reconcile با Task، Review، Apply، اجرای تست، تکمیل Task، Publish وضعیت. موفقیت یک مرحله مجوز خودکار مرحلهٔ بعدی نیست.

### ۶.۴. شناسه و Revision پایدار

Project، Agent، Task، Task Revision، Attempt، Response، Handoff، Artifact، Decision، Evidence و Snapshot شناسهٔ مستقل داشته باشند. نام نمایشی شناسهٔ مرجع نیست.

### ۶.۵. حفظ تاریخچه

پاسخ جدید، Attempt قبلی را بازنویسی نمی‌کند. رد یا لغو نیز رکورد را حذف نمی‌کند. تغییر هدف یا معیار پذیرش Task یک Revision جدید ایجاد می‌کند.

### ۶.۶. Idempotency

تکرار دوبارهٔ Import/Apply/Publish نباید خروجی تکراری یا تخریب‌کننده بسازد. عملیات دارای ID، وضعیت و نتیجه باشند. روی تکرار یک درخواست Publish برای همان State Revision نباید Commitهای تکراری بی‌دلیل ساخته شود.

### ۶.۷. سازگاری Schema

Schemaهای پایدار نسخه‌گذاری شوند. پاسخ‌های قدیمی از مسیر Legacy Import پشتیبانی شوند. فیلد اجرایی ناشناخته حدس زده نشود. تغییر قرارداد با migration مشخص و تست‌شده انجام شود.

# بخش A — فاز اول: Response Inbox و Context Request

## ۷. Response Inbox: ورودی واحد برای همهٔ خروجی‌ها

### ۷.۱. حفظ پاسخ خام

هنگام Paste، Drag & Drop یا انتخاب فایل، ابتدا `Raw Response` با `response_id` ذخیره شود و سپس Parse انجام شود. قبل از ذخیره نباید Markdown، encoding یا محتوای پاسخ Normalize و حذف شود.

داده‌های پایه:

- `response_id`, زمان دریافت، منبع ورود (`clipboard`, `file`, `zip`, `manual` و غیره)؛
- `project_id`, `task_id`, `task_revision`, `attempt_id` در صورت قابل‌تعیین‌بودن؛
- Hash ورودی خام، وضعیت Parse، خطاها و محل ذخیره؛
- نوع احتمالی پاسخ و Parser انتخاب‌شده.

اگر Parse شکست خورد، کاربر بتواند متن اصلی را ببیند، دوباره Parse کند یا آن را به‌صورت یادداشت/پاسخ خام نگه دارد.

### ۷.۲. انواع ورودی

Parserها ممکن است JSON، بلوک ساختاریافتهٔ AIWB، Markdown/کد چندفایلی، ZIP، Patch/Diff، گزارش مدیر پروژه، Handoff، Context Request یا متن عادی را تشخیص دهند. تشخیص نوع، پیشنهاد Parser است نه مجوز اعمال.

اگر پاسخ مبهم است، برنامه چند گزینهٔ روشن نمایش دهد؛ هیچ پاسخ نباید صرفاً به خاطر اینکه با Schema جدید منطبق نیست از دست برود.

### ۷.۳. Pipeline اجباری

`Capture → Classify → Parse → Validate → Reconcile → Preview → User Decision → Apply/Record`

- `Capture`: پاسخ خام را حفظ کند.
- `Classify`: قالب محتمل را تشخیص دهد.
- `Parse`: ساختار و Artifactها را استخراج کند.
- `Validate`: Schema، مسیر، نوع فایل و موارد مورد انتظار را بررسی کند.
- `Reconcile`: شناسه، Revision و تلاش مربوط را بررسی کند.
- `Preview`: برداشت برنامه و اقلام استخراج‌شده را نشان دهد.
- `User Decision`: پذیرش/رد/اصلاح/نگهداری خام.
- `Apply/Record`: فقط عملیات تأییدشده یا ثبت نتایج.

هیچ Parserی فایل Apply نکند؛ هیچ مرحلهٔ Import فرمانی را اجرا نکند.

### ۷.۴. پاسخ ناقص و جزئی

اگر از پنج Artifact مورد انتظار چهار مورد دریافت شده‌اند، چهار مورد سالم حفظ شوند و مورد پنجم مشخص شود. خطاهای هر فایل جدا از خطای کل پاسخ باشند. کاربر باید بتواند با همان پاسخ خام، Import را دوباره انجام دهد یا فقط فایل مفقود را درخواست کند.

### ۷.۵. تشخیص تلاش قدیمی

برای هر اجرای پرامپت، `attempt_id` مستقل تولید شود. اگر پاسخ به Attempt قبلی مربوط بود، ذخیره شود اما بی‌صدا نتیجهٔ Attempt جدید تلقی نشود. اگر ID در متن پاسخ نیست، UI باید از کاربر بخواهد Attempt/Task مقصد را انتخاب کند یا اتصال را با هشدار پیشنهادی انجام دهد.

### ۷.۶. خطای قابل‌فهم

هر پیام خطا باید این اطلاعات را داشته باشد:

1. چه اتفاقی افتاد؟
2. چه چیزی با موفقیت دریافت/استخراج شد؟
3. چه چیزی نامعتبر، مفقود یا نامطمئن است؟
4. دادهٔ خام کجا حفظ شده است؟
5. امن‌ترین اقدام بعدی چیست؟

از پیام‌هایی مثل «Invalid format» به‌تنهایی اجتناب شود. علت مشخص و گزینهٔ بازیابی نمایش داده شود.

## ۸. Context Request — درخواست فایل یا کد از سمت مدل

این یکی از نیازهای مشخص‌شده در تست واقعی کاربر است. گاهی مدل برای ادامهٔ کار به یک فایل یا بخش کد نیاز دارد، اما کاربر نمی‌داند چه فایلی را آماده کند و در کجای Workbench این درخواست را مدیریت کند.

### ۸.۱. اصل رفتار

مدل به‌صورت مستقیم به فایل‌سیستم محلی دسترسی ندارد و نمی‌تواند واقعاً فرمانی به Workbench بفرستد. مدل فقط می‌تواند در خروجی خود درخواست ساختاریافته تولید کند. Workbench آن درخواست را بررسی می‌کند، فایل/بخش کد را آماده می‌سازد و به کاربر می‌گوید بسته یا پرامپت آماده‌شده را به همان چت مدل منتقل کند.

### ۸.۲. Capability Manifest

Workbench باید هنگام تولید پرامپت، فهرست قابلیت‌های واقعی و فعال خود را به مدل معرفی کند. این Manifest باید از Registry/تنظیمات داخلی تولید شود یا با قابلیت‌های واقعی کد هماهنگ نگه داشته شود؛ متن دست‌نویس مستقل که به‌مرور قدیمی شود مناسب نیست.

نمونهٔ قابلیت‌ها:

- درخواست یک فایل کامل از پروژه؛
- درخواست خطوط مشخص یک فایل؛
- درخواست تابع/کلاس/ساختار مشخص در زبان‌های پشتیبانی‌شده؛
- ساخت Context Pack به‌صورت ZIP یا قطعه‌کد در پرامپت؛
- درخواست سؤال تکمیلی از کاربر؛
- اعلام فایل/Artifact ناقص؛
- درخواست اطلاعاتی که در زمینهٔ جاری حاضر نیست.

پرامپت باید صریح بگوید که مدل به فایل‌سیستم دسترسی مستقیم ندارد؛ باید درخواست را در قالب تعریف‌شده تولید کند و هر درخواست توسط Workbench اعتبارسنجی و به کاربر نمایش داده می‌شود. هیچ قابلیتی که واقعاً پیاده‌سازی نشده به مدل وعده داده نشود.

### ۸.۳. قرارداد `AIWB_CONTEXT_REQUEST`

یک Schema نسخه‌دار تعریف شود. حداقل فیلدهای پیشنهادی:

- `schema_version`, `request_id`, `project_id`, `task_id`, `task_revision`, `attempt_id`;
- `reason`: دلیل نیاز به زمینه؛
- `files[]`: فهرست فایل‌های درخواست‌شده؛
- برای هر فایل: `path`, `mode`, `required`, `reason`؛
- `mode`: حداقل `full_file` و `range`; در آینده `symbol` برای تابع/کلاس در زبان پشتیبانی‌شده؛
- `ranges[]`: شمارهٔ خط شروع/پایان در حالت range؛
- `questions[]`: سؤال‌هایی که باید کاربر جواب دهد؛
- `urgency` یا `blocking` در صورت نیاز، بدون اینکه مدل بتواند وضعیت Task را به‌تنهایی تغییر دهد.

نمونه:

```json
{
  "schema_version": "1.0",
  "type": "AIWB_CONTEXT_REQUEST",
  "request_id": "CR-0042",
  "task_id": "TASK-0142",
  "task_revision": 3,
  "attempt_id": "ATT-004",
  "reason": "بررسی رفتار فعلی پنجره پیش از اضافه‌کردن تنظیمات",
  "files": [
    {
      "path": "src/main_window.py",
      "mode": "range",
      "ranges": [{ "start_line": 120, "end_line": 230 }],
      "required": true,
      "reason": "فهم چرخه فعلی ساخت پنجره"
    },
    {
      "path": "requirements.txt",
      "mode": "full_file",
      "required": true,
      "reason": "بررسی وابستگی‌ها"
    }
  ],
  "questions": []
}
```

نمونه، قرارداد پیشنهادی است؛ باید با parserها و مدل دادهٔ واقعی سازگار شود.

### ۸.۴. رفتار UI برای Context Request

پس از واردکردن پاسخ، اگر درخواست ساختاریافتهٔ فایل تشخیص داده شد، به‌جای خطا صفحه‌ای روشن نشان دهد:

- «مدل به اطلاعات بیشتری نیاز دارد»؛
- فهرست فایل‌ها/بازه‌ها و دلیل هر درخواست؛
- آیا فایل وجود دارد یا نه؛
- آیا درخواست به محدودهٔ پروژه می‌خورد؛
- آیا فایل حساس یا ممنوع است؛
- روش پیشنهادی تحویل: کد Inline یا ZIP؛
- دکمه‌های مشاهده/ویرایش محتوا، ساخت بسته و کپی پرامپت ادامه.

ساخت بسته یا کپی پرامپت به‌معنی ارسال اطلاعات به مدل نیست. UI باید دقیقاً بگوید «آمادهٔ ارسال» و نه «ارسال شد».

### ۸.۵. Inline Code در مقابل ZIP

- یک یا چند قطعه‌کد کوچک: می‌توان آن‌ها را همراه مسیر، محدودهٔ خطوط، Revision/Hash منبع و جداکنندهٔ روشن در پرامپت بعدی جاسازی کرد.
- فایل کامل یا چند فایل: Context Pack/ZIP بساز؛ Manifest مسیر اصلی، روش استخراج، Hash و محدودهٔ هر فایل را ثبت کند.
- پاسخ بزرگ/مبهم: بستهٔ ZIP و Preview محتوا بهتر از پرامپت متنی عظیم است.
- اگر رابط چت انتخابی ZIP را نپذیرد، راه جایگزین تولید قطعه‌کد Inline یا تحویل فایل‌ها به‌صورت جداگانه ارائه شود.

### ۸.۶. استخراج خطوط و Symbol

برای `range`، فایل جاری را با اعتبارسنجی مسیر بخوان و محدوده را نمایش بده. برای درخواست Symbol مانند `load_project()`، ابتدا فقط در زبان‌هایی که parser/AST قابل‌اعتماد وجود دارد پشتیبانی کن؛ در غیر این صورت جست‌وجوی best-effort پیشنهاد شود و قطعیت ادعا نشود.

اگر فایل از زمان درخواست مدل تغییر کرده باشد، بر اساس Hash ثبت‌شده یا Revision تشخیص بده که درخواست مبتنی بر نسخهٔ قدیمی است. در آن حالت از کاربر بپرس آیا نسخهٔ فعلی ارسال شود، همان نسخهٔ قبلی در دسترس است یا پرامپت جدید ساخته شود.

### ۸.۷. درخواست مبهم در متن عادی

اگر مدل بلوک `AIWB_CONTEXT_REQUEST` نساخت ولی متن پاسخ می‌گوید «فایل اصلی را ارسال کن»، Workbench می‌تواند این مورد را به‌عنوان پیشنهاد تشخیص دهد، اما نباید متن آزاد را فرمان قطعی تلقی کند. در UI درخواست را خلاصه کرده و از کاربر می‌خواهد فایل/محدوده را انتخاب یا اصلاح کند.

### ۸.۸. درخواست فایل ناموجود یا خطرناک

- فایل ناموجود: مورد مشخص شود؛ گزینهٔ انتخاب فایل مشابه، پاسخ به سؤال یا تولید پرامپت جایگزین ارائه شود.
- مسیر خارج از پروژه/traversal/symlink غیرمجاز: رد شود.
- Secretها، `.env` و فایل‌های حساس: به‌صورت پیش‌فرض وارد Context Pack نشوند؛ هشدار و تصمیم آگاهانهٔ جداگانه لازم است.
- درخواست کل پروژه: ابتدا فهرست پیشنهادی فایل‌های مرتبط و مسیرهای حذف‌شده نشان داده شود؛ همهٔ فایل‌ها بی‌قیدوشرط جمع نشوند.
- درخواست تکراری: تاریخچه نشان دهد فایل قبلاً برای کدام Attempt آماده شده و آیا کاربر گزارش کرده که آن را در چت قرار داده است. برنامه نمی‌تواند به‌طور قطعی بداند کاربر فایل را در چت بارگذاری کرده؛ این وضعیت باید صادقانه نمایش داده شود.

### ۸.۹. معیارهای پذیرش Context Request

1. پاسخ دارای درخواست ساختاریافته به‌عنوان خطای Import رد نشود.
2. درخواست به Task/Attempt و Revision صحیح متصل شود.
3. فایل‌های موجود به Preview قابل‌مشاهده تبدیل شوند.
4. Inline و ZIP هر دو مسیر پشتیبانی شوند.
5. پاسخ خام حفظ شود.
6. فایل حساس، مسیر نامعتبر یا فایل بیرون از پروژه بی‌صدا بسته‌بندی نشود.
7. اگر مدل فرمت ساختاریافته را رعایت نکرد، مسیر دستی بازیابی موجود باشد.
8. وضعیت «آماده‌شده برای ارسال» با «مدل فایل را دریافت کرده است» اشتباه نشود.

# بخش B — فاز دوم: V2، مهم‌ترین هدف محصول

## ۹. تعریف هدف فاز دوم

فاز دوم یک سیستم مدیریت پروژهٔ چندعاملی است، نه موتور فراخوانی چند مدل. کاربر یک نقش Project Manager انتخاب می‌کند و نقش‌های دیگر را برای Taskهای مشخص استفاده می‌کند. تعامل همچنان دستی است:

`Workbench Prompt → کپی به چت عادی مدل → پاسخ مدل → Import به Workbench → بررسی/ثبت → Handoff بعدی`

GPT و Gemini لازم نیست به تاریخچهٔ هم دسترسی داشته باشند. Workbench حافظهٔ مشترک معتبر و Handoff را تولید می‌کند.

### ۹.۱. تعریف پایان واقعی V2

V2 زمانی موفق است که یک پروژهٔ واقعی بتواند:

1. هدف و محدودهٔ پروژه را تعریف کند.
2. مدیر پروژه و چند نقش Agent را ثبت کند.
3. مدیر پروژه یک طرح ساختاریافته شامل تسک، Scope، معیار پذیرش و وابستگی پیشنهاد کند.
4. کاربر طرح را اصلاح/تأیید کند.
5. Taskهای آماده و مسدود درست تشخیص داده شوند.
6. یک Task به GPT و Task بعدی/وابسته به Gemini داده شود.
7. پاسخ هر مدل به Attempt و Handoff درست متصل شود.
8. خروجی ناقص، قدیمی یا متعارض بدون گم‌شدن داده تشخیص داده شود.
9. فایل/کد موردنیاز از طریق Context Request تهیه شود.
10. فایل‌ها Preview، Apply و در صورت نیاز Validation شوند.
11. ادعاهای مدل از Evidence واقعی جدا باشند.
12. Project State Snapshot از وضعیت محلی سازگار ساخته شود.
13. Snapshot به GitHub منتشر شود یا در صف باقی بماند.
14. پرامپت مدیر پروژه با Snapshot/خلاصهٔ fallback ساخته شود.
15. پاسخ مدیر پروژه به Proposal ساختاریافته تبدیل شود.
16. کاربر Proposal را بررسی/قبول/رد کند.
17. تغییرات معتبر در Task Graph و Decision Ledger ثبت شوند.
18. Next Action روشن باشد و چرخه ادامه پیدا کند.

## ۱۰. معماری مفهومی فاز دوم

خدمات باید مرز مسئولیت روشن داشته باشند. نام فایل‌ها پیشنهاد است و باید با معماری موجود تطبیق داده شود:

- `agent_registry`: پروفایل Agentها؛
- `task_service`: Task، Revision، وابستگی و اعتبارسنجی Graph؛
- `attempt_service`: تلاش‌های مستقل مدل؛
- `response_inbox`: پاسخ خام و Parse/Reconcile؛
- `handoff_service`: ساخت Handoff و Prompt؛
- `decision_ledger`: تصمیم‌های پیشنهادی/تأیید/رد/جایگزین‌شده؛
- `evidence_service`: ثبت شواهد؛
- `project_state_service`: Snapshot سازگار از وضعیت محلی؛
- `github_state_publisher`: انتشار وضعیت و مدیریت صف/تعارض؛
- `proposal_review_service`: بررسی پیشنهادهای مدیر پروژه؛
- `next_action_service`: اقدام بعدی و دلیل آن.

UI این سرویس‌ها را هماهنگ می‌کند، اما منطق داده و تصمیم امنیتی نباید در callbackهای UI پراکنده شود. اگر قابلیت موجودی شبیه یکی از این سرویس‌ها وجود دارد، توسعهٔ همان سرویس ترجیح دارد.

## ۱۱. قرارداد پایهٔ اول: Agent و Task

### ۱۱.۱. Agent یک نقش است، نه حساب مدل

Agent پروفایل قابل‌بازاستفاده با دستورالعمل، مسئولیت، قرارداد ورودی/خروجی و سیاست ارجاع است. `preferred_model` فقط برچسب/ترجیح متنی است؛ Agent به GPT یا Gemini قفل نمی‌شود.

فیلدهای پیشنهادی Agent:

- `agent_id`, `name`, `role`, `purpose`;
- `instructions`, `revision`;
- `preferred_model_label`;
- `input_contract`, `output_contract`;
- `allowed_task_types`, `review_policy`, `escalation_rules`;
- `enabled`, `created_at`, `updated_at`.

نقش‌های Template پیشنهادی: Project Manager، Architect/Planner، Implementer، Reviewer/QA و در آینده Researcher/Technical Writer/Security Reviewer. نقش‌های زیاد در شروع لازم نیستند.

### ۱۱.۲. Task مستقل از مکالمه

حداقل فیلدهای Task:

- `task_id`, `project_id`, `task_revision`;
- `title`, `objective`, `context_refs`;
- `owner_agent_id` و نقش‌های کمکی؛
- `depends_on`؛
- `scope.include`, `scope.exclude`;
- `acceptance_criteria`, `deliverables`;
- `base_state_revision`, `base_commit_sha`, و Hash فایل‌های کلیدی در صورت نیاز؛
- `priority`, `risk_level`, `required_approvals`;
- `status`, timestamps و `origin`.

تغییر هدف/Scope/Acceptance Criteria یک Revision جدید می‌سازد؛ Attemptهای قبلی به Revision پیشین متصل باقی می‌مانند.

### ۱۱.۳. وضعیت Task و Attempt مستقل باشد

وضعیت‌های پیشنهادی Task:

- `draft`: تعریف اولیه؛
- `proposed`: پیشنهادشده، منتظر تأیید در صورت نیاز؛
- `ready`: پیش‌نیازها برآورده شده؛
- `in_progress`: کار فعال است؛
- `blocked`: مانع دارد؛
- `needs_decision`: تصمیم انسانی لازم است؛
- `in_review`: تحویل آمادهٔ بازبینی است؛
- `validation_pending`: بررسی لازم هنوز کامل نیست؛
- `done`: معیارهای الزامی با شواهد کافی برآورده شده‌اند؛
- `cancelled`: لغو با حفظ تاریخچه؛
- `superseded`: با Task/Revision جدید جایگزین شده.

وضعیت‌های پیشنهادی Attempt:

`created`, `prompt_ready`, `exported`, `waiting_response`, `response_received`, `parse_failed`, `parsed`, `reconciliation_required`, `ready_for_review`, `accepted`, `rejected`, `stale`, `abandoned`.

### ۱۱.۴. گراف وابستگی

- وابستگی به خود ممنوع است.
- چرخه در گراف رد شود.
- شناسهٔ وابستگی ناموجود رد شود.
- لغو پیش‌نیاز، Task وابسته را بی‌صدا آزاد نکند.
- Revision جدیدِ Scope/Acceptance Criteria باید Taskهای وابستهٔ متأثر را علامت‌گذاری کند.
- موازی‌سازی تنها وقتی پیشنهاد شود که وابستگی‌ها تکمیل و تداخل فایل/قرارداد روشن باشد.

### ۱۱.۵. مالکیت فایل و موازی‌سازی

در نسخهٔ اولیهٔ V2، چند Task می‌توانند هم‌زمان در وضعیت پیشرفت باشند، اما این به معنی Apply هم‌زمان روی همان فایل نیست. هر Task باید محدوده و Revision مبنا داشته باشد. خروجی‌ها به Change Set مستقل تبدیل شوند و قبل از Apply با فایل‌های فعلی تطبیق داده شوند.

اگر دو Agent یک فایل را تغییر داده‌اند، Workbench به‌صورت خودکار یکی را انتخاب یا هانک‌ها را ادغام نکند. تعارض باید نمایش داده و حل آن به کاربر/فرایند بازبینی سپرده شود. پشتیبانی از Branch/Worktree به‌عنوان بهبود Git آینده قابل بررسی است، نه شرط اولیهٔ پروتکل.

## ۱۲. قرارداد پایهٔ دوم: Handoff Protocol

### ۱۲.۱. سه بخش اصلی

1. **مأموریت مقصد:** Task/Revision، هدف، Scope، معیار پذیرش، محدودیت‌ها، خروجی مورد انتظار.
2. **زمینهٔ معتبر:** خلاصهٔ مرتبط پروژه، تصمیم‌های تأییدشده، خروجی Taskهای وابسته، فایل‌ها و Revision مبنا.
3. **تحویل مبدأ:** خلاصهٔ کار، Artifactها، موارد ناقص، فرض‌ها، سؤال‌ها، یافته‌های بازبینی، ادعاهای مدل و شواهد واقعی.

### ۱۲.۲. فیلدهای حداقلی

`handoff_id`, `schema_version`, `project_id`, `task_id`, `task_revision`, `attempt_id`, `from_agent_id`, `to_agent_id`, `created_at`, `base_state_revision`, `base_commit_sha`, `outcome`, `summary`, `completed_items`, `unresolved_items`, `assumptions`, `decision_requests`, `artifact_refs`, `validation_claims`, `verified_evidence_ids`, `recommended_next_action`, `source_response_id`.

`outcome` مانند `complete`, `partial`, `blocked`, `needs_decision`, `failed` فقط گزارش تحویل است؛ وضعیت نهایی Task را به‌تنهایی تعیین نمی‌کند.

### ۱۲.۳. پرامپت Handoff

پرامپت مقصد باید هویت Agent، مأموریت، معیارهای پذیرش، Scope، خلاصهٔ معتبر پروژه، تصمیم‌های مرتبط، تحویل قبلی، فایل‌های موجود/غایب، Revision مبنا و قالب خروجی را مشخص کند. متن گزارش انسان‌خوان و Artifactها می‌توانند جدا باشند؛ مدل مجبور نیست کل پاسخ را JSON کند.

### ۱۲.۴. چرخهٔ Handoff

`created → prompt_ready → exported → response_received → parsed → reconciled → accepted/rejected`

اگر پاسخ ناقص است، Artifactهای سالم حفظ شوند. اگر Revision مبنا قدیمی است، به `stale` یا `reconciliation_required` برود و Apply متوقف شود. اگر پاسخ برای Attempt دیگری است، ذخیره شود اما Task جاری را بی‌صدا تکمیل نکند. رد کاربر نیز دلیل داشته و تاریخچه را نگه دارد.

### ۱۲.۵. معیار پذیرش

- یک Task از GPT به Gemini و سپس بازبین منتقل شود و ID/منشأ از بین نرود.
- Artifact دارای Hash و منشأ باشد.
- ادعای مدل دربارهٔ تست از Evidence واقعی جدا بماند.
- پاسخ ناقص دور ریخته نشود.
- کاربر بتواند بسته و پرامپت Handoff را قبل از Copy مشاهده/ویرایش کند.

## ۱۳. قرارداد پایهٔ سوم: Project State، Decision Ledger و Evidence

### ۱۳.۱. Project State Snapshot

Workbench یک Snapshot از وضعیت محلی معتبر می‌سازد. Snapshot باید صریحاً اعلام کند مربوط به کدام Revision و کدام Commit سورس است؛ وضعیت پروژه و وضعیت کد دو جریان مستقل‌اند.

فیلدهای پیشنهادی:

- `schema_version`, `project_id`, `state_revision`, `generated_at_utc`;
- `previous_snapshot_hash` یا ارجاع Snapshot قبلی؛
- `source.repository_id`, `repository`, `branch`, `commit_sha`;
- `source.local_changes_pending` و در صورت لزوم شرح محدود تغییرات بدون افشای محتوای سورس؛
- هدف/خلاصهٔ تأییدشده و فاز جاری؛
- شمارش Taskها که توسط Workbench محاسبه شده باشد؛
- IDهای Task فعال/مسدود/نیازمند تصمیم؛
- IDهای Decision باز؛
- آخرین Evidence معتبر و وضعیت Validation؛
- اقدام بعدی پیشنهادی/تأییدشده؛
- زمان/Revision آخرین Publish و وضعیت آن.

شمارش‌ها و وضعیت‌ها را مدل ننویسد؛ Workbench از داده‌های معتبر محاسبه کند.

### ۱۳.۲. Decision Ledger

هر Decision شامل `decision_id`, revision، عنوان/مسئله، گزینه‌های بررسی‌شده، انتخاب و دلیل، وضعیت (`proposed`, `accepted`, `rejected`, `superseded`)، منشأ پیشنهاد، تأییدکننده/زمان، Taskها و قراردادهای متأثر و ارجاع به تصمیم قبلی است.

تصمیم ردشده را حذف نکن؛ نگه‌دار تا مدل بعداً همان گزینه را بی‌خبر دوباره پیشنهاد ندهد.

### ۱۳.۳. Evidence Ledger

هر Evidence حداقل `evidence_id`, type, observed_at, subject reference, source, source revision/commit, result, summary, URL/path/log reference, verification method و Hash/Artifact ID در صورت کاربرد دارد.

انواع پیشنهادی: `model_report`, `file_change`, `test_run`, `build_run`, `git_operation`, `manual_review`, `external_artifact`.

### ۱۳.۴. وضعیت نهایی Task از سیاست و شواهد به دست آید

- مدل گزارش می‌کند پیاده‌سازی تمام شده: حداکثر `in_review`.
- Diff پذیرفته و Apply شده: ممکن است `validation_pending` باقی بماند.
- تست لازم واقعاً اجرا شده و معیارها/تأییدهای لازم برآورده‌اند: می‌تواند `done` شود.
- ابزار نصب نیست یا تست اجرا نشده: `not_verified`/`blocked`، نه موفق.
- برای Taskهایی که ذاتاً تست اجرایی ندارند، سیاست پذیرش می‌تواند Review انسانی یا Artifact مشخص باشد؛ نباید برای همهٔ Taskها شرط تست کدنویسی تحمیل شود.

### ۱۳.۵. اتصال Auto-Publish به GitHub

انتشار وضعیت در GitHub باید روی زیرسیستم GitHub Integration سوار شود، نه یک کلاینت/Token جداگانه.

تنظیمات هر Project:

- Repository binding؛
- Branch/مسیر هدف وضعیت (پیشنهاد پیش‌فرض: `aiwb-state` یا مخزن وضعیت مستقل در صورت نیاز)؛
- فایل‌های Status مجاز؛
- سیاست Event-driven و بازهٔ دوره‌ای؛
- قواعد redaction/ignore؛
- Snapshot آخر منتشرشده و صف Publish.

**Auto-Publish Project State جدا از Auto-Sync کد است.** تغییر Task/Decision/ Evidence می‌تواند Snapshot را به‌روزرسانی کند؛ این کار نباید به‌طور ضمنی Commit/Push سورس را انجام دهد.

### ۱۳.۶. انتشار رویدادمحور و دوره‌ای

- رویدادمحور: پس از تغییر معنادار مانند Decision تأییدشده، وضعیت Task، Evidence مهم یا Handoff پذیرفته‌شده، انتشار علامت‌گذاری شود.
- Debounce/Coalesce: تغییرات نزدیک به هم در یک Snapshot جمع شوند.
- دوره‌ای: بازهٔ قابل‌تنظیم مانند 5/15/30/60 دقیقه به‌عنوان fallback؛ این Timer فقط وقتی برنامه اجراست فعال است، مگر Windows Task Scheduler به‌صورت قابلیت جداگانه ساخته شود.
- No-op: اگر Hash Snapshot جدید با آخرین Snapshot منتشرشده برابر است، Commit تکراری نساز.
- Queue: در اینترنت قطع/خطای موقت، Revision محلی حفظ و انتشار در صف بماند.
- Retry: Backoff و `Retry-After`/rate limit رعایت شود.
- Conflict: مقصد قبل از نوشتن بررسی شود؛ Force Push ممنوع؛ در تعارض، Snapshot محلی حفظ شود.
- Idempotency: هر Publish شناسه و State Revision دارد.
- عملیات نوشتن چندفایلی به‌صورت Commit واحد انجام شود تا Snapshot نیمه‌نوشته منتشر نشود.
- پس از بسته‌شدن برنامه، صف پایدار بماند و در اجرای بعدی بازیابی شود.

### ۱۳.۷. ساختار پیشنهادی انتشار

نمونه:

```text
.aiwb/
├── project-state.json
├── PROJECT_STATUS.md
├── decisions/
├── tasks/             # فقط داده‌هایی که اجازهٔ انتشار دارند
└── handoffs/          # خلاصه/Manifest منتخب، نه الزاماً پاسخ خام کامل
```

ساختار نهایی باید با نیاز واقعی و قابلیت خواندن مدل‌ها آزمایش شود. بعضی چت‌ها/ابزارهای GitHub ممکن است فقط Branch پیش‌فرض را آسان بخوانند. در آغاز اتصال، Compatibility Probe انجام شود. اگر مدل به Branch وضعیت دسترسی ندارد، خلاصهٔ کم‌حجم داخل پرامپت قرار گیرد؛ یا مسیر خواندنی مناسب‌تری تعریف شود. هیچ‌گاه فرض نکن همهٔ مدل‌ها مخزن خصوصی و Branch دلخواه را می‌خوانند.

### ۱۳.۸. محتوایی که به‌طور پیش‌فرض منتشر نشود

- Tokenها، رمزها، کلید امضا، کوکی و Secret؛
- همهٔ Promptها/Responseهای خام بدون انتخاب صریح؛
- سورس یا محتوای فایل صرفاً به دلیل استفاده در Context؛
- مسیر مطلق محلی و دادهٔ شخصی غیرضروری؛
- Logهای بالقوه حاوی Secret.

کاربر باید بداند کدام بخش منتشر می‌شود. انتشار وضعیت نباید به معنی Push خودکار همه‌چیز باشد.

### ۱۳.۹. رفتار در شکست Publish

- GitHub در دسترس نیست: وضعیت محلی معتبر می‌ماند، صف و زمان آخرین تلاش نمایش داده می‌شود.
- Credential نامعتبر است: انتشار متوقف و پیام روشن می‌شود؛ retry بی‌نهایت انجام نشود.
- Rate limit: زمان retry رعایت شود.
- Branch جلوتر رفته است: Fetch/بررسی؛ نه Force Push.
- وضعیت محلی جدیدتر از Snapshot آمادهٔ ارسال است: Snapshot قدیمی جای آخرین وضعیت معرفی نشود؛ Revision جدیدتر در صف بماند.
- نوشتن یکی از فایل‌ها شکست می‌خورد: Commit چندفایلی اتمیک/هم‌بسته استفاده شود؛ Snapshot ناقص به‌عنوان معتبر معرفی نشود.
- دو دستگاه Publish می‌کنند: نسخهٔ مبنای مقصد بررسی و تعارض گزارش/حل شود.

## ۱۴. Project Manager Agent

### ۱۴.۱. تعریف نقش

مدیر پروژه یک Agent Profile با دستورالعمل روشن است، نه یک سرویس خودکار متصل به چت. کاربر پرامپت آن را در چت معمولی مدل انتخابی ارسال و پاسخ را دستی برمی‌گرداند.

مسئولیت‌ها:

- کمک به روشن‌کردن هدف و Non-goals؛
- پیشنهاد معماری/قرارداد؛
- پیشنهاد Taskها، Scope، Acceptance Criteria و وابستگی‌ها؛
- شناسایی فرض‌ها، ریسک‌ها و تصمیم‌های باز؛
- تحلیل Snapshot/Evidence و گزارش پیشرفت؛
- پیشنهاد بازبرنامه‌ریزی؛
- درخواست شواهد/زمینهٔ تکمیلی؛
- گزارش دوره‌ای و Next Action.

### ۱۴.۲. خروجی برنامه‌ریزی پروژه

حداقل هدف و محدوده، معماری پیشنهادی، فرض‌ها/سؤال‌ها، Agentهای لازم، Task Graph، معیار پذیرش، ریسک، برنامهٔ Validation و سیاست هماهنگی. طرح خام به‌صورت پیشنهاد نمایش داده شود و قبل از ثبت در دیتابیس واقعی قابل‌ویرایش باشد.

### ۱۴.۳. Manager Update Prompt

پرامپت گزارش مدیر باید شامل:

- `state_revision` و زمان Snapshot؛
- Repository/Branch/مسیر وضعیت در صورت انتشار؛
- دستور مراجعه به وضعیت منتشرشده و درخواست اعلام صریح در صورت نداشتن دسترسی؛
- خلاصهٔ ضروری fallback، چون دسترسی به GitHub تضمین‌شده نیست؛
- رخدادهای مهم از گزارش قبلی؛
- Taskهای فعال/مسدود/منتظر Review؛
- Evidenceهای جدید و نتایج واقعی؛
- Decisionهای باز و تعارض‌ها؛
- قالب Proposal مورد انتظار.

مدیر نباید صرفاً خلاصهٔ عمومی تولید کند؛ باید تغییرات پیشنهادی و دلیل آن‌ها را مشخص کند.

### ۱۴.۴. Manager Proposal Protocol

انواع پیشنهادهای قابل‌پشتیبانی در نسخهٔ اول:

- `create_task`؛
- `update_task`؛
- `add_dependency` / `remove_dependency`؛
- `assign_agent`؛
- `propose_decision`؛
- `reorder_priority`؛
- `split_task`؛
- `close_or_cancel_task` به‌صورت پیشنهاد؛
- `request_more_evidence`؛
- `change_scope`؛
- `report_risk`.

هر Proposal دارای شناسه، State/Task Revision مبنا، عملیات پیشنهادی، دلیل، اثر روی Taskهای وابسته و ابهام‌ها باشد. Workbench آن را اعتبارسنجی و به‌صورت Before/After نشان دهد. تغییر معتبر فقط پس از تأیید لازم اعمال شود.

### ۱۴.۵. تفکیک وضعیت و پیشنهاد

مدیر پروژه می‌تواند بگوید «به نظر من TASK-20 تکمیل است» یا پیشنهاد دهد Task اولویت بالاتری بگیرد؛ اما Workbench باید بسنجد Evidence/سیاست پذیرش چه می‌گوید. پیشنهاد مدیر با وضعیت واقعی یکی نیست.

## ۱۵. سناریوهای واقعی چند Agent و رفتار موردانتظار

### سناریو ۱: طرح → پیاده‌سازی بین GPT و Gemini

1. کاربر هدف پروژه را تعریف می‌کند.
2. پرامپت Project Manager به GPT داده می‌شود.
3. طرح و Task Graph به Workbench برمی‌گردد؛ برنامه Schema و وابستگی‌ها را بررسی می‌کند.
4. کاربر طرح را اصلاح/تأیید می‌کند.
5. Task معماری به Agent معمار داده می‌شود؛ Handoff و قراردادها تولید و تأیید می‌شوند.
6. Task پیاده‌سازی به Gemini داده می‌شود و همان قرارداد/زمینهٔ لازم در پرامپت آن قرار می‌گیرد.
7. پاسخ Gemini Import می‌شود؛ فایل‌ها و گزارش به Attempt متصل می‌شوند.
8. فایل‌ها Preview/Apply/Validation می‌شوند؛ نتیجهٔ واقعی Evidence می‌سازد.
9. State Snapshot به‌روز/Publish می‌شود.
10. کاربر Manager Update Prompt می‌سازد و GPT بر اساس آخرین وضعیت پیشنهاد مرحلهٔ بعد را می‌دهد.
11. Proposal بعدی در Workbench Review می‌شود و در صورت تأیید به Task Graph اعمال می‌شود.

### سناریو ۲: مدل فایل می‌خواهد

- مدل `AIWB_CONTEXT_REQUEST` می‌سازد.
- Workbench آن را Parse و اعتبارسنجی می‌کند.
- فایل‌های موجود/ناموجود و محدوده‌ها نمایش داده می‌شوند.
- کاربر Preview را می‌بیند؛ برای قطعه‌کد کوچک Inline Prompt و برای چند فایل ZIP پیشنهاد می‌شود.
- بسته و پرامپت آماده می‌شوند؛ کاربر آن را به همان چت می‌برد.
- وضعیت «آماده شد» ثبت می‌شود، نه «مدل قطعاً دریافت کرد».
- پاسخ بعدی به همان Attempt/Handoff وصل می‌شود.

### سناریو ۳: خروجی ناقص یا Parse ناموفق

- Raw Response حفظ می‌شود.
- فایل‌های سالم استخراج‌شده از دست نمی‌روند.
- UI دقیقاً مورد ناقص/نامعتبر را گزارش می‌کند.
- Next Action، Reparse، Import دستی، درخواست فقط فایل مفقود یا Repair Prompt را پیشنهاد می‌کند.
- Task بی‌دلیل از ابتدا ساخته نمی‌شود.

### سناریو ۴: پروژه گسترش پیدا می‌کند

اگر Task فعلی تکمیل شده و کاربر می‌گوید «حالا امکان ثبت هزینه اضافه کن»، Workbench این را به‌عنوان کار بعدی پیشنهاد می‌کند، نه ادامهٔ اجباری Task قبلی. هدف جدید با وضعیت پروژه مقایسه و Task تازه ساخته می‌شود. اگر کاربر می‌گوید «صفحهٔ فعلی کار نمی‌کند»، این ادامه/اصلاح همان Task است یا Task رفع‌باگ مرتبط ایجاد می‌شود؛ قبل از تصمیم، برنامه باید تفاوت را به زبان ساده روشن کند.

### سناریو ۵: چت جدید یا مدل دیگر

Workbench از حافظهٔ محلی و Snapshot آخر، Handoff جدید می‌سازد. مدل مقصد تمام تاریخچهٔ خام لازم ندارد؛ بستهٔ زمینه شامل هدف، تصمیم‌های تأییدشده، قراردادها، وضعیت Task و فایل‌های مرتبط است. اگر GitHub قابل‌خواندن نباشد، خلاصه در خود Prompt قرار می‌گیرد.

### سناریو ۶: دو Agent تغییر متناقض می‌دهند

اگر دو Change Set با فایل مشترک یا قرارداد متفاوت باشند، هر دو حفظ و تعارض نمایش داده شود. هیچ‌کدام خودکار اولویت نمی‌گیرد. کاربر می‌تواند یکی را انتخاب کند، Task هماهنگ‌کننده بسازد یا از Agent بخواهد با Handoff به‌روز دوباره کار کند.

## ۱۶. Auto-Publish وضعیت در GitHub

Auto-Publish به‌ویژه برای مدیر پروژه مهم است: مدل ممکن است با قابلیت GitHub در چت خود وضعیت پروژه را بخواند و لازم نباشد هر بار تمام جزئیات را در Prompt تکرار کنیم. با این حال دسترسی مدل به Repository خصوصی یا Branch خاص قطعی نیست؛ Compatibility Probe و fallback Prompt الزامی است.

### ۱۶.۱. تفکیک دو عملیات

- `Project State Auto-Publish`: انتشار Manifest، خلاصه، Taskهای فعال، Decisionهای منتخب و Evidenceهای مجاز.
- `Code Auto-Sync`: Commit/Push سورس واقعی.

این دو تنظیم و سرویس مستقل‌اند. انتشار وضعیت به‌طور ضمنی کد را Push نمی‌کند و Push کد به‌طور ضمنی تمام پاسخ‌های مدل را منتشر نمی‌کند.

### ۱۶.۲. Triggerها

- **Event-driven:** تغییر معنادار، پذیرش Handoff، ثبت Evidence، تأیید Decision، تغییر وضعیت Task.
- **Periodic fallback:** بازهٔ انتخابی کاربر مانند 5/15/30/60 دقیقه.
- **Debounce/coalesce:** چند تغییر نزدیک به هم در یک Snapshot جمع شوند.
- **No-op:** اگر محتوا تغییری نکرده، Commit جدید نساز.

Timer داخل برنامه در حالت اجرا فعال است. اگر کاربر می‌خواهد زمان‌بندی هنگام بسته‌بودن برنامه نیز کار کند، این باید با Windows Task Scheduler یا سرویس مشخص دیگری پیاده‌سازی و به‌صراحت تست شود؛ نباید رفتار پس‌زمینهٔ ناموجود وعده داده شود.

### ۱۶.۳. وضعیت Snapshot

حداقل متغیرها:

- `local_state_revision`؛
- `published_state_revision`؛
- `pending_state_revision`؛
- `source_commit_sha`؛
- `last_publish_at` و `publish_status`.

Snapshot باید از یک Revision سازگار ساخته شود و Hash/شناسه داشته باشد. اگر Publish شکست خورد، دادهٔ محلی و صف باقی بمانند. Snapshot قدیمی نباید آخرین وضعیت معرفی شود.

### ۱۶.۴. Branch و ساختار پیشنهادی

Branch جدا مانند `aiwb-state` یا Repository وضعیت مستقل قابل بررسی است. مسیر نمونه:

```text
.aiwb/
├── project-state.json
├── PROJECT_STATUS.md
├── decisions/
├── tasks/
└── handoffs/
```

ساختار واقعی باید با توانایی ابزارهای خواندن GitHub در چت مدل‌ها آزمایش شود. اگر Branch سفارشی یا Repository خصوصی از مدل مقصد قابل خواندن نیست، خلاصهٔ ضروری داخل Prompt گذاشته شود.

### ۱۶.۵. Publisher قابل اعتماد

- Credentialها از زیرسیستم GitHub مشترک استفاده کنند؛ منطق GitHub در چند دکمه تکرار نشود.
- انتشار چندفایلی به صورت یک Commit واحد انجام شود تا Snapshot نصفه در مخزن ظاهر نشود.
- هر Publish دارای `publish_id`, `state_revision`, مقصد و نتیجه باشد.
- Retry با backoff/rate limit محترمانه باشد.
- در تعارض Remote، Force Push انجام نشود.
- در قطع شبکه/بسته‌شدن برنامه، صف در دیتابیس پایدار باقی بماند.
- Publish خالی/تکراری Commit نسازد.

# بخش C — GitHub، Monorepo و اپ موبایل

## ۱۷. تمایز مهم: GitHub integration با AI model integration فرق دارد

کاربر صریحاً نمی‌خواهد Workbench به حساب GPT/Gemini وارد شود یا API مدل داشته باشد. این اصل باید حفظ شود.

GitHub Integration یک نیاز مستقل است تا:

- حساب GitHub/Token از داخل برنامه تنظیم و آزمون شود؛
- Repositoryها فهرست و به پروژه متصل شوند؛
- Git محلی، Commit، Push/Pull و Branch از یک زیرسیستم مدیریت شوند؛
- GitHub Actions وضعیت Build را گزارش کند؛
- Artifactهای مربوط به Commit صحیح دریافت شوند؛
- Project State مستقل از کد منتشر شود.

کاربر خواسته اتصال GitHub برای استفادهٔ شخصی راحت باشد و امکان واردکردن Token داشته باشد. پیاده‌سازی باید Credential را از Repository، Log و Prompt جدا نگه دارد و آن را با Windows Credential Manager یا ذخیره‌سازی امن سیستم‌عامل مدیریت کند. Token نباید در Remote URL، Source Code، Snapshot یا گزارش‌های قابل انتشار قرار گیرد.

## ۱۸. Monorepo برای خود AI Workbench

چون مالک هنوز محصول را به GitHub منتقل نکرده بود و قصد دارد Monorepo داشته باشد، ساختار پیشنهادی کلی چنین است (پیش از اعمال، با سورس موجود و نصب‌کننده تطبیق داده شود):

```text
AI-Workbench/
├── apps/
│   ├── desktop/
│   │   ├── src/
│   │   ├── installer/
│   │   └── tests/
│   └── mobile/
│       ├── app-source/
│       ├── android/
│       ├── ios/              # در صورت نیاز
│       └── tests/
├── packages/
│   └── contracts/
│       ├── schemas/
│       ├── fixtures/
│       └── README.md
├── docs/
│   ├── architecture/
│   ├── product/
│   └── releases/
├── tools/
├── .github/
│   └── workflows/
│       ├── desktop-ci.yml
│       ├── mobile-ci.yml
│       └── release.yml
├── README.md
└── CHANGELOG.md
```

نام و محل دقیق پوشه‌ها به فناوری موبایل و ساختار فعلی وابسته است. این ساختار هدف مفهومی است؛ انتقال به `apps/desktop` نباید به‌صورت جابه‌جایی کورکورانه انجام شود، چون مسیر فایل‌ها ممکن است در نصب‌کننده، تست‌ها یا اسکریپت‌ها hard-coded شده باشد.

### ۱۸.۱. نسخه‌ها و Workflowها مستقل باشند

- تغییر Desktop فقط تست/Build لازم Desktop را اجرا کند.
- تغییر Mobile تست/Build لازم Mobile را اجرا کند.
- تغییر `packages/contracts` تست‌های مشترک و مصرف‌کنندگان متأثر را اجرا کند.
- تغییر صرفاً `.aiwb` وضعیت پروژه، نباید Build کامل محصول را در حالت عادی اجرا کند.
- مراقب path filters باشید: Workflowی که Check اجباری است نباید به وضعیت Pending بی‌پایان رها شود.
- هر Build باید به `repository_id`, `workflow_id`, `run_id`, `commit_sha`, `artifact_id` وصل باشد.

### ۱۸.۲. GitHub Hub داخل Workbench

بخش پیشنهادشده:

- GitHub Accounts: افزودن/اعتبارسنجی حساب و Token.
- Repository Browser: جست‌وجو و انتخاب مخزن قابل دسترسی.
- Repository Binding در هر Project: مخزن، ریشهٔ محلی، Subpath، Branch و تنظیمات Sync.
- Git Operations: وضعیت فایل، Branch، Commit، Fetch/Pull/Push و گزارش تعارض.
- Build Center: Runهای Actions، Log، Artifact و SHA سازنده.
- Project State Publisher: مجزا از Code Auto-Sync.

هر پروژه می‌تواند به Repository شخصی خودش وصل شود. Repository محصول AI Workbench نیز Monorepo مستقل خود محصول است. این دو موضوع نباید در مدل داده با هم اشتباه شوند.

### ۱۸.۳. Sync & Build

یک عملیات راحت می‌تواند مراحل زیر را هماهنگ کند، اما در هر مرحله باید وضعیت روشن و قابلیت لغو امن داشته باشد:

1. بررسی Git Status و فایل‌های Staged/Untracked/Deleted؛
2. نمایش Diff و فایل‌های انتخاب‌شده؛
3. پیشنهاد Commit Message مرتبط با Task؛
4. بررسی Remote و تشخیص جلوتر بودن Branch؛
5. Commit/Push به Branch توسعه، نه انتشار پایدار؛
6. دنبال‌کردن اجرای Workflow مربوط به همان Commit؛
7. نمایش نتیجهٔ تست و Log؛
8. دریافت Artifact متعلق به همان Commit؛
9. ثبت نتیجه در Evidence Ledger.

در تعارض، Force Push پیش‌فرض ممنوع باشد. عملیات Git نباید Token را در متن فرمان/Log چاپ کند.

### ۱۸.۴. Build و انتشار موبایل

- APK آزمایشی و Release پایدار دو کانال جدا باشند.
- هر Artifact به Commit SHA و شمارهٔ نسخه متصل باشد.
- `versionCode` اندروید در هر نسخهٔ متوالی افزایش یابد.
- کلید امضای نسخهٔ نهایی داخل Git/Prompt/Log قرار نگیرد و فقط در محیط مناسب انتشار استفاده شود.
- Build آزمایشی از Pull Request/Branch توسعه نباید به Secretهای انتشار پایدار دسترسی داشته باشد.
- برای دانلود مستقیم APK، Hash فایل و اطلاعات Release ثبت شوند؛ نصب به تأیید و مجوزهای متعارف Android نیاز دارد.
- انتشار iOS مسیر جداگانه می‌خواهد و نباید به‌عنوان نسخهٔ کپی‌شده از APK طراحی شود.

### ۱۸.۵. تکامل قابلیت بین Desktop و Mobile

قابلیت ویندوز لزوماً معادل موبایل ندارد. برای هر Feature یک Capability Registry نگه‌داری شود، مثلاً `desktop: implemented`, `mobile: planned`, `companion: supported`.

زمانی که قابلیت جدید ایجاد می‌شود، Workbench می‌تواند Task پیگیری موبایل پیشنهاد کند. آنچه بین پلتفرم‌ها به اشتراک می‌رود، رفتار، Schema، معیار پذیرش و Fixtureهای تست است؛ UI و عملیات اختصاصی هر سیستم‌عامل جدا می‌مانند.

### ۱۸.۶. Mobile Companion (بعداً)

در صورت نیاز به کنترل Workbench دسکتاپ از طریق گوشی، Companion باید Pairing صریح، مجوزهای جدا برای Read/Apply/Run، ارتباط رمزنگاری‌شده و تأیید عملیات حساس داشته باشد. بازکردن بی‌احراز هویت پورت روی اینترنت توصیه نمی‌شود. این قابلیت prerequisite نسخهٔ اولیهٔ Auto-Publish یا Multi-Agent نیست.

# بخش D — فاز سوم: UI دوحالته

## ۱۹. اصول UX

### ۱۹.۱. حالت ساده

کاربر باید فقط موارد اصلی را ببیند:

- خلاصهٔ هدف و وضعیت پروژه؛
- Task جاری و آخرین خروجی؛
- Next Action واحد با دلیل؛
- نمایش واضح خطا/اطلاعات موردنیاز؛
- ورودی ساده برای «کار بعدی»؛
- وضعیت آخرین Publish یا تست، اگر مرتبط باشد.

نباید نیاز باشد کاربر از میان ده‌ها تب بفهمد باید کجا کلیک کند.

### ۱۹.۲. حالت پیشرفته

برای کاربر حرفه‌ای، اطلاعات زیر قابل مشاهده/ویرایش باشند:

- Agent Registry؛
- Task Graph و وابستگی‌ها؛
- Task/Attempt Revisionها؛
- Handoff و Context Request؛
- Raw Response و Parse Result؛
- Change Set، Hash و شواهد؛
- Decision Ledger و Evidence Ledger؛
- GitHub State Publisher و صف انتشار؛
- تنظیمات Scope، سیاست Review و Validation.

### ۱۹.۳. Next Action واحد

هر دو حالت یک سرویس مشترک برای محاسبهٔ اقدام بعدی داشته باشند. اقدام باید با اولویت، دلیل و مقصد مشخص باشد. مثال‌ها:

- پاسخ مدل باید Import شود؛
- فایل مورد انتظار مفقود است؛
- مدل اطلاعات بیشتری درخواست کرده؛
- Diff آمادهٔ بازبینی است؛
- تست اجرا نشده؛
- تعارض Revision وجود دارد؛
- Project State منتشرنشده است؛
- مدیر پروژه نیازمند گزارش جدید است؛
- Task تکمیل شده و کاربر می‌تواند کار بعدی را تعریف کند.

اگر چند کار مهم وجود دارند، یکی به‌عنوان اقدام اصلی و بقیه در فهرست ثانویه نمایش داده شوند.

### ۱۹.۴. اصطلاحات و خطا

- واژه‌ها در کل برنامه یکدست باشند.
- وضعیت فقط با رنگ نشان داده نشود؛ متن/آیکون/توضیح داشته باشد.
- خطای فنی داخلی به زبان قابل‌فهم ترجمه شود، اما جزئیات قابل‌مشاهده برای کاربر پیشرفته هم موجود باشد.
- هیچ وضعیت `unknown`, `not run`, `blocked` یا `unverified` به‌عنوان موفق نمایش داده نشود.
- دکمه‌ها بر اساس وضعیت فعال/غیرفعال شوند؛ در صفحهٔ فعلی همهٔ عملیات به یک اندازه برجسته نباشند.

### ۲۰.۱. محدودیت چرخهٔ اصلاح

هر اصلاح یک Attempt جدید باشد. بعد از تعداد قابل‌تنظیم چرخه‌های ناموفق پیاپی (پیشنهاد پیش‌فرض: ۳)، به‌جای تولید Repair Prompt جدید به‌صورت تکراری، Task به `needs_decision` برود و خلاصه‌ای از مواردی که تلاش شده، شواهد شکست، تغییرات واقعی و گزینه‌های بعدی نمایش داده شود. عدد پیش‌فرض باید قابل‌تغییر باشد.

## ۲۱. قراردادهای ذخیره‌سازی و مهاجرت

قبل از پیاده‌سازی Agent/Task/Handoff/State، دیتامدل واقعی نسخهٔ فعلی بررسی شود. اگر `task`, `history`, `response`, `project_version` یا مشابه موجود است، به‌جای ساخت جدول موازی، باید مشخص شود چگونه توسعه می‌یابد.

الزامات:

- migrationها نسخه‌گذاری، قابل‌آزمون و دارای مسیر failure recovery باشند.
- backup دیتابیس قبل از migration عمده ساخته شود.
- تاریخچهٔ موجود حفظ شود؛ Attemptهای قدیمی در صورت نبود فیلدهای جدید با مقادیر `legacy/unknown` مهاجرت شوند، نه اینکه دادهٔ خیالی برای آن‌ها ساخته شود.
- `schema_version` در پروتکل‌ها و Snapshotها مشخص باشد.
- parserهای Legacy تا زمان تعیین سیاست deprecation کار کنند.
- schema جدید با fixtureهای واقعی و نمونه‌های malformed تست شود.
- مرجع وضعیت روشن باشد؛ دو سرویس نباید همان داده را با دو منطق متفاوت محاسبه کنند.

## ۲۵. معیارهای موفقیت محصولی

این شاخص‌ها برای ارزیابی عملی مفیدند. در ابتدا Baseline از چند پروژهٔ واقعی بساز؛ سپس قبل/بعد از قابلیت‌ها مقایسه کن.

- **Import Failure Rate:** چه سهمی از پاسخ‌ها به دلیل ساختار/محتوا نیازمند اصلاح دستی می‌شوند؟
- **Recovery Rate:** از پاسخ‌هایی که Import اول شکست خورده، چند مورد بدون دریافت مجدد از مدل قابل‌بازیابی‌اند؟
- **Handoff Rework:** چند تحویل به دلیل زمینهٔ ناقص/ابهام دوباره انجام می‌شود؟
- **Stale Response Rate:** چند پاسخ بر اساس Revision قدیمی تولید شده‌اند؟
- **First-Pass Acceptance:** چه سهمی از تحویل‌ها در اولین Review معیارها را برآورده می‌کنند؟
- **Verification Coverage:** چه سهمی از Taskهای Done شواهد منطبق با Acceptance Policy دارند؟
- **Human Confusion Events:** کاربر چند بار مجبور می‌شود برای فهم قدم بعدی از بیرون برنامه کمک بگیرد یا در تب‌های مختلف جست‌وجو کند؟
- **Publish Reliability:** نرخ موفقیت Snapshot، تعداد انتشار تکراری و بازیابی از قطعی اتصال.
- **Rework / Conflict Rate:** میزان کار دوباره به علت تعارض فایل یا قرارداد.

این شاخص‌ها نباید به پنل‌های شلوغ بی‌هدف تبدیل شوند. هدف، شناخت نقاط اصطکاک و تصمیم‌گیری برای بهبود است.

## ۲۸. اولویت مفهومی: چه چیزهایی اولویت بالاتری دارند؟

این بخش Roadmap زمانی/نسخه‌ای نیست؛ فقط نسبت اهمیت تصمیم‌ها را روشن می‌کند.

1. **جلوگیری از گم‌شدن پاسخ و روشن‌کردن Next Action:** بدون این، تجربهٔ فعلی کاربر همچنان گیج‌کننده می‌ماند.
2. **شناسه و Revision پایدار برای Task/Attempt/Response:** زیربنای Handoff و مدیریت چند Agent.
3. **قرارداد Handoff:** امکان ادامهٔ واقعی کار بین چت/مدل‌های متفاوت.
4. **مرجع Project State و Evidence:** جلوگیری از تکیهٔ مدیر پروژه به ادعای نادرست مدل.
5. **Proposal Review برای مدیر پروژه:** پیشنهادهای ساختاریافته بدون بازنویسی بی‌تأیید برنامه.
6. **GitHub State Publisher:** Snapshot خواندنی، صف پایدار، کنترل تعارض و fallback Prompt.
7. **Context Request و Capability Manifest:** مدل می‌داند چه چیزی درخواست کند و Workbench درخواست را به فایل/قطعه‌کد قابل‌تحویل تبدیل می‌کند.
8. **UI ساده/پیشرفته:** نمایش قدم بعدی، progressive disclosure و کنترل جزئیات.

از نظر راهبردی، فاز دوم مهم‌ترین هدف است. اما ساخت آن بدون Response Inbox قابل‌اعتماد، شناسه/Revision و Context Request تجربهٔ شکننده‌ای خواهد ساخت. فاز اول زیرساخت فاز دوم است؛ فاز سوم باید نحوهٔ استفاده از همین منطق را ساده و قابل‌فهم کند.

## ۲۹. چک‌لیست فهم مشترک قبل از شروع توسعه

برنامه‌نویس و مالک محصول باید روی موارد زیر هم‌نظر باشند:

- [ ] تعامل مدل فقط از طریق Prompt copy/paste و Response import دستی است؛ API/ورود به حساب مدل در هدف نیست.
- [ ] Agent یک نقش است، نه یک اتصال خودکار به مدل.
- [ ] Task از Attempt و مکالمه مستقل است.
- [ ] هر Attempt و Response شناسهٔ مستقل دارد.
- [ ] خروجی خام قبل از Parse حفظ می‌شود.
- [ ] مدل می‌تواند Context Request ساختاریافته تولید کند؛ Workbench آن را بررسی می‌کند و کاربر فایل/بسته را به چت می‌دهد.
- [ ] Capability Manifest فقط قابلیت‌های واقعاً پیاده‌شده را اعلام می‌کند.
- [ ] Project State محلی مرجع اصلی است؛ GitHub Snapshot یک Projection منتشرشده است.
- [ ] Auto-Publish وضعیت و Auto-Sync سورس مستقل‌اند.
- [ ] ادعای مدل با Evidence واقعی یکی نیست.
- [ ] مدیر پروژه Proposal تولید می‌کند؛ Workbench/کاربر آن را اعتبارسنجی و تأیید می‌کنند.
- [ ] تعارض فایل/قرارداد/Revision خودکار و بی‌صدا حل نمی‌شود.
- [ ] Next Action در هر وضعیت قابل‌فهم است.
- [ ] Simple Mode و Advanced Mode از منطق دادهٔ مشترک استفاده می‌کنند.
- [ ] قابلیت موجود از صفر بازسازی نمی‌شود؛ اول Capability Audit انجام می‌شود.

## ۳۰. نتیجهٔ نهایی

AI Workbench قرار نیست صرفاً مجموعه‌ای از ابزارها کنار یکدیگر باشد. هدف، تبدیل تعامل پراکنده با مدل‌های مختلف به یک جریان کاری قابل‌فهم و قابل‌اعتماد است.

در کوتاه‌مدت، برنامه باید به کاربر کمک کند از پاسخ مدل عبور کند: پاسخ را حفظ کند، خطاها را بفهمد، فایل‌های لازم را آماده کند و قدم بعدی را روشن سازد.

در V2، برنامه باید همین مفهوم را به کل پروژه گسترش دهد: نقش‌ها، Taskها، وابستگی‌ها، Handoffها، تصمیم‌ها، شواهد و Snapshot وضعیت را مدیریت کند تا GPT بتواند کار Gemini را ادامه دهد، یا هر مدل دیگری بتواند از نتیجهٔ قبلی استفاده کند، بدون وابستگی به تاریخچهٔ چت قبلی.

GitHub یک لایهٔ مهم برای اشتراک وضعیت، سورس و Build است، اما خود GitHub منبع نهایی وضعیت محلی یا جایگزین تعامل دستی با مدل‌ها نیست. مدل مدیر پروژه می‌تواند به Snapshot منتشرشده مراجعه کند؛ اگر دسترسی ندارد، Workbench خلاصهٔ معتبر را در Prompt ارائه می‌دهد.

سه قرارداد Agent/Task، Handoff و Project State/Evidence باید از ابتدا نسخه‌دار، قابل‌تست و مستقل از UI طراحی شوند. پاسخ مدل، وضعیت واقعی فایل، نتیجهٔ تست، تصمیم انسانی و وضعیت منتشرشده باید قابل‌تفکیک بمانند.

معیار راهنما برای هر قابلیت این باشد: آیا سردرگمی کاربر را کم می‌کند؟ آیا تحویل کار را قابل‌اعتمادتر می‌کند؟ آیا مانع گم‌شدن زمینه و شواهد می‌شود؟ آیا کنترل کاربر و قابلیت بازیابی را حفظ می‌کند؟ اگر نه، ممکن است صرفاً تعداد دکمه‌ها و پیچیدگی را بیشتر کند.

**هدف نهایی:** کاربر هدف و نیاز خود را توضیح دهد؛ AI Workbench وضعیت واقعی پروژه را نگه دارد، اطلاعات مناسب را برای مدل بعدی آماده کند، نتیجه را قابل‌بررسی سازد و همیشه قدم بعدی روشن را نشان دهد—با همان روش سادهٔ چت معمولی، کپی پرامپت و برگرداندن پاسخ.
