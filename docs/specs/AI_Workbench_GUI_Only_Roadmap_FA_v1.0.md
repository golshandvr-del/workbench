# رودمپ نهایی بازطراحی رابط کاربری AI Workbench

**نسخه:** 1.0 نهایی  
**تاریخ تدوین:** 2026-10-19  
**دامنه:** فقط GUI، UX، معماری اطلاعات، طراحی بصری و کیفیت تجربهٔ استفاده در اپ دسکتاپ AI Workbench  
**مبنای مخزن:** Desktop `2.6.0`، شاخهٔ `main` در مخزن `golshandvr-del/workbench`  
**وضعیت:** سند آمادهٔ اجرا؛ شروع کدنویسی منوط به عبور از دروازه‌های تصمیم‌گیری و نمونه‌سازی این سند است.

---

## 0. تصمیم نهایی طراحی در یک نگاه

این پروژه «تعویض رنگ و شکل دکمه‌ها» نیست. هدف، تبدیل رابط فعلی به یک **محیط کاری منسجم، کم‌ابهام، حرفه‌ای و قابل پیش‌بینی** است؛ رابطی که کاربر در هر لحظه بفهمد در کدام پروژه و کدام کار قرار دارد، چه چیزی واقعاً اتفاق افتاده، چه چیزی صرفاً منتظر اقدام دستی اوست و قدم منطقی بعدی چیست.

**جهت پیشنهادی:** ابزار دسکتاپی آرام و کاربردی با تراکم اطلاعات کنترل‌شده؛ ناوبری روشن، یک فضای کاری مرکزی، جزئیات زمینه‌ای در صورت نیاز و زبان بصری واحد. الهام از الگوهای جاافتادهٔ ابزارهای کاری مانند Linear، Visual Studio Code و GitHub Desktop مجاز است؛ تقلید مستقیم از ظاهر، چیدمان یا برند هیچ‌کدام هدف نیست.

**تصمیم‌های قطعی برای این رودمپ:**

1. **یک بازطراحی یکپارچه، نه وصله‌های متوالی.** پیش از تغییر نماها، معماری اطلاعات، الگوی صفحات، Design Tokens و قراردادهای کامپوننت باید مشخص شوند.
2. **یک Workspace و یک منبع حقیقت.** GUI از Store، Controller و سرویس‌های فعلی استفاده می‌کند؛ منطق Task، وضعیت Workflow، Event، تیم یا Evidence در ویجت‌ها بازنویسی نمی‌شود.
3. **حفظ Tkinter/ttk در این رودمپ.** ADR-007 فناوری فعلی را بر اساس هزینهٔ نصب و اندازه‌گیری‌های ثبت‌شده انتخاب کرده است. مهاجرت به فناوری دیگر خارج از دامنه است، مگر آنکه آزمایش واقعی یک مانع بنیادی و قابل‌اندازه‌گیری را ثابت کند و ADR جدید تصویب شود.
4. **اول رفتار و ساختار، بعد زیبایی بصری.** هیچ مرحله‌ای نباید صرفاً به «ظاهر بهتر شده» استناد کند؛ باید مسئلهٔ UX، شواهد، سناریو و معیار پذیرش داشته باشد.
5. **ساده‌سازی از راه حذف و اولویت‌بندی.** هدف افزودن پنل و کارت بیشتر نیست. قابلیت کم‌استفاده باید به مسیر ثانویه منتقل شود؛ قابلیت ضروری باید در جای پیش‌بینی‌پذیر قرار بگیرد.
6. **هیچ وضعیت ساختگی.** UI نباید فعالیت مدل، تکمیل، انتشار، ارسال پیام یا تأیید صحت را بدون شاهد واقعی نشان دهد. محدودیت ارسال دستی و تأیید کاربر در طراحی بصری هم باید واضح بماند.

## 1. تعریف موفقیت و مسئله‌ای که حل می‌کنیم

### 1.1 مسئلهٔ محصول

AI Workbench یک اپ نمایشی برای نمایش «هوش مصنوعی» نیست؛ یک ابزار کاری برای مدیریت پروژه، Task، حساب/چت دستی، Handoff، پاسخ، اصلاح، Context Request، اعتبارسنجی و تحویل است. پیچیدگی دامنه واقعی است؛ طراحی نباید این پیچیدگی را با حذف نشانه‌های لازم پنهان کند، اما نباید همهٔ جزئیات داخلی را هم‌زمان روی صفحه بریزد.

چالش اصلی UX این است که کاربر گاهی نمی‌داند:

- الان باید پاسخ دریافتی را اصلاح کند، همان Task را ادامه دهد، Task جدید بسازد یا از مدیر پروژه Re-plan بخواهد؛
- کدام خروجی واقعاً دریافت و ثبت شده و کدام مرحله را خودش باید در چت بیرونی انجام دهد؛
- در چت تازه چه Context و فایل‌هایی باید ارسال شوند؛
- کدام وضعیت، ادعای مدل است و کدام مورد با تست، Build، Git یا تأیید کاربر شاهد دارد؛
- برای رسیدن به اقدام لازم باید به کدام نما برود.

بنابراین، «واضح‌شدن قدم بعدی و وضعیت واقعی» معیار اصلی تصمیم‌های طراحی است؛ ظاهر خوشایند بدون حل این مسائل موفقیت محسوب نمی‌شود.

### 1.2 معیارهای نتیجه

پس از پیاده‌سازی، با آزمون سناریوهای واقعی باید نشان داده شود که:

- کاربر تازه‌کار می‌تواند بدون راهنمایی بیرونی پروژه را باز کند و کار بعدی را پیدا کند؛
- کاربر می‌تواند پاسخ ناقص را به مسیر Repair ببرد، بدون اینکه از صفر شروع کند یا Task اشتباه را تغییر دهد؛
- برای ویژگی جدید، مسیرهای «گسترش همین Task / Task جدید / درخواست Re-plan» واضح و بدون تغییر بی‌صدای داده باشد؛
- حالت‌های «پرامپت آماده»، «کپی‌شده»، «کاربر ارسال را تأیید کرده»، «منتظر پاسخ»، «پاسخ دریافت‌شده»، «پاسخ ناقص» و «نیازمند بازبینی» با هم اشتباه نشوند؛
- جزئیات فنی لازم برای کاربر حرفه‌ای قابل دسترسی بمانند، اما پیش‌فرض روزمره را اشغال نکنند؛
- نماها در فارسی RTL و انگلیسی LTR، تم روشن/تاریک، اندازه‌های مختلف پنجره و DPI ویندوز قابل استفاده باشند؛
- هیچ تغییر بصری، رفتار دامنه‌ای یا تاریخچهٔ پروژه را تغییر ندهد.

### 1.3 معیارهای اندازه‌پذیر اولیه

این اعداد هدف اولیه‌اند و پس از ثبت Baseline واقعی نهایی می‌شوند:

| معیار | هدف پذیرش |
|---|---|
| یافتن اقدام بعدی از صفحهٔ اصلی | حداقل 4 نفر از 5 نفر آزمون‌گر، بدون راهنمایی، اقدام درست را در حداکثر 10 ثانیه پیدا کنند. |
| انتخاب مسیر برای پاسخ ناقص | حداقل 4 از 5 نفر، در حداکثر 30 ثانیه، مسیر Repair و پاسخ مربوط را انتخاب کنند. |
| انتخاب مسیر برای قابلیت جدید | حداقل 4 از 5 نفر بتوانند تفاوت سه مسیر را توضیح دهند و انتخاب درست کنند. |
| یافتن وضعیت ارسال دستی | حداقل 4 از 5 نفر تشخیص دهند Workbench پیام را خودش ارسال نکرده است. |
| خطاهای بحرانی استفاده‌پذیری | صفر مورد از دست‌دادن داده، تغییر Task ناخواسته یا برداشت نادرست «ارسال/انتشار/تأییدشده». |
| کنتراست | متن معمولی حداقل 4.5:1؛ متن بزرگ حداقل 3:1، مطابق معیار مناسب WCAG. |
| عملکرد | حفظ هدف فعلی ساخت پنجرهٔ اصلی زیر 500ms روی Baseline هم‌شرایط، مگر با علت اندازه‌گیری‌شده و تصویب‌شده. |
| یکپارچگی بصری | هیچ View توکن رنگ، فاصله، فونت یا شعاع اختصاصی خارج از Design System تعریف نکند، مگر با ثبت استثنا. |

نمونهٔ 5 نفره برای کشف مشکل‌های جدی مفید است، اما معیار آماری عمومی یا اثبات مناسب‌بودن برای تمام کاربران نیست. آزمون باید تکرار شود و با شواهد کیفی همراه باشد.

## 2. تحقیق انجام‌شده و نتایج طراحی

این بخش خروجی تحقیق مقدماتی است؛ قرار نیست چند منبع را کنار هم بگذاریم و از آن‌ها یک ظاهر کلیشه‌ای بسازیم. هر مرجع برای پرسش مشخصی استفاده شده است.

### 2.1 موج تحقیق اول — اصول پایه و الگوهای رابط حرفه‌ای

**پرسش:** چه چیزی باعث می‌شود رابط یک ابزار کاری حرفه‌ای منسجم، قابل اسکن و قابل پیش‌بینی به نظر برسد؟

**یافته‌ها:**

- راهنمای [Apple Human Interface Guidelines — Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars/) تأکید می‌کند Sidebar برای مقصدهای اصلی و سطح بالای ناوبری است؛ سلسله‌مراتب عمیق نباید بدون نیاز در آن فشرده شود و امکان جمع‌کردنش در شرایط مناسب فضای کار را بیشتر می‌کند.
- راهنمای [Apple — Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars/) می‌گوید Toolbar باید کنترل‌ها و عملیات پرتکرار را با انتخاب آگاهانه نگه دارد؛ بارگذاری تعداد زیاد دکمه، تشخیص و فعال‌سازی را دشوار می‌کند.
- [Microsoft Fluent 2 — Layout](https://fluent2.microsoft.design/layout) از فاصله‌گذاری هدفمند، نزدیکی معنایی، سلسله‌مراتب و سازگاری چیدمان با اندازهٔ صفحه دفاع می‌کند. فاصلهٔ بصری صرفاً تزئین نیست؛ به کاربر می‌گوید کدام عناصر با هم ارتباط دارند.
- [Atlassian Design System — Spacing](https://atlassian.design/foundations/spacing) نشان می‌دهد سیستم فاصلهٔ محدود و نام‌گذاری‌شده به ایجاد ریتم و جلوگیری از تنظیمات تصادفی کمک می‌کند.
- [Nielsen Norman Group — 10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) روی مشاهده‌پذیری وضعیت سیستم، هم‌خوانی با زبان کاربر، ثبات، پیشگیری از خطا و کمک به بازیابی تأکید دارد. این‌ها قواعد سرانگشتی برای ارزیابی‌اند، نه جایگزین تست با کاربر.

**نتیجه برای Workbench:** هر صفحه باید یک هدف قابل بیان داشته باشد. سلسله‌مراتب بصری حداکثر چند سطح روشن داشته باشد؛ عنوان، زمینه، اقدام اصلی، محتوای کاری و جزئیات ثانویه نباید همگی وزن بصری یکسان بگیرند. ظاهر باید از فاصله‌ها، تایپوگرافی، ترازبندی و کنترل منطقی وضعیت‌ها کیفیت بگیرد، نه از کارت‌ها و جلوه‌های متعدد.

### 2.2 موج تحقیق دوم — نمونه‌های ابزار کاری و الگوهای جریان کار

**پرسش:** ابزارهایی که کاربر هر روز با آن‌ها کار می‌کند چگونه ناوبری، محتوای اصلی و جزئیات را از هم جدا می‌کنند؟

**مراجع مورد بررسی:**

- [Linear — نمونه‌ها و معرفی رابط](https://linear.app/now/how-we-redesigned-the-linear-ui): چیدمان فشرده اما منظم، رنگ‌های نسبتاً خنثی، تأکید محدود بر وضعیت‌ها و اولویت، و تلاش برای ایجاد ریتم ثابت بین فهرست و جزئیات.
- [GitHub Desktop — راهنمای رابط و گردش کار](https://docs.github.com/en/desktop/overview/creating-your-first-repository-using-github-desktop): وضعیت مخزن و شاخه، تغییرات و تاریخچه در بخش‌های مشخص نمایش داده می‌شوند؛ اقدام وابسته به زمینه است و متن دکمه وضعیت جاری را مشخص می‌کند.
- [Visual Studio Code — ساختار Workbench](https://code.visualstudio.com/docs/getstarted/userinterface): نواحی مشخص برای فعالیت، فهرست/Sidebar، ویرایشگر مرکزی و پنل‌های پشتیبان، همراه با امکان تنظیم فضای کاری.

این اپ‌ها از نظر فناوری و دامنه یکسان نیستند؛ از آن‌ها اصول فضایی و رفتاری می‌گیریم، نه اینکه چیدمانشان را عیناً تکرار کنیم.

**نتیجه برای Workbench:** مدل محتمل، یک فضای کاری ثابت با ناوبری اصلی، ناحیهٔ مرکزی متناسب با کار جاری و پنل جزئیاتِ قابل جمع‌شدن است. جزئیات هر Task باید در همان زمینه قابل دسترسی باشد. عملیات مرتبط با یک ردیف یا مورد در همان زمینه ظاهر شود؛ کاربر را برای هر قدم به صفحه‌ای دور از زمینه نفرستیم.

### 2.3 موج تحقیق سوم — دسترس‌پذیری، وضعیت و طراحی قابل نگهداری

**پرسش:** چطور ظاهر حرفه‌ای در شرایط مختلف حفظ می‌شود و به مجموعه‌ای از استثناهای بی‌قاعده تبدیل نمی‌شود؟

- [Fluent 2 — Design Tokens](https://fluent2.microsoft.design/design-tokens) از توکن‌های معنایی برای رنگ، تایپوگرافی، فاصله و Elevation استفاده می‌کند تا هر View مقادیر دلخواه خودش را اختراع نکند.
- [Fluent 2 — Color](https://fluent2.microsoft.design/color) توصیه می‌کند رنگ برای معنا استفاده شود، اما تنها حامل معنا نباشد؛ متن یا نشانه نیز لازم است.
- [Fluent 2 — Typography](https://fluent2.microsoft.design/typography) سلسله‌مراتب نوشتاری، خوانایی و رعایت جهت مناسب زبان‌های RTL را برجسته می‌کند.
- [W3C — Understanding WCAG 2.2](https://www.w3.org/WAI/WCAG22/Understanding/) معیارهای کنتراست، اندازهٔ هدف، Focus قابل مشاهده، کنترل کیبورد، خطا و پیام وضعیت را تعریف می‌کند.
- [Apple — Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback/) تأکید می‌کند پیام نتیجه و وضعیت باید با اهمیت رخداد متناسب باشد و علت غیرقابل‌انجام‌بودن یک فرمان را توضیح دهد.
- [Figma — Components, styles and shared libraries](https://www.figma.com/best-practices/components-styles-and-shared-libraries/) توضیح می‌دهد که کامپوننت و Style مشترک امکان یک‌بار اصلاح و انتشار ثبات‌مند در بخش‌های متعدد را فراهم می‌کنند.
- [NN/g — Parallel & Iterative Design](https://www.nngroup.com/articles/parallel-and-iterative-design/2011/) از ارزیابی و اصلاح تکرارشوندهٔ نسخه‌های طراحی حمایت می‌کند؛ اما چرخه باید بر شواهد استفاده‌پذیری بنا شود، نه سلیقهٔ روزانه.

**نتیجه برای Workbench:** توکن‌های مرکزی، قرارداد کامپوننت، زبان پیام روشن و مجموعهٔ آزمون ثابت ضروری‌اند. ظاهر قبل از اصلاح تجربهٔ استفاده نهایی نمی‌شود. تم روشن/تاریک، RTL/LTR، مقیاس DPI و وضعیت‌های خطا از ابتدا بخشی از طراحی‌اند، نه کار پایانی.

### 2.4 جمع‌بندی تحقیق: چه چیزی را انتخاب نمی‌کنیم؟

برای جلوگیری از ظاهر کلیشه‌ای یا «AI-made»، موارد زیر پیش‌فرض طراحی نیستند:

- پس‌زمینه‌های گرادیانی، Glow، Glassmorphism، نئون یا انیمیشن تزئینی بدون کارکرد؛
- کارت برای هر شمارنده یا هر قطعهٔ متن؛
- استفاده از رنگ‌های متعدد و Badgeهای رنگی برای جلب توجه به همه‌چیز؛
- عنوان‌های بسیار بزرگ، فضای خالی نمایشی یا Heroهای بازاریابی داخل محیط کاری؛
- آیکون‌های بدون برچسب در عملیات حیاتی؛
- نمایش هر شناسهٔ داخلی، Revision و Evidence در نمای روزمره؛
- چند سبک متفاوت برای دکمه‌ها، Dialogها، فاصله‌ها، گوشه‌ها و وضعیت‌های مشابه؛
- اضافه‌کردن کامپوننت صرفاً برای اینکه صفحه مدرن‌تر «به نظر برسد».

رابط حرفه‌ای لزوماً مینیمالِ خالی نیست؛ به نسبت وظیفه، اطلاعات کافی دارد، ولی برای جلب توجه رقابت غیرضروری راه نمی‌اندازد.

## 3. ممیزی وضعیت فعلی Workbench

### 3.1 آنچه از مخزن تأیید شد

این ممیزی از کد و اسناد شاخهٔ `main` انجام شده؛ ارزیابی بصری کامل روی نسخهٔ نصب‌شده و مانیتور واقعی هنوز باید به‌عنوان کار مرحلهٔ صفر اجرا شود.

- نسخهٔ دسکتاپ موجود `2.6.0` است و پوستهٔ Workspace در `apps/desktop/src/aiwb/workspace/` قرار دارد.
- فناوری رابط Tkinter/ttk است و انتخاب آن در [ADR-007](https://github.com/golshandvr-del/workbench/blob/main/docs/adr/ADR-007-workspace-gui-technology-v2.3.0.md) مستند شده است. در آن سند، وزن نصب/وابستگی و معیارهای عملکرد عامل اصلی حفظ Tkinter بوده‌اند؛ بنابراین این رودمپ مهاجرت Framework را پیش‌فرض نمی‌گیرد.
- پوستهٔ فعلی شامل Project Bar، Sidebar، ناحیهٔ مرکزی، Inspector جمع‌شونده، Next Action و Footer است.
- Sidebar هفت مقصد اصلی دارد: Overview، Timeline، Tasks، Team، Files & Context، Versions & Builds و Settings.
- نوار بالایی به‌طور هم‌زمان انتخاب حالت Simple/Advanced، زبان، تم و کنترل Inspector را در بر دارد.
- توکن‌های فعلی در `theme.py` متمرکزند و Palette روشن/تاریک، فاصله‌ها، اندازهٔ فونت، نقاط شکست و کنتراست را تعریف می‌کنند.
- `WorkspaceController` نماهای Project، Overview، Tasks، Team و سایر بخش‌ها را از کنترلرها و Read Modelهای فعلی تغذیه می‌کند؛ تمایل معماری به جداسازی منطق دامنه از View از قبل وجود دارد.
- اسناد موجود بر شفافیت مراحل ارسال دستی، تفاوت وضعیت گزارش‌شده و وضعیت تأییدشده، RTL/LTR، بازبینی پاسخ و مسیرهای Repair / Task جدید / Re-plan تأکید دارند.
- Release Gate نسخهٔ 2.6.0 آزمون‌های خودکار و GUI smoke را ثبت کرده، اما DPI فیزیکی ویندوز، آزمون دستی دو چت واقعی و Companion روی گوشی واقعی را NOT RUN اعلام کرده است. این موارد را نباید PASS فرض کرد.

### 3.2 فرضیه‌های طراحی که باید آزمایش شوند

این موارد تشخیص قطعی از ظاهر نیستند؛ فرضیه‌هایی‌اند که باید با Screenshot و آزمون کاربر بررسی شوند:

1. **تراکم بالای نوار بالا:** کنترل Mode، Language و Theme شاید برای عملیات روزانه اهمیت یکسان نداشته باشند و بهتر باشد بخشی از آن‌ها به تنظیمات/منوی عمومی منتقل شوند.
2. **اقدام بعدی در تمام صفحات:** یک نوار ثابتِ بزرگ ممکن است به‌جای راهنمایی مفید، فضای عمودی بگیرد یا با اقدام اصلی داخل صفحه رقابت کند. باید نسخهٔ کامل در برابر نسخهٔ جمع‌وجور و زمینه‌محور مقایسه شود.
3. **تعداد مقصدهای اصلی:** هفت گزینه به‌خودی‌خود اشتباه نیست، اما باید بررسی شود که کاربر کدام‌ها را به‌عنوان مقصد مستقل می‌فهمد و کدام‌ها ابزار یا جزئیات یک جریان هستند.
4. **Inspector عمومی:** پنل واحد ممکن است برای خلاصهٔ Task، Event، Agent و Version مناسب نباشد؛ قرارداد آن باید مشخص کند کدام جزئیات و عملیات در هر نوع انتخاب نمایش داده شود.
5. **تفاوت واژگان فنی و زبان کاربر:** Attempt، Handoff، State Revision و Evidence باید به‌اندازهٔ لازم در نمای پیش‌فرض توضیح داده شوند، نه اینکه از UI ناپدید یا بدون توضیح نمایش داده شوند.
6. **ساخت مجدد نما در هر جابه‌جایی:** در `shell.py` نماها هنگام انتخاب صفحه از نو ساخته می‌شوند. مرحلهٔ فنی باید بررسی کند این رفتار به از دست‌رفتن حالت فیلتر، انتخاب یا اسکرول منجر می‌شود یا خیر؛ اصلاح آن فقط بر اساس باگ تأییدشده انجام شود.
7. **خوانایی فونت و کنترل‌ها:** اندازه‌های فعلی توکن‌ها در سورس تعریف شده‌اند، اما مناسب‌بودن واقعی آن‌ها فقط با تست در Windows/DPI و زبان‌های واقعی قابل تأیید است.

### 3.3 اجزایی که نباید دوباره ساخته شوند

پیش از شروع هر View، فهرست قابلیتی باید مشخص کند منطق از کجا خوانده می‌شود. این رودمپ نباید موارد زیر را دوباره پیاده کند:

- Store و State پروژه؛
- وضعیت‌های Task/Workflow، Task graph، Handoff، Attempt و Inbox؛
- Account Profile و Chat Binding؛
- Event Ledger و Timeline Read Model؛
- Team Planner، Proposal و Dashboard؛
- اعتبارسنجی، GitHub/Build و مسیرهای انتشار؛
- Context Request، Repair و خط لولهٔ پاسخ موجود.

اگر View برای تجربهٔ بهتر به Action جدید نیاز دارد، ابتدا قرارداد آن در Controller/Service موجود بررسی می‌شود. تغییرات دامنه‌ای یا Schema تغییر Scope هستند و بدون تصمیم جداگانه وارد رودمپ GUI نمی‌شوند.

## 4. معماری تجربهٔ پیشنهادی

### 4.1 مدل ذهنی

مدل ذهنی پیشنهادی این است: **«انتخاب پروژه → فهم وضعیت → انتخاب کار → انجام قدم بعدی → بازبینی نتیجه»**. جزئیات تیم و تاریخچه به این گردش کار کمک می‌کنند؛ خودشان نباید تبدیل به چند اپ جدا درون یک پنجره شوند.

### 4.2 ساختار کلی Workspace برای نمونه‌سازی

این طرح اولیه برای تست است، نه حکم قطعی دربارهٔ پیکسل نهایی:

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ Project Context: project name · local/GitHub status · project actions        │
├───────────────┬───────────────────────────────────────┬──────────────────────┤
│ Main nav      │ Current view                          │ Context inspector    │
│               │                                       │ (optional/collapsible)│
│ Overview      │ Page title + short purpose            │ Selected item summary│
│ Tasks         │ Primary action (only when relevant)   │ State / references    │
│ Team          │ Work list / form / timeline           │ Relevant next actions │
│ Timeline      │ Empty, loading, error and success      │ Advanced details      │
│ Files/Context │ states                                 │                      │
│ Deliveries    │                                       │                      │
│               │                                       │                      │
│ Settings      │                                       │                      │
├───────────────┴───────────────────────────────────────┴──────────────────────┤
│ Compact status line: local state / sync / last meaningful result             │
└──────────────────────────────────────────────────────────────────────────────┘
```

**قواعد ساختار:**

- Project Bar باید هویت پروژه و وضعیت‌های عمومی مهم را نشان دهد؛ کنترل‌های کم‌کاربرد داخل آن انباشته نشوند.
- Sidebar فقط مقصدهای سطح اول را دارد و نباید به درختی عمیق از زیرمنوها تبدیل شود.
- فضای مرکزی محل اصلی انجام کار است؛ پهنای آن نباید به‌خاطر پنل‌های همیشه‌باز بی‌دلیل کم شود.
- Inspector فقط وقتی ارزش افزوده دارد باز می‌ماند؛ جزئیات باید نسبت به مورد انتخاب‌شده تغییر کنند.
- Status line برای وضعیت کلی کم‌مزاحمت است؛ اعلان‌های مهم یا خطا نباید در Footer ریز و دور از زمینه دفن شوند.
- Next Action نباید به نوار تبلیغاتی همیشگی تبدیل شود. جای آن بر اساس نتیجهٔ آزمایش می‌تواند یک ردیف باریک در صفحهٔ Overview، یک اقدام اصلی در صفحهٔ مربوط یا یک مورد اولویت‌دار در Needs Attention باشد.

### 4.3 معماری اطلاعات اولیه

برای نمونهٔ اول این گروه‌بندی پیشنهاد می‌شود؛ نام و دسته‌بندی نهایی پس از تست تأیید خواهد شد:

| مقصد پیشنهادی | هدف کاربر | چیزهایی که در آن متعلق‌اند |
|---|---|---|
| Overview | «الان در چه وضعیتی هستم و قدم بعدی چیست؟» | وضعیت واقعی پروژه، اقدام بعدی، موارد نیازمند اقدام، خلاصهٔ پیشرفت و فعالیت اخیر منتخب |
| Tasks | «چه کاری باید انجام/بررسی/اصلاح کنم؟» | فهرست Task، جزئیات، مالک، وابستگی، Attempt/Handoff، پاسخ، Repair و تغییر Scope |
| Team | «چه نقش‌ها و چت‌های دستی دارم و هرکدام به چه چیزی متصل‌اند؟» | Agent/Role، Account Profile، Chat Binding، آمادگی شروع و Team Proposal |
| Timeline | «چه رخ داده و ترتیب وقایع چه بوده؟» | Event history، فیلتر، Milestone و ردیابی وضعیت‌ها؛ بدون ساخت رویداد از تغییر View |
| Files & Context | «چه فایل یا زمینه‌ای باید بررسی/آماده شود؟» | Context Request، بستهٔ زمینه، ورودی/خروجی پاسخ و مسیرهای فایل موجود |
| Deliveries | «چه چیزی Build/اعتبارسنجی/انتشار شده و شاهدش چیست؟» | Build، Version، Artifact، وضعیت Release و شواهد مرتبط |
| Settings | «ترجیحات رابط و تنظیمات عمومی کجاست؟» | Theme، زبان، تنظیمات نمایش، ابزارهای تخصصی و تنظیمات موجود |

این جدول یک **پیشنهاد بازطراحی** است. ممکن است بخشی از Files & Context یا Deliveries در مدل موجود با دیالوگ/ابزار کلاسیک مشترک باشد؛ در این صورت رابط جدید باید آن مسیر را به‌صورت روشن باز کند، نه اینکه نسخهٔ دوم و ناسازگار بسازد.

### 4.4 الگوی صفحات

هر صفحه باید بر اساس همین قرارداد طراحی شود:

1. عنوان واقعی صفحه و یک جملهٔ کوتاه که هدف آن را روشن کند، در جایی که نام صفحه به‌تنهایی کافی نیست؛
2. یک اقدام اصلی حداکثر، آن هم فقط وقتی واقعاً اقدام غالب همان صفحه است؛
3. فیلترها و عملیات ثانویه در ناحیهٔ مشخص و پایدار؛
4. محتوای اصلی با سلسله‌مراتب قابل اسکن؛
5. حالت‌های خالی، بارگذاری، نتیجه، خطا و عدم دسترسی که برای همان محتوا طراحی شده‌اند؛
6. جزئیات مورد منتخب در Inspector یا صفحهٔ جزئیات؛
7. راه بازگشت/انصراف و اثر اقدام، متناسب با ریسک آن.

نباید هر صفحه را با کارت‌های یکسان پر کرد. جدول برای مقایسهٔ سطرها، فهرست برای پیمایش، فرم برای ورود داده، Timeline برای توالی زمانی، و Detail panel برای زمینهٔ انتخاب‌شده انتخاب مناسب‌تری‌اند؛ نوع نمایش از خود کار و داده تعیین می‌شود.

## 5. رودمپ اجرایی مرحله‌به‌مرحله

ترتیب زیر وابستگی دارد. مرحلهٔ بعد بدون عبور از Gate مرحلهٔ قبلی آغاز نمی‌شود، مگر با تصمیم مکتوب و علت مشخص. شماره‌گذاری نسخهٔ انتشار در اختیار فرآیند Release مخزن است؛ شماره‌های این سند، مرحله‌های طراحی و اجرا هستند نه تضمین نسخهٔ نرم‌افزار.

### مرحلهٔ 0 — تثبیت محدوده و ثبت Baseline

**هدف:** جلوگیری از شروع شتاب‌زدهٔ کدنویسی و تفکیک مشکل بصری از مشکل رفتار.

**کارها:**

- اجرای نسخهٔ `2.6.0` از یک نصب تمیز و ثبت اندازهٔ پنجره، تم، زبان، DPI و وضعیت پروژه برای هر Screenshot؛
- تهیهٔ Screenshot از تمام نماهای اصلی در حالت عادی، با دادهٔ واقعی/ساختگی مشخص‌شده، با انتخاب یک مورد و بدون انتخاب؛
- تهیهٔ فهرست تمام دکمه‌ها، منوها، پنل‌ها، Dialogها و مسیرهای قدیمی که از Workspace باز می‌شوند؛
- ثبت مشکلات به چهار دسته: IA/UX، Visual hierarchy، Component consistency، Responsive/Accessibility؛
- ثبت Baseline عملکرد با اسکریپت موجود؛ ثبت حداقل زمان شروع/بازکردن پروژه و رفتار پیمایش در مجموعه‌دادهٔ بزرگ؛
- ثبت فهرست «نباید تغییر کند»: Schema، State، رفتار workflow، ذخیره‌سازی، Git/Build، Installer و مسیرهای دستی تعامل با مدل.

**خروجی‌ها:** `GUI_AUDIT_FA.md`، مجموعه Screenshot دارای نام/شرایط ثابت، فهرست اجزای موجود، ماتریس مسیرهای کاربر و Baseline.

**Gate 0:** هر مشکلِ درج‌شده دارای مدرک، اثر بر کاربر و اولویت باشد. هیچ تغییر کد بصری هنوز آغاز نشده باشد.

### مرحلهٔ 1 — تحقیق و بنچمارک طراحی، موج اول

**هدف:** اصول طراحی را به تصمیم‌های روشن مرتبط با Workbench تبدیل کنیم؛ از moodboard صرف فراتر برویم.

**کارها:**

- گردآوری 3 تا 5 مرجع با دامنهٔ متفاوت: یک محیط توسعه (VS Code)، ابزار تغییرات/تاریخچه (GitHub Desktop)، ابزار مدیریت کار (Linear) و دو راهنمای سیستم طراحی رسمی؛
- برای هر مرجع، فقط الگوهای هدفمند بررسی شوند: Main navigation، Page title، toolbar، split view، list/detail، وضعیت و خطا، empty state، command hierarchy، typography، density؛
- ثبت «چه چیزی خوب کار می‌کند»، «چه چیزی برای Workbench نامناسب است» و «چرا»؛
- تهیهٔ Pattern board بدون کپی رنگ/برند: الگوهای ساختاری، فاصله، سلسله‌مراتب، نمایش جزئیات، حالت‌های خطا؛
- مرور 10 Heuristic کاربردپذیری و WCAG 2.2 به‌عنوان معیار ارزیابی اولیه.

**خروجی‌ها:** `GUI_RESEARCH_FA.md`، Pattern board و جدول منبع ← اصل ← کاربرد احتمالی در Workbench.

**Gate 1:** حداقل 8 اصل کاربردی و حداکثر 5 ضدالگوی مشخص برای پروژه نوشته شده باشد؛ هیچ تصمیم بصری مهم صرفاً با عبارت «مدرن‌تر است» توجیه نشود.

### مرحلهٔ 2 — تحقیق UX و معماری اطلاعات، موج دوم

**هدف:** مشخص‌کردن اینکه کاربر برای کار واقعی کجا می‌رود و چه چیزی را در هر لحظه باید ببیند.

**سناریوهای اجباری:**

1. اولین بازکردن پروژه و یافتن اقدام بعدی؛
2. آماده‌کردن Prompt، کپی‌کردن آن و تشخیص روشن اینکه هنوز ارسال نشده؛
3. تأیید دستی ارسال و بازگشت با پاسخ از یک چت مستقل؛
4. دریافت پاسخ ناقص/نامعتبر و شروع Repair بدون از دست دادن پاسخ/Attempt قبلی؛
5. اضافه‌کردن قابلیت جدید و تصمیم بین ادامهٔ Task، Task جدید یا Re-plan؛
6. پاسخ مدل که Context Request دارد؛ تشخیص فایل/خطوط درخواستی و آماده‌سازی بسته؛
7. بازبینی پیشنهاد Team Planner و پذیرش کل/انتخابی/رد؛
8. تشخیص مورد نیازمند اقدام در پروژه‌ای با 7 تا 10 Agent؛
9. بررسی اینکه Build/Version واقعاً با چه شاهدی ثبت شده است؛
10. بررسی فعالیت گذشته و تشخیص رویداد واقعی از اطلاعات legacy/گزارش‌شده.

**کارها:**

- ترسیم جریان وظیفه (Task flows) از شروع تا نتیجه، با نقاط تصمیم و مسیر خطا؛
- ترسیم معماری اطلاعات پیشنهادی و مسئولیت هر View؛
- برای هر عنصر مشخص‌کردن «لازم در لحظه / لازم در صورت انتخاب / پیشرفته / غیرضروری»؛
- تدوین واژه‌نامهٔ UI فارسی/انگلیسی با معادل‌های ساده و قاعدهٔ حفظ شناسه‌های فنی؛
- ساخت دو الگوی رقیب فقط برای تصمیم‌های پرریسک، نه ده‌ها گزینهٔ تزئینی: مثلاً نوار اقدام دائمی در برابر اقدام زمینه‌ای، و Inspector ثابت در برابر نمایش جزئیات در همان صفحه؛
- آزمون کاغذی یا Clickable prototype کم‌جزئیات با سناریوهای بخش بالا پیش از کدنویسی.

**خروجی‌ها:** نقشهٔ اطلاعات، 10 جریان کاری، واژه‌نامهٔ UI و نتیجهٔ آزمون نمونهٔ اولیه.

**Gate 2:** یک مسیر واحد برای هر سناریو یا دلیل روشن برای چند مسیر تأیید شده باشد. تعارض‌های «کدام View صاحب این قابلیت است؟» حل شده باشد.

### مرحلهٔ 3 — نمونه‌سازی ساختاری و انتخاب چیدمان

**هدف:** ساختار و سلسله‌مراتب را پیش از انتخاب رنگ و پرداخت بصری تثبیت کنیم.

**کارها:**

- آماده‌سازی Wireframe برای Overview، Tasks، Task detail/Repair، Team، Timeline، Files & Context، Deliveries و Settings؛
- طراحی سه سطح عرض پنجره: عریض، معمولی و محدود؛ در عرض محدود صرفاً فشرده‌کردن هرچیز کافی نیست، اولویت و محل پنل‌ها باید تغییر کند؛
- مقایسهٔ دو نسخه از Project Bar و Next Action؛
- مشخص‌کردن اندازهٔ Sidebar و Inspector، نحوهٔ جمع‌شدن، حفظ انتخاب و بازگشت از پنل؛
- تعریف تعامل لیست/جزئیات: انتخاب سطر، Inspector، دوبارکلیک، بازکردن جزئیات و برگشت؛
- طراحی موارد فاقد داده، نتیجهٔ موفق، خطا، وضعیت انتظار و وضعیت بدون امکان اقدام؛
- بازبینی با آزمون وظیفه، نه رأی‌گیری دربارهٔ سلیقهٔ رنگ.

**خروجی‌ها:** Wireframe قابل مقایسه، پروتوتایپ قابل پیمایش و Decision log برای Layout.

**Gate 3:** ساختار صفحه، مقصدهای اصلی و مسیرهای سناریویی تأیید شده باشند. تغییر IA پس از این Gate فقط با شواهد تست یا کشف تعارض دامنه‌ای مجاز است.

### مرحلهٔ 4 — موج تحقیق نهایی و طراحی بصری پایه

**هدف:** تبدیل ساختار تأییدشده به زبانی بصری واحد که در کل اپ دوام بیاورد.

**کارها:**

- انتخاب یک جهت بصری مشخص: ابزار کاری خنثی و دقیق، نه داشبورد بازاریابی؛
- تعریف Design Tokens معنایی برای سطوح، متن، Border، انتخاب، Focus، Primary action، وضعیت موفق/خطا/هشدار/اطلاع؛
- تعریف مقیاس فاصله، مقیاس تایپوگرافی و Line-height، اندازهٔ کنترل، ارتفاع ردیف، شعاع گوشه و Border؛
- محدودکردن رنگ تأکیدی به یک خانوادهٔ اصلی؛ رنگ Status فقط برای وضعیت واقعی و با متن/نشانهٔ مکمل؛
- تعریف آیکون‌نگاری یکدست و تعیین اینکه کجا آیکون به‌تنهایی مجاز نیست؛
- تعیین رفتار Light/Dark با توکن‌های معنایی، نه Paletteهای پراکنده و hard-coded؛
- تعریف الگوی Focus، Hover، Selected، Disabled، Busy و Error؛
- بررسی فونت روی Windows و فارسی؛ ترتیب خواندن RTL، هم‌ترازی، عدد/شناسه و متن ترکیبی فارسی/انگلیسی؛
- مقایسهٔ UI در سطح خاکستری (بدون رنگ) برای تأیید Hierarchy و سپس افزودن رنگ؛
- ایجاد صفحهٔ Design System/Component catalogue با مثال درست و نادرست.

**خروجی‌ها:** `GUI_DESIGN_SYSTEM_FA.md`، Design tokens اولیه، نمونه‌های Hi-Fi برای صفحات کلیدی، و فهرست کامپوننت‌های مشترک.

**Gate 4:** همهٔ صفحات اصلی با همان سیستم قابل ساخت باشند. هیچ View نباید برای خوانایی یا جلب‌توجه به ترفندهای بصری خاص خودش نیاز داشته باشد.

### مرحلهٔ 5 — ساخت هستهٔ بصری و کامپوننت‌های مشترک

**هدف:** یک‌بار ساختن پایه‌هایی که تمام نماها از آن استفاده کنند.

**کارها:**

- بازطراحی Project Bar، Main Navigation، Workspace frame، Inspector، Status line و صفحهٔ عنوان؛
- ساخت مؤلفه‌های مشترک Button (Primary/Secondary/Quiet/Danger)، Field، Dropdown، Table/List row، Filter, Tabs، Empty state، Inline feedback، Dialog و Confirm pattern؛
- تعریف قواعد فاصله/اندازه و State برای هر کامپوننت؛
- فراهم‌کردن مسیرهای کیبورد، Tab order و Focus آشکار؛
- متمرکزکردن Tokenها در `theme.py` یا ماژول طراحی مجاز در همان معماری؛ Viewها نباید رنگ، فونت یا اندازهٔ دلخواه تعریف کنند؛
- جداسازی متن‌های UI از ساختار چیدمان برای حفظ i18n و RTL/LTR؛
- تعریف قرارداد Inspector بر اساس نوع مورد انتخاب‌شده، بدون شرط‌های پراکنده در هر صفحه؛
- نوشتن تست برای Tokenها، کنتراست، Layout breakpoints و رفتارهای انتخاب/جمع‌شدن.

**خروجی‌ها:** پوستهٔ تازهٔ Workspace و Component gallery کوچک برای بررسی بصری.

**Gate 5:** دو View متفاوت باید بتوانند با همان کامپوننت‌ها و بدون ساختن Style موازی ساخته شوند. اگر هر View سبک جداگانه می‌خواهد، سیستم هنوز کامل نیست.

### مرحلهٔ 6 — بازطراحی نماهای اصلی، به ترتیب اهمیت کاربر

**هدف:** بازطراحی تجربهٔ کار به‌صورت جریان منسجم، نه تبدیل هر صفحه به پروژه‌ای جدا.

**ترتیب پیشنهادی:**

**6A — Overview و Needs Attention**

- به‌جای اعداد نمایشی زیاد، خلاصهٔ واقعی و چند مورد مهم نشان داده شود؛
- فقط یک مورد بالاترین اولویت به‌صورت پررنگ مطرح شود، بقیه در فهرست قابل اسکن؛
- هر ردیف بگوید «چه اتفاقی افتاده»، «چرا توجه لازم است» و «گام بعدی چیست»؛
- وضعیت‌های عادی در صف اضطراری شلوغ نشوند؛ موارد اطلاع‌رسانی از اقدام فوری جدا بمانند.

**6B — Tasks و Detail/Repair**

- شناسه، عنوان، وضعیت انسانی، مالک، وابستگی و اقدام معتبر در الگوی ثابت نمایش داده شوند؛
- مهم‌ترین اطلاعات برای تصمیم اولیه در نمای پیش‌فرض بماند و Attempt ID/Revision/Evidence در جزئیات ثانویه در دسترس باشد؛
- پاسخ سالم، ناقص، قدیمی یا نامرتبط از هم قابل تشخیص باشد؛
- Repair نزدیک به پاسخ و Task منبع قرار بگیرد؛ انتخاب اشتباه Task خطرناک باید سخت باشد؛
- مسیر Task جدید و Re-plan از مسیر اصلاح همان Task متمایز و قابل فهم بماند.

**6C — Team و Account/Chat binding**

- نقش Agent، منبع Account Profile، نام Chat، تعداد Taskهای باز و آمادگی شروع به‌صورت یک رابطهٔ واضح دیده شوند؛
- حساب/چت صرفاً برچسب نمایشی تلقی نشود؛ کمبود Binding و علت عدم آمادگی مشخص باشد؛
- اصطلاحات «Agent نقش است»، «Account Profile منبع کاربراظهاری است» و «Chat Binding یادداشت اتصال دستی است» در جزئیات قابل فهم باشند؛
- بازبینی Team Proposal از حالت نمایش متن خام به مرور ساختاریافتهٔ تغییرات برسد، ولی منطق پذیرش/رد موجود را دوباره پیاده نکند.

**6D — Timeline و Deliveries**

- Timeline برای توالی زمانی و فیلتر مناسب باشد، نه صفحه‌ای متراکم از همهٔ جزئیات؛
- Eventها دارای زمان/منبع/نوع/مرجع روشن باشند؛ تغییر View رویداد جدید نسازد؛
- Milestone، Version، Commit، Build Run و Artifact از هم متمایز بمانند؛
- «Released» با متن واردشدهٔ کاربر به‌تنهایی به رنگ سبز یا وضعیت قطعی تبدیل نشود؛ UI باید دقیقاً منبع/سطح تأیید موجود را منعکس کند.

**6E — Files & Context و Settings**

- Context Request باید فایل، مسیر/بازهٔ خطوط، علت اعلام‌شده و وضعیت بستهٔ آماده‌شده را روشن کند؛
- UI باید صریحاً بین «آماده شد» و «به چت ارسال شد» تفاوت بگذارد؛
- Settings مقصدی برای ترجیحات و ابزارهای کم‌کاربرد باشد؛ نباید عملیات روزانه را پنهان کند.

**قواعد مشترک:**

- برای هر View، حالت Empty/Loading/Success/Error/Disabled/Long-content طراحی و تست شود.
- هیچ متن کمکی برای توضیح رفتار، قانون دامنه‌ای تازه اختراع نکند.
- اگر عملیات در ابزار کلاسیک فعلی اجرا می‌شود، انتقال کاربر با نام و نتیجهٔ مشخص باشد و نسخهٔ دوم از همان عملیات ساخته نشود.

**خروجی‌ها:** نماهای بازطراحی‌شده، نقشهٔ اتصال View به Controller/Service و تست‌های GUI مرتبط.

**Gate 6:** تمام سناریوهای اصلی از اول تا آخر با نماهای یکپارچه اجرا شوند؛ هیچ مسیر پرتکرار فقط با ترکیب پنجره‌ها یا راهنمای شفاهی قابل استفاده نباشد.

### مرحلهٔ 7 — Responsive، RTL/LTR، Accessibility و حالت‌های مرزی

**هدف:** ظاهر فقط در Screenshot عریض و شرایط ایده‌آل خوب نباشد.

**کارها:**

- تست عرض‌های `1024×640`، `1280×720`، `1366×768` و `1920×1080` و اندازهٔ نزدیک حداقل پنجره؛
- تست DPI ویندوز `100%`، `125%`، `150%` و `200%`؛ در صورت امکان جابه‌جایی بین دو مانیتور با DPI متفاوت؛
- بررسی پنجرهٔ Maximized، پنجرهٔ قابل تغییر اندازه، Taskbar در بالا/پایین و جابه‌جایی به مانیتور دوم؛
- تست واقعی فارسی RTL، انگلیسی LTR و متن ترکیبی فارسی/انگلیسی، شناسه‌های لاتین، مسیر فایل، URL و نام‌های بسیار بلند؛
- تست Tab/Shift+Tab، Focus قابل مشاهده، فعال‌سازی کیبورد، باز/بسته‌کردن Sidebar و Inspector؛
- کنتراست تمام ترکیب‌های متن/پس‌زمینه و State؛ رنگ تنها علامت وضعیت نباشد؛
- بررسی متن‌های بریده، کنترل‌های کوچک، Tooltipهای گمراه‌کننده و افقی‌شدن اسکرول ناخواسته؛
- تست با دادهٔ زیاد: 200 Task و 2000 Event یا Dataset مرجع نزدیک آن؛
- ثبت اسکرین‌شات قبل/بعد در تم روشن و تاریک، با Layout مشخص.

**خروجی‌ها:** ماتریس QA دسکتاپ، ایرادهای اصلاح‌شده، نتایج تست کنتراست و گزارش DPI ویندوز.

**Gate 7:** تمام مسیرهای اصلی در محدودهٔ هدف دسترس‌پذیر باشند؛ هیچ اقدام اصلی به‌خاطر عرض/ارتفاع/RTL/DPI پنهان یا غیرقابل فعال‌سازی نشود. اگر محیط فیزیکی در دسترس نیست، مورد باید NOT RUN بماند.

### مرحلهٔ 8 — ارزیابی استفاده‌پذیری و بازنگری نهایی

**هدف:** بازبینی رودمپ و خود پیاده‌سازی با معیار واقعی؛ نه تأیید بر اساس پسند شخصی سازنده.

**کارها:**

- اجرای تست وظیفه با حداقل 5 نفر/جلسهٔ مستقل یا چند دور با کاربران هدف؛ اگر فقط مالک محصول در دسترس است، تست اکتشافی با خود مالک انجام شود اما نتیجه به‌عنوان تست مستقل کاربر ثبت نشود؛
- آزمون همان 10 سناریوی بخش 2؛ ناظر از راهنمایی یا توضیح‌دادن در حین کار خودداری کند؛
- ثبت زمان تکمیل، خطاها، مسیرهای اشتباه، مکث‌ها و جایی که کاربر به توضیح بیرونی نیاز دارد؛
- هر مشکل بر اساس Severity رتبه‌بندی شود: Critical (تغییر/برداشت خطرناک)، Major (بن‌بست یا اشتباه مهم)، Moderate (اصطکاک قابل توجه)، Minor (پولیش)؛
- دست‌کم دو دور اصلاح با تست مجدد انجام شود: دور اول برای مشکلات IA/Flow و دور دوم برای جزئیات و ثبات بصری؛
- ممیزی همهٔ Viewها از حیث توکن‌ها و کامپوننت مشترک؛
- جست‌وجوی استثناهای تک‌موردی و حذف یا مستندکردن همهٔ آن‌ها؛
- ثبت موارد حل‌نشده و علت پذیرش/تعویق.

**خروجی‌ها:** گزارش UX test، لیست نهایی مشکلات، Screenshot نهایی، Design system پایدار و Release Gate GUI.

**Gate 8:** هیچ مشکل Critical یا Major حل‌نشده‌ای در مسیر اصلی باقی نماند؛ تمام موارد NOT RUN و محدودیت‌های تست صریحاً گزارش شوند.

### مرحلهٔ 9 — یکپارچه‌سازی و انتشار کنترل‌شده

**هدف:** عرضهٔ GUI یکپارچه به‌گونه‌ای که کاربر بتواند به نسخهٔ قبلی برگردد یا مشکل را دقیق گزارش کند.

**کارها:**

- ادغام بازطراحی در یک مسیر اصلی Workspace و حذف Viewهای آزمایشی/موازی پس از تأیید اتصال همهٔ عملیات؛
- حفظ سازگاری داده و تنظیمات کاربر؛ تغییر View یا Theme نباید State پروژه یا Event بسازد؛
- اجرای تست‌های regression، GUI smoke، installer clean-install و upgrade مطابق خط لولهٔ فعلی؛
- اجرای تست با پروژهٔ موجود از نسخهٔ قبلی و پروژهٔ تازه؛
- تهیهٔ Release Notes با فهرست رفتارهای تغییریافته، مسیرهای جابه‌جاشده و محدودیت‌های شناخته‌شده؛
- ثبت راه Rollback مطابق سیاست مخزن؛
- انتشار مرحله‌ای: داخلی/آزمایشی، تأیید Gate، سپس Release عمومی.

**Gate 9:** CI لازم سبز، آزمون مسیرهای اصلی کامل، دادهٔ قبلی سالم، موارد NOT RUN علامت‌گذاری و Release Gate امضا شده باشد.

## 6. مشخصات Design System موردنیاز

### 6.1 اصول بصری

- **Neutral first:** بخش عمدهٔ UI از سطوح خنثی، متن خوانا و مرزبندی ظریف ساخته شود.
- **One clear accent:** رنگ تأکیدی اصلی برای انتخاب جاری و عمل اصلی؛ نه برای همهٔ عناصر قابل کلیک.
- **Meaningful status colors:** رنگ موفق/هشدار/خطا/اطلاع تنها در زمینهٔ معنایی مناسب استفاده شود و با متن/نشان همراه باشد.
- **Typography does the hierarchy:** اهمیت با اندازه/وزن/فاصلهٔ متن و محل قرارگیری مشخص شود؛ نه اینکه همه چیز داخل کارت رنگی برود.
- **Consistent density:** فاصله و ارتفاع ردیف‌ها در صفحات هم‌نوع ثابت باشد؛ صفحات جدول‌محور به‌طور غیرضروری هوادار و بزرگ نشوند.
- **Motion is functional:** انیمیشن فقط وقتی بازخورد یا رابطهٔ فضایی را روشن می‌کند؛ هیچ افکت تزئینی اجباری نیست.
- **No visual competition:** هر صفحه یک نقطهٔ تمرکز غالب داشته باشد؛ اگر همه چیز برجسته است، چیزی برجسته نیست.

### 6.2 توکن‌های لازم

| گروه | توکن‌های لازم | قاعده |
|---|---|---|
| Color | background, surface, elevated surface, text, muted text, border, divider, selected, focus, accent, success, warning, danger, info | مقدار خام در View ممنوع؛ نام توکن معنایی باید استفاده شود. |
| Type | page title, section title, body, secondary, caption, numeric/status, code/ID | اندازه و وزن محدود؛ متن عادی خوانا باشد؛ شناسه و متن معمولی از هم قابل تشخیص باشند. |
| Spacing | 0, 1, 2, 3, 4, 6, 8 واحد پایه (مقیاس دقیق پس از تست) | فقط از مقیاس تعریف‌شده استفاده شود؛ فاصلهٔ تصادفی نیاز به دلیل دارد. |
| Shape | radius کوچک/متوسط، border width، divider | شعاع و Border در کل برنامه ثابت و متناسب با کاربرد باشند؛ کارت‌سازی افراطی ممنوع. |
| Control | ارتفاع و padding دکمه/فیلد، row height، اندازهٔ هدف کیبورد/ماوس | خوانایی و DPI بر فشرده‌سازی صرف اولویت دارند. |
| Layout | Sidebar width, Inspector width, content min width, breakpoint rules | رفتار در resize بر اساس فضای واقعی تعریف شود؛ اندازهٔ ثابت تنها راه نیست. |
| Feedback | inline info, success, warning, error, confirmation, destructive dialog | شدت بازخورد با اهمیت پیام متناسب باشد. |
| State | default, hover, focus, selected, disabled, busy, invalid | هر کنترل تعاملی باید حالت‌های لازم را طراحی و تست کند. |

این جدول **نام‌گذاری مفهومی** است، نه مقدار عددی نهایی. مقادیر باید در نمونهٔ Hi-Fi، روی نمایشگر واقعی و در تم‌ها آزمایش شوند و سپس تثبیت شوند.

### 6.3 Button hierarchy

هر صفحه حداکثر یک Primary action داشته باشد مگر آنکه الگوی تخصصی با توجیه روشن نیاز دیگری داشته باشد. نوع‌های عمومی:

- **Primary:** اقدام اصلیِ معتبر در وضعیت فعلی؛
- **Secondary:** اقدام مهم اما غیرغالب؛
- **Quiet/Ghost:** ابزار کم‌وزن یا اقدام ردیفی؛
- **Destructive:** حذف/رد غیرقابل‌برگشت یا عملیات پرخطر؛ با زمینه و تأیید مناسب؛
- **Disabled with reason:** فقط اگر نشان‌دادن قابلیت آینده یا علت عدم آمادگی ارزش داشته باشد؛ در غیر این صورت اصلاً نشان داده نشود.

متن دکمه باید نتیجه را مشخص کند؛ «ادامه» یا «انجام بده» در جایی که منظور می‌تواند مبهم باشد کافی نیست. برای مثال: «ساخت پرامپت اصلاح»، «آماده‌سازی بستهٔ زمینه» و «بازبینی پاسخ» اطلاعات بیشتری منتقل می‌کنند. اگر طول متن زیاد است، برچسب کوتاه و توضیح زمینه‌ای باید مشخص باشد.

### 6.4 Language & content design

- متن کوتاه، مستقیم و بدون jargon غیرضروری باشد.
- اصطلاح فنی وقتی لازم است حفظ می‌شود، اما نخستین ظهور آن توضیح ساده دارد.
- خطا با چهار بخش طراحی شود: چه اتفاقی افتاد، اثر چه بود، چه چیزی حفظ شد، کاربر چه کاری می‌تواند انجام دهد.
- وضعیت بیرونی باید منبع خود را نشان دهد: «تأییدشده توسط کاربر»، «از GitHub دریافت شد»، «گزارش‌شده»، «هنوز بررسی نشده»؛ زبان UI نباید گواهی جعلی تولید کند.
- فارسی و انگلیسی باید متن واقعی داشته باشند، نه ترجمهٔ کوتاه‌شده یا جایگزین انگلیسی در نسخهٔ فارسی.
- شناسه‌ها، pathها، URLها و متن ترکیبی در RTL باید با ترتیب خواندن درست نمایش داده شوند.

## 7. قواعد جلوگیری از وصله‌پینه و «ظاهر ساخته‌شده با AI»

این بخش یکی از دروازه‌های اصلی پروژه است. هر PR مربوط به GUI باید با آن سنجیده شود.

### 7.1 قواعد سفت‌وسخت

1. تغییر بصری باید به Issue/تصمیم مشخص در رودمپ وصل باشد؛ «چون قشنگ‌تر است» دلیل کافی نیست.
2. پیش از ساخت کامپوننت جدید، جست‌وجو شود آیا نمونهٔ موجود قابل تعمیم است.
3. رنگ/فونت/فاصله/Border radius در View hard-code نشود.
4. یک الگوی تکرارشونده در یک PR جداگانه و با تست نمونه ساخته شود، سپس به نماها تعمیم یابد.
5. تغییر ساختاری بزرگ با پولیش‌های کوچک نامرتبط در یک PR مخلوط نشود.
6. در هر PR Screenshot قبل/بعد برای صفحات متأثر و فهرست رفتارهای مورد انتظار ضمیمه شود.
7. هر استثنای Design System باید دلیل، محدوده، تاریخ بازبینی و مالک داشته باشد؛ استثناهای بی‌مالک بعد از انتشار حذف شوند.
8. کپی/پیست ویجت با چند Style متفاوت ممنوع است؛ Component یا helper مشترک ترجیح دارد.
9. برای افزودن Badge، Card، Icon یا رنگ تازه باید یک ضرورت تعاملی/اطلاعاتی قابل توضیح وجود داشته باشد.
10. پیش از تغییر صفحهٔ دیگر، همهٔ موارد هم‌نوع بررسی شوند تا دوباره‌کاری در چند مرحله پخش نشود.

### 7.2 علائم هشدار در Code Review

PR باید بازنگری شود اگر:

- هر View رنگ یا فاصلهٔ منحصربه‌فردی ساخته که توکن موجود پوشش می‌دهد؛
- دکمه‌های Primary در یک صفحه زیاد شده‌اند و سلسله‌مراتب ندارند؛
- برای هر پیام یک باکس/Badge جدید ساخته شده؛
- متن و آیکون بدون الگوی ترازبندی ثابت جابه‌جا شده‌اند؛
- کنترل‌های Language/Theme/Mode در چند محل تکرار شده‌اند؛
- رفتار RTL با شرط‌های پراکنده و پرش‌های بصری اصلاح شده؛
- Dialog به‌جای رفع مشکل جریان کار اضافه شده؛
- UI وضعیت مدل/چت/Build را بیش از شواهد نشان می‌دهد؛
- تغییر UI به وضعیت Task یا تاریخچهٔ Event ناخواسته اثر می‌گذارد.

### 7.3 قرارداد PR مربوط به UI

هر Pull Request باید شامل این موارد باشد:

- مرحله و معیار پذیرش مرجع در رودمپ؛
- مشکل کاربر و تصمیم طراحی؛
- Screenshot قبل/بعد یا Wireframe برای تغییر ساختاری؛
- فهرست نماها و کامپوننت‌های متأثر؛
- تست GUI و سناریوی دستی؛
- بررسی فارسی RTL، انگلیسی LTR و تم روشن/تاریک متناسب با دامنهٔ تغییر؛
- تأیید اینکه Domain State، Event Ledger و دادهٔ ذخیره‌شده تغییر نکرده‌اند، مگر در محدودهٔ جداگانهٔ مصوب.

## 8. معماری فنی اجرای GUI

### 8.1 مرزبندی

- `WorkspaceWindow` و Viewها مسئول ارائه، چیدمان و دریافت ورودی هستند.
- `WorkspaceController` مسئول آماده‌سازی داده برای UI و هماهنگ‌کردن Actionها از مسیر سرویس‌های موجود است.
- V2 Store/Service/Read Model مرجع منطق دامنه می‌ماند.
- Tokenهای طراحی در یک منبع مرکزی نگهداری می‌شوند؛ Viewها مقدار بصری جدید اختراع نمی‌کنند.
- ترجمه و جهت متن از ماژول i18n و قواعد RTL/LTR تبعیت می‌کند.
- تنظیم ترجیحات نمایش در فایل UI/preferences موجود می‌ماند، نه در State پروژه.
- تغییر صفحه، بازکردن Inspector یا تعویض Theme نباید Revision یا Event دامنه ایجاد کند.

### 8.2 چطور از تغییرات پرریسک جلوگیری می‌کنیم؟

- ابتدا پوستهٔ مشترک و یک View آزمایشی؛ بعد تعمیم.
- تغییر بزرگ در یک PR، تست و اسکرین‌شات مستقل.
- کنترل View-to-service mapping پیش از حذف هر مسیر کلاسیک.
- هیچ تغییر State Schema، مهاجرت داده، منطق workflow یا Publisher برای راحت‌ترکردن UI داخل PR بازطراحی انجام نشود.
- اگر یک Action لازم موجود نیست، مسئله به‌عنوان وابستگی ثبت می‌شود؛ GUI نباید از طریق دست‌کاری State آن را دور بزند.
- بازنویسی کامل App یا تغییر Toolkit «پیش‌فرض رودمپ» نیست؛ فقط با ADR تازه و مقایسهٔ واقعی قابل بررسی خواهد بود.

### 8.3 معیار عملکرد

Baseline رسمی نسخهٔ 2.6.0 به‌عنوان نقطهٔ مرجع گرفته می‌شود. Gate عملکرد باید همان ماشین/روش اندازه‌گیری را تا حد ممکن حفظ کند. هدف‌ها:

- ساخت پنجرهٔ اصلی زیر 500ms در Baseline مرجع موجود؛
- تعاملات محلی معمولی با تأخیر قابل‌احساس کمتر از 100ms در P95، جایی که قابلیت سنجش دارد؛
- بارگذاری Timeline/فهرست با صفحه‌بندی و بدون مسدودکردن UI؛
- عملیات شبکه/Build در UI thread اجرا نشود؛
- افزایش حافظه/اندازهٔ نصب نسبت به Baseline، اگر ایجاد شد، اندازه‌گیری و توضیح داده شود.

اگر ظاهر جدید سرعت را کاهش داد، طراحی باید ابتدا ساده‌سازی شود؛ اضافه‌کردن Cache و پیچیدگی معماری صرفاً برای نگه‌داشتن تزئینات انتخاب مطلوب نیست.

## 10. مدیریت Scope و تصمیم‌گیری

### 10.1 موارد داخل Scope

- ظاهر و چیدمان پنجرهٔ اصلی و نماهای Workspace؛
- معماری اطلاعات و ناوبری؛
- Design System و کامپوننت‌های مشترک؛
- UX برای Empty/Error/Success/Busy/Disabled/Long content؛
- Responsive desktop، RTL/LTR، تم روشن/تاریک و Accessibility؛
- اصلاح جابه‌جایی View/حفظ انتخاب فقط در صورت کشف مشکل واقعی؛
- GUI smoke، Regression بصری و آزمون وظیفه؛
- راهنمای زبان/متن UI و مستندسازی الگوها.

### 10.2 موارد خارج از Scope

- افزودن قابلیت AI یا API مدل؛
- ورود به حساب مدل، اسکرپ چت یا ارسال خودکار پیام؛
- تغییر پروتکل Handoff/Response یا State Machine؛
- بازنویسی Store/Event Ledger/Task schema؛
- تغییر رفتار GitHub Publisher، Build و Installer فراتر از الزامات بسته‌بندی GUI؛
- طراحی مجدد اپ موبایل یا Companion؛
- مهاجرت به PySide/Qt یا Framework جدید بدون ADR مستقل؛
- افزودن داشبورد/کارت/انیمیشن صرفاً تزئینی.

### 10.3 تغییر Scope

اگر در جریان طراحی مشخص شد یک مشکل واقعی UI بدون تغییر Controller/API قابل حل نیست، باید آن را به‌صورت «وابستگی» ثبت کرد، اثرش را توضیح داد و تصمیم جدا گرفت. تغییرات متقاطع GUI و Domain در یک PR بزرگ ادغام نشوند.

### 10.4 نقش تصمیم‌گیر

- **مالک محصول:** تأیید جریان کار، اولویت‌ها و معیارهای پذیرش.
- **مجری/برنامه‌نویس:** رعایت مرزبندی فنی، کامپوننت‌های مشترک، تست‌ها و مستندات.
- **بازبین طراحی:** بررسی یکپارچگی بصری، کاربردپذیری، RTL و معیارهای این سند؛ می‌تواند مالک محصول به‌همراه یک بازبین مستقل باشد.
- **Gate release:** براساس شواهد؛ شمارهٔ نسخه به‌تنهایی معادل تأیید GUI نیست.
