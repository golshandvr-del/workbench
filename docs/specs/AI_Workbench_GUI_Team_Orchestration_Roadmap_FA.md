# نقشه‌راه پیشنهادی بازطراحی محیط کاری و مدیریت تیم چندهوش‌مصنوعی در AI Workbench

**نسخه سند:** 1.0  
**تاریخ:** ۱۸ اکتبر ۲۰۲۶  
**مخاطب:** برنامه‌نویس اصلی، مسئول معماری و مالک محصول AI Workbench  
**وضعیت:** پیشنهاد محصول و فنی؛ پیش از تبدیل به برنامه اجرایی رسمی باید با یک ADR تصویب و به `ROADMAP.md` اصلی متصل شود.  
**مبنای کد موجود:** ریپوی `golshandvr-del/workbench`، شاخه `main`، نسخه‌های گزارش‌شده `desktop-v2.2.0` و `mobile-v0.3.0`.

> **هدف این سند:** تبدیل سه نیاز مرتبط به یک طرح اجرایی منسجم: ۱) محیط کاری مدرن، سبک و واکنش‌گرا؛ ۲) تایم‌لاین و ردیابی قابل‌اعتماد پیشرفت پروژه؛ ۳) برنامه‌ریزی، تخصیص و پیگیری چند Agent با اکانت‌ها و چت‌های معمولی مدل‌ها، بدون اتصال مستقیم به API و بدون ورود Workbench به حساب مدل‌ها.
>
> این سند صرفاً پیشنهاد Roadmap است. نباید بدون بررسی و تصویب ADR، شماره نسخه‌ها یا ترتیب آن به‌عنوان تغییر قطعی در Roadmap اصلی اعمال شود.

## ۱. خلاصه اجرایی

AI Workbench تا نسخه‌های فعلی زیرساخت‌های مهمی برای مدیریت پروژه با چند Agent دارد: مدل داده نسخه‌دار V2، Agent Registry، Task Graph، وابستگی Taskها، Prompt Planning مدیر پروژه، Handoff بین چت‌ها، Response Inbox، Repair Prompt، Context Request، Decision/Evidence Ledger، انتشار وضعیت پروژه در GitHub، Next Action و حالت‌های Simple/Advanced. این زیرساخت‌ها باید حفظ و توسعه داده شوند؛ بازنویسی دوباره آن‌ها هدف این Roadmap نیست.

فاصله اصلی باقی‌مانده، تبدیل این قابلیت‌ها به تجربه‌ای یکپارچه و قابل‌فهم برای کاربر است. رابط فعلی چند مسیر و پنجره جدا دارد و هنوز به‌طور کامل شبیه یک محیط کاری پروژه‌محور نیست. همچنین Agent فعلی یک **نقش کاری** است؛ برچسبی مانند `preferred_model_label` به‌تنهایی به این معنا نیست که Workbench اکانت واقعی یا وضعیت داخلی یک چت ChatGPT/Gemini را می‌شناسد. پیشنهاد تیم مدیر پروژه نیز هنوز به یک برنامه‌ریز صریح برای تعداد Agentها، منابع واقعی در دسترس کاربر، تخصیص چت‌ها و داشبورد یکپارچه وضعیت تبدیل نشده است.

این Roadmap، محصول را به سوی یک **Project Workbench** هدایت می‌کند: یک پوسته اصلی مدرن و واکنش‌گرا، مرکز پروژه، Timeline/Activity، Team Planner، فهرست منابع و چت‌های دستی، داشبورد عملیات Agentها و صف اقدام‌هایی که فقط موارد نیازمند توجه کاربر را در اولویت می‌گذارد.

اصل کلیدی این است که برنامه باید وضعیت گردش‌کار را دقیق نشان دهد، نه اینکه درباره فعالیت داخلی مدل حدس بزند. در معماری فعلی، Workbench پرامپت را آماده می‌کند؛ کاربر آن را به چت معمولی مدل می‌برد و پاسخ را برمی‌گرداند. بنابراین وضعیت‌هایی مانند «پرامپت آماده»، «کاربر ارسال را تأیید کرده»، «در انتظار پاسخ»، «پاسخ دریافت شده»، «پاسخ ناقص» و «اعتبارسنجی تأیید شده» قابل ثبت‌اند؛ اما «مدل اکنون در حال تولید پاسخ است» بدون سیگنال واقعی از سرویس مدل قابل اثبات نیست.

### خروجی مورد انتظار

در پایان اجرای Roadmap، کاربر باید بتواند:

1. یک پروژه را باز کند و بلافاصله هدف، وضعیت کلی، گام فعلی، خطرها و اقدام بعدی را بفهمد.
2. تاریخچه و مسیر پیشرفت پروژه را در Timeline ببیند و هر رویداد را به Task، Attempt، Handoff، Evidence، Commit یا Release مرتبط باز کند.
3. اکانت‌ها/پروفایل‌های مدل و چت‌های دستی در دسترسش را ثبت کند، بدون ذخیره‌کردن گذرواژه یا اتصال به حساب مدل.
4. از مدیر پروژه بخواهد تعداد و نقش Agentهای مناسب، تقسیم کار، وابستگی‌ها و امکان موازی‌سازی را پیشنهاد دهد؛ پیشنهاد را بازبینی و اصلاح کند؛ سپس آن را به وضعیت واقعی منابع خود نگاشت کند.
5. وضعیت گردش‌کار همه Agentها را در یک نمای مشترک ببیند و بدون وارسی تک‌تک چت‌ها، مواردی را که واقعاً اقدام می‌خواهند پیدا کند.
6. بین «اصلاح خروجی همین Task»، «ادامه/توسعه Task موجود» و «تعریف قابلیت یا Task جدید» سردرگم نشود.
7. چت جدید را با پرامپت انتقال و فایل‌ها/بخش‌های زمینه لازم آماده کند، با اطلاع صریح از آنچه آماده شده و آنچه هنوز خودش باید در چت ارسال کند.
8. از Timeline و درصدها برداشت غلط نکند: ادعای مدل از شواهد واقعی جدا باشد و نسخه‌سازی معادل انجام هر Task تلقی نشود.
9. برنامه را در رزولوشن‌ها و مقیاس‌های متداول Windows بدون دکمه‌ها یا پنل‌های خارج از محدوده، و بدون کندی محسوس در تعاملات محلی به‌کار ببرد.

## ۲. اصول تغییرناپذیر محصول و محدوده

### ۲.۱. الگوی تعامل با مدل‌ها حفظ می‌شود

این Roadmap **اتصال API مدل، استفاده از API Key مدل، ورود Workbench به حساب ChatGPT/Gemini، scraping چت مرورگر یا ارسال خودکار پیام به چت مدل را اضافه نمی‌کند**. مسیر پیش‌فرض همچنان دستی است:

1. Workbench برای یک Task/Agent پرامپت می‌سازد.
2. کاربر پرامپت را کپی می‌کند و در چت معمولی مدل منتخب می‌فرستد.
3. کاربر پاسخ متنی/فایلی را به Workbench برمی‌گرداند.
4. Workbench پاسخ خام را نگه می‌دارد، آن را تحلیل و اعتبارسنجی می‌کند و نتیجه یا اقدام بعدی را نمایش می‌دهد.
5. تغییرات فایل فقط از مسیر بازبینی و تأیید موجود اعمال می‌شوند.

### ۲.۲. «Agent»، «اکانت»، «چت» و «Task» مفاهیم جدا هستند

- **Agent:** نقش کاری پایدار با دستورالعمل، وظایف مجاز و قرارداد خروجی؛ مانند Project Manager، Architect، Implementer یا Reviewer.
- **Account Profile:** برچسب محلی‌ای که کاربر به یکی از حساب‌های در اختیارش می‌دهد؛ مثلاً «GPT پولی»، «Gemini رایگان» یا «اکانت کاری». نوع طرح/رایگان/پولی خوداظهاری کاربر است و Workbench آن را تأیید یا از سرویس مدل استعلام نمی‌کند.
- **Chat Binding:** نام یا لینک اختیاری چت دستی‌ای که کاربر تصمیم می‌گیرد برای یک Agent استفاده کند. لینک/نام فقط یادداشت راهنما است؛ اتصال یا نظارت خودکار بر چت ایجاد نمی‌کند.
- **Task:** واحد مشخص کار که هدف، محدوده، معیار پذیرش، وابستگی، مالک کاری و وضعیت مستقل خود را دارد.
- **Attempt/Handoff:** تلاش مشخص برای گرفتن خروجی یک Task یا انتقال کار بین نقش‌ها/چت‌ها. تاریخچه آن نباید با Task جدید اشتباه گرفته شود.
- **Milestone:** نقطه عطف قابل‌تأیید، مثل «MVP قابل اجرا».
- **Version/Release:** نسخه برچسب‌خورده و قابل ردیابی؛ ممکن است چند Task را شامل شود. هر Task به‌طور خودکار نسخه جدید نمی‌سازد.

### ۲.۳. انسان مسئول تصمیم‌های پرریسک باقی می‌ماند

- پیشنهاد تیم، برنامه و تغییر Scope باید قابل بازبینی باشد.
- هیچ پاسخ مدل با صرف Import/Parse به‌تنهایی فایل پروژه را تغییر نمی‌دهد.
- ادعای مدل درباره تست یا Build، به‌عنوان Evidence تأییدشده ثبت نمی‌شود مگر شاهد معتبر وجود داشته باشد.
- تعارض دو خروجی روی یک فایل به‌صورت خودکار Merge نمی‌شود.
- تخصیص کار، ارسال پرامپت، تأیید پاسخ، اعمال تغییر و ساخت/انتشار نسخه باید وضعیت مستقل و روشن داشته باشند.

### ۲.۴. اصل کم‌بارکردن کاربر

هدف «نمایش همه چیز در یک صفحه» نیست؛ هدف این است که کاربر در صفحه اصلی فقط اطلاعات لازم برای تصمیم بعدی را ببیند. جزئیات تخصصی باید در Inspector، بخش‌های بازشونده، پنل‌های زمینه‌ای یا نمای Advanced موجود باشند. هر سطح پیچیدگی باید برای حل یک کار واقعی وجود داشته باشد.

## ۳. ممیزی مبنا: آنچه داریم و آنچه باید تکمیل شود

این بخش بر اساس سورس و اسناد فعلی ریپو نوشته شده و باید هنگام شروع توسعه با `main` واقعی دوباره تأیید شود.

| وضعیت بعدی | `aiwb/v2/next_action.py` و `controller.py` | استفاده از همان منطق در داشبورد، Timeline و صف عملیات |
| شواهد | Decision/Evidence Ledger و Release Gates فعلی | اتصال بصری شواهد به Taskها، نقاط عطف و نسخه‌ها |

| GUI فعلی | Tkinter؛ پنجره Projects با Simple/Advanced | پوسته و تعاملات بازطراحی شوند، ولی منطق سرویس از UI جدا بماند |
| Windows Installer / CI | Monorepo، manifest، release workflows و قراردادهای مشترک | بسته‌بندی، نصب، ارتقا و امضا در هر Release حفظ و آزمایش شود |

### ۳.۲. شکاف‌های اصلی

1. **پوسته یکپارچه کم‌رنگ است:** پرامپت کلاسیک، Response Inbox، Projects، Context Request، GitHub و Companion هنوز به شکل مجموعه‌ای از پنجره‌ها/تب‌ها تجربه می‌شوند، نه یک Workspace با Navigation ثابت و Inspector زمینه‌ای.
2. **ساده‌بودن محدود به پنجره Projects است:** Simple/Advanced موجود، تمام GUI برنامه را به یک محیط ساده یا حرفه‌ای تبدیل نمی‌کند؛ چندین دکمه همچنان در همان سطح دیده می‌شوند.
3. **Agent از حساب و چت واقعی تفکیک نشده است:** برچسب مدل جای registry منابع قابل انتخاب و binding دستی چت را نمی‌گیرد.
4. **برنامه‌ریزی تیم صریح نیست:** مدیر پروژه از ابتدا موظف نیست تعداد Agentهای اضافی، نقش‌ها، ظرفیت‌های در دسترس، برنامه موازی و دلیل انتخاب تیم را پیشنهاد دهد.
5. **حالت بیرونی چت محدودیت معنایی دارد:** UI باید ارسال کاربر و انتظار پاسخ را از «مدل واقعاً مشغول است» جدا کند.
6. **داشبورد تیم و صف اولویت‌دار یکپارچه نیست:** برای پروژه‌ای با چندین Agent، کاربر نباید مجبور باشد Task/Attemptهای مختلف را دستی بگردد تا بفهمد کدام خروجی خراب یا منتظر تصمیم است.
7. **Timeline پروژه‌محور مستقل هنوز نیازمند طراحی است:** تاریخچه رویداد، Milestone، Version، Task و خطوط کاری Agent باید به هم وصل شوند، بدون آنکه با یکدیگر اشتباه گرفته شوند.
8. **تناسب GUI و Performance باید به‌عنوان Gate مستقل آزمایش شود:** ظاهر بهتر بدون سنجش اندازه پنجره، DPI، سرعت، مصرف حافظه و UX قابل‌قبول نیست.

## ۴. مدل مفهومی محیط کاری

### ۴.۱. اسکلت اصلی برنامه

پنجره اصلی باید یک قاب پایدار داشته باشد:

- **Title/Project Bar:** پروژه فعال، وضعیت خلاصه، شاخه/Repository در صورت اتصال، وضعیت ذخیره/Publish و کنترل‌های پنجره.
- **Navigation Rail/Sidebar:** دسترسی به نمای کلی، Timeline، Tasks، Team، Files & Context، Versions & Builds و Settings. گزینه‌های کم‌کاربرد در More/Tools باشند، نه همگی در سطح اصلی.
- **Central Workspace:** محیط اصلی متناسب با نمای منتخب. Timeline یا Task Board باید فضای کافی داشته باشد؛ از قرار دادن همه جزئیات در تب‌های کوچک خودداری شود.
- **Context Inspector:** پنل سمت راست یا پایین که با انتخاب Task/Agent/Event اطلاعات مرتبط و اقدام‌های مجاز را نشان می‌دهد. در عرض کم قابلیت جمع‌شدن دارد.
- **Action Bar:** فقط دکمه‌های مربوط به نمای فعلی/عنصر انتخاب‌شده؛ سایر ابزارها در منو یا پنل مرتبط.
- **Next Action Strip:** عبارت روشن و قابل اجرا درباره مهم‌ترین اقدام بعدی، در بالای Workspace یا Overview. این بخش باید از `ProjectsController/Next Action` و وضعیت واقعی داده استفاده کند، نه متن مستقل و متناقض.
- **Status/Activity Footer:** عملیات محلی زمان‌بر، انتشار وضعیت، خطاهای اخیر و وضعیت اتصال به‌صورت کم‌مزاحمت نشان داده شود.

### ۴.۲. ناوبری پیشنهادی

1. **Overview / نمای کلی:** هدف، وضعیت پروژه، اقدام بعدی، Taskهای نیازمند توجه، پیشرفت تأییدشده و آخرین فعالیت.
2. **Timeline / تاریخچه:** رویدادهای واقعی، مسیر Taskها، Milestoneها، تلاش‌ها، Commitها و Versionها.
3. **Tasks / وظایف:** لیست/برد Task، فیلتر بر اساس وضعیت، Agent، اولویت، وابستگی یا Version.
4. **Team / تیم AI:** Agentها، Account Profileهای کاربر، Chat Bindingها، پیشنهاد تیم و وضعیت گردش‌کار هر Agent.
5. **Files & Context / فایل‌ها و زمینه:** تغییرات پیشنهادی، فایل‌های دریافت‌شده، Context Packهای آماده‌شده و درخواست‌های زمینه.
6. **Versions & Builds / نسخه‌ها و ساخت‌ها:** Milestoneها، نسخه‌ها، Commit/Build/Artifact و شواهد مرتبط.
7. **Settings / تنظیمات پروژه:** هدف، معیار موفقیت، منابع و سقف هم‌زمانی، ترجیحات رابط و اتصال Repository.

نام‌ها و ترتیب نهایی پس از تست نمونه اولیه قابل تغییر است. این ساختار، جهت طراحی است، نه الزام برای استفاده از همین عبارات انگلیسی.

### ۴.۳. طراحی ابزارها با الهام از محیط‌های حرفه‌ای

از نرم‌افزارهایی مثل Photoshop، SolidWorks، Word و PowerPoint باید این اصول را بگیریم:

- یک Workspace مشخص و ثابت؛
- ابزارها در گروه‌های منظم و وابسته به Context؛
- پنل‌های قابل‌تنظیم و قابل پنهان‌کردن؛
- انتخاب عنصر و نمایش Inspector مرتبط؛
- میانبرهای صفحه‌کلید و فرمان‌های قابل جست‌وجو در صورت توجیه؛
- حفظ فضای اصلی برای کار واقعی.

**نباید** Ribbon بسیار شلوغ، ده‌ها دکمه همیشه آشکار، ابزارهای فنی غیرمرتبط با Task منتخب یا نمودارهای صرفاً تزئینی کپی شوند. هدف تقلید ظاهری نیست؛ هدف کاهش زمان پیدا کردن اقدام درست است.

## ۵. معماری Timeline، رویدادها و Versioning

### ۵.۱. موجودیت‌هایی که نباید با هم ادغام شوند

- **Task:** واحد کاری قابل‌تعریف و مستقل.
- **Attempt:** یک تلاش برای تولید خروجی یک Task؛ ممکن است پاسخ موفق، ناقص، خراب، قدیمی یا ردشده داشته باشد.
- **Handoff:** انتقال Task/اطلاعات بین Agentها یا چت‌های مختلف.
- **Milestone:** یک نتیجه یا مرحلهٔ مهم با معیار پذیرش مشخص.
- **Version:** برچسب نسخه برای مجموعه‌ای از تغییرات؛ معمولاً Semantic Versioning یا سیاست نسخه‌بندی تعریف‌شده توسط پروژه.
- **Release/Build:** رویداد ساخت/انتشار واقعی همراه شناسه اجرا، Commit، Artifact و Hash در صورت وجود.
- **Project Event:** رویداد تاریخی ثبت‌شده مثل ایجاد Task، تغییر Revision، پاسخ واردشده، تأیید Handoff، شکست اعتبارسنجی، Commit یا انتشار نسخه.

یک Task می‌تواند چند Attempt داشته باشد، چند Task می‌توانند یک Milestone را تشکیل دهند و یک Version می‌تواند چند Task را شامل شود. هیچ نگاشت اجباری یک‌به‌یک نباید بین Task و Version ایجاد شود.

### ۵.۲. Timeline باید داده‌محور باشد

پیشنهاد می‌شود نمای Timeline از Event Ledger پایدار ساخته شود. پیش از پیاده‌سازی، بررسی شود آیا رویدادهای موجود در `ProjectStore` با سقف نگهداری فعلی (`MAX_EVENTS`) نیازهای تاریخچهٔ بلندمدت را برآورده می‌کنند یا Event Ledger append-only مجزا لازم است. تاریخچه نباید فقط از وضعیت فعلی بازسازی حدسی شود.

هر Event، در حد اطلاعات موجود، باید شامل این فیلدها باشد:

- `event_id` پایدار؛
- `schema_version`؛
- `timestamp_utc` و منبع زمان؛
- `project_id`؛
- `event_type`؛
- شناسه‌های مرتبط مثل `task_id`، `agent_id`، `attempt_id`، `handoff_id`، `evidence_id`، `milestone_id`، `version_id` یا Commit SHA؛
- وضعیت قبل/بعد در صورت کاربرد؛
- `state_revision`؛
- منبع رویداد (Workbench، تأیید کاربر، مدل گزارش‌کرده، GitHub Actions و غیره)؛
- نشانگر Evidence (`verified`، `reported`، `not_run`، `failed` یا مقادیر قراردادی معادل)؛
- برچسب خواندنی و Payload محدود، بدون Prompt/Response خام مگر در سیستم ذخیرهٔ مربوطه و با سیاست مستقل.

رویدادهای تکراری باید با شناسه/کلید idempotency یا قاعدهٔ معادل از تولید چند نقطهٔ یکسان جلوگیری شوند. تغییر زبان رابط، باز کردن پنل یا جابه‌جایی تب نباید Event پروژه ایجاد کند.

### ۵.۳. انواع رویداد پیشنهادی

- `project_created`, `project_goal_updated`, `project_settings_updated`;
- `team_plan_requested`, `team_proposal_received`, `team_proposal_accepted`, `team_proposal_partially_accepted`;
- `agent_created`, `agent_assignment_changed`, `account_profile_added`, `chat_binding_updated`;
- `task_created`, `task_updated`, `task_revision_created`, `task_assigned`, `task_blocked`, `task_unblocked`;
- `attempt_created`, `prompt_prepared`, `prompt_copied`, `user_confirmed_sent`, `response_received`;
- `response_parse_failed`, `response_partial`, `repair_prepared`, `context_request_received`, `context_pack_prepared`;
- `handoff_prepared`, `handoff_response_received`, `handoff_accepted`, `handoff_rejected`, `handoff_stale`;
- `decision_proposed`, `decision_accepted`, `decision_rejected`;
- `validation_started`, `validation_passed`, `validation_failed`;
- `milestone_created`, `milestone_accepted`, `version_proposed`, `version_created`, `release_published`;
- `project_state_publish_started`, `project_state_published`, `project_state_publish_failed`.

لیست فوق پیشنهادی است. هر Event فقط وقتی ثبت شود که رویداد واقعی یا عمل کاربر رخ داده باشد. «پرامپت آماده شد» را نباید با «پرامپت ارسال شد» یکی گرفت.

### ۵.۴. Timeline با Laneها

نمای ساده، یک تاریخچه خطی از رویدادها با گروه‌بندی بر اساس روز، Milestone یا Task ارائه می‌دهد. نمای پیشرفته می‌تواند Laneهای موازی برای Agentها یا جریان‌های کاری را نمایش دهد.

قواعد:

- Lane نشان‌دهندهٔ **جریان کاری/Agent** است؛ لزوماً همان Git Branch نیست.
- Git Branch، گروه منطقی Taskها و Lane تیم سه مفهوم مستقل‌اند.
- Task موازی باید وابستگی و Scope خودش را نشان دهد؛ موازی بودن صرفاً با قرارگرفتن در Lane جدا اثبات نمی‌شود.
- رویدادهای ریز مثل هر بار بازکردن پنجره به Timeline اضافه نشوند.
- فیلتر بر اساس Agent، Task، نوع رویداد، بازه زمانی، Milestone، Version، وضعیت و سطح Evidence پشتیبانی شود.
- کاربر بتواند از هر نقطه به Task/Attempt/Handoff/Evidence اصلی برود.
- رویدادهای آینده یا برنامه‌ریزی‌شده با رویدادهای انجام‌شده تفاوت بصری و متنی روشن داشته باشند.
- زمان‌های تاریخی ناقص/legacy با برچسب نامعلوم/قدیمی ارائه شوند؛ تاریخ جدید حدس زده نشود.

### ۵.۵. قواعد Versioning

- سیاست پیش‌فرض پروژه می‌تواند Semantic Versioning باشد، اما الزام نیست؛ سیاست باید قابل تنظیم و مستند باشد.
- اضافه‌شدن Task یا پاسخ یک مدل به‌تنهایی Version جدید نمی‌سازد.
- Milestone می‌تواند چند Task را تجمیع کند.
- Version انتشار‌یافته باید در صورت امکان به Commit SHA، Build/Run ID، Artifact و SHA-256 متصل باشد.
- پیشنهاد Version می‌تواند از مدیر پروژه بیاید؛ تأیید، ساخت Tag یا انتشار واقعی باید جداگانه ثبت شود.
- نسخهٔ پیشنهادی، نسخهٔ محلی، Tag ایجادشده و Release منتشرشده در UI وضعیت‌های متفاوت باشند.
- اگر پروژه GitHub/Build ندارد، قابلیت تاریخچه و Milestone باید همچنان محلی کار کند؛ وضعیت Version نباید به‌طور ساختگی Released نشان داده شود.

## ۶. محاسبه و نمایش پیشرفت

### ۶.۱. درصد پیشرفت نباید ساختگی باشد

از مدل نباید پرسید «چند درصد پروژه تمام شده؟» و عدد را بدون محاسبه پذیرفت. درصدهای برنامه باید از وضعیت داده و روش محاسبهٔ روشن به‌دست آیند.

### ۶.۲. شاخص‌های پیشرفت

1. **Taskهای تأییدشده:** `done / تمام Taskهای داخل Scope گزارش`. UI باید صورت و مخرج را نشان دهد، مثلاً «۸ از ۱۲ Task تأیید شده؛ ۶۷٪ از تعداد Taskها». این درصد مساوی درصد حجم واقعی پروژه نیست.
2. **پیشرفت وزنی تخمینی:** فقط در صورت وجود وزن/اندازهٔ Task با روش مستند. باید صریحاً برچسب «تخمینی» داشته باشد؛ وزن‌ها نباید بی‌توضیح از خروجی مدل پذیرفته شوند.
3. **وضعیت اعتبارسنجی:** تعداد Taskهای Done، در انتظار تست/Build، در انتظار بازبینی، مسدود و نیازمند تصمیم به‌صورت جداگانه.
4. **آمادگی Release:** تعداد معیارهای پذیرش و شواهد الزامی که واقعاً پاس شده‌اند؛ نه درصدی که مدیر پروژه گزارش کرده باشد.

### ۶.۳. قواعد تکمیل Task

- وضعیت Task بر اساس ماشین وضعیت مرکزی و Acceptance Policy موجود مدیریت شود.
- گزارش مدل به‌تنهایی Task را `done` نمی‌کند.
- Evidence قدیمی، متعلق به Commit/Revision ناسازگار یا بدون منبع معتبر باید به‌عنوان قدیمی/گزارش‌شده نمایش داده شود.
- اگر یک Task بر اساس سیاست خود فقط Manual Review می‌خواهد، UI باید همین سیاست را نشان دهد؛ شاخص‌ها از سیاست پذیرش پنهان پیروی نکنند.
- Task لغوشده یا جایگزین‌شده باید در تاریخچه باقی بماند، ولی بسته به تعریف Scope گزارش از مخرج پیشرفت خارج یا جداگانه گزارش شود؛ این قاعده باید در تنظیمات/تعریف گزارش شفاف باشد.

## ۷. Team Planner: پیشنهاد تیم و تقسیم کار از سوی مدیر پروژه

### ۷.۱. هدف

هنگام تعریف پروژه، کاربر هدف و محدودیت‌ها را می‌دهد و منابع موجود را مشخص می‌کند. Workbench یک Planning Prompt برای مدیر پروژه آماده می‌کند که از او می‌خواهد علاوه بر معماری و Taskها، **ترکیب پیشنهادی تیم** و دلیل انتخاب آن را ارائه دهد. پیشنهاد مدیر پروژه باید توسط Workbench دریافت، اعتبارسنجی و پیش از اعمال به کاربر نشان داده شود.

### ۷.۲. اطلاعات ورودی برنامه‌ریزی

در کنار ورودی‌های فعلی پروژه، این اطلاعات به‌صورت اختیاری/مرحله‌ای جمع‌آوری شوند:

- هدف و غیرهدف‌های پروژه؛
- معیارهای موفقیت؛
- پلتفرم و فناوری‌های معلوم؛
- محدودیت‌های زمانی/هزینه‌ای که کاربر می‌خواهد وارد کند؛
- اولویت میان سرعت، سادگی مدیریت، کیفیت/بازبینی و کم‌هزینه‌بودن؛
- تعداد Account Profileهای ثبت‌شده و تعداد چت‌هایی که کاربر واقعاً مایل است هم‌زمان پیگیری کند؛
- حداکثر Agent فعال یا حداکثر جریان موازی موردنظر کاربر؛
- Agentهای قابل استفاده و نقش‌هایشان؛
- ترجیح کاربر برای انتخاب مدیر پروژه، مانند قوی‌ترین/قابل‌اعتمادترین مدل در دسترس؛
- محدودیت‌های Scope، دسترسی فایل، Build، GitHub و اجرای محلی.

Workbench نباید از روی عبارت «اکانت پولی» قابلیت یا سهمیهٔ واقعی را حدس بزند. منابع در دسترس باید توسط کاربر ثبت شوند و این ثبت، احراز صحت حساب نیست.

### ۷.۳. ورودی Team Proposal از مدیر پروژه

قرارداد Proposal باید توسعه یابد یا یک قرارداد نسخه‌دارِ سازگار ایجاد شود تا پیشنهاد بتواند این موارد را بیان کند:

- خلاصهٔ برنامه و فرض‌ها؛
- تعداد کل Agentهای منطقی پیشنهادی، با مشخص‌کردن اینکه مدیر پروژه در این شمارش هست یا خارج از آن؛
- نقش‌ها و مسئولیت‌های هر Agent؛
- افرادی که باید در نقش مدیر پروژه، معمار، پیاده‌ساز، تست/بازبین یا پژوهشگر باشند؛
- Taskهای پیشنهادی و معیار پذیرش هر Task؛
- مالک Agent پیشنهادی برای هر Task؛
- Reviewers پیشنهادی، در صورت نیاز؛
- وابستگی‌ها و گروه‌های Task موازی؛
- Scope فایل/زیرسیستم، خروجی مورد انتظار و محدودیت‌های تداخل؛
- دلیل اینکه اندازه تیم مناسب است؛
- جایگزین ساده‌تر/کم‌ریسک‌تر و هزینه مدیریتی تیم بزرگ‌تر؛
- ریسک‌ها، اطلاعات ناموجود و سؤال‌هایی که فقط کاربر می‌تواند جواب دهد؛
- پیشنهاد مدل/Account Profile برای هر نقش فقط در حد منابعی که کاربر ثبت کرده است؛
- میزان اطمینان و فرض‌ها، نه ادعای دقت عددی بی‌پایه.

### ۷.۴. قواعد انتخاب اندازه تیم

- تعداد بیشتر Agentها همیشه بهتر نیست؛ موازی‌سازی تنها وقتی ارزش دارد که Taskها واقعاً مستقل یا دارای قرارداد مرزی مشخص باشند.
- پیشنهاد پیش‌فرض باید تیم کوچک و قابل مدیریت را ترجیح دهد، مگر آنکه پروژه واقعاً امکان تقسیم مستقل کار را نشان دهد.
- اگر کاربر چهار Account Profile دارد، مدیر پروژه باید روشن کند آیا این چهار منبع شامل خودش هستند یا کارگرهای اضافی؛ UI نباید شمارش را مبهم بگذارد.
- یک Account Profile می‌تواند به چند Chat Binding دستی متصل باشد، اما کاربر باید محدودیت واقعی سرویس و بار تعویض چت را در نظر بگیرد.
- بهتر است کاربر «حداکثر چت‌های فعال/در حال پیگیری» را تعیین کند. این سقف از تعداد کل Agentهای تعریف‌شده جداست.
- تعداد Agent منطقی می‌تواند از تعداد اکانت‌ها بیشتر باشد، اما Workbench باید reuse یک Account Profile را صریح نشان دهد و هر چت/نقش را از دیگری تفکیک کند.
- اگر Taskها در یک فایل یا قرارداد مشترک تداخل دارند، به‌طور پیش‌فرض موازی نشوند یا نیازمند سیاست ادغام/هماهنگی مشخص باشند.
- طرح بزرگ فقط با توضیح مزیت، ریسک، بار مدیریتی و امکان ساده‌سازی پیشنهاد شود.

### ۷.۵. بازبینی پیشنهاد تیم

پیشنهاد مدیر پروژه به‌صورت Preview در Workbench ارائه شود:

- خلاصهٔ تیم، تعداد Agentها و منابع مورد نیاز؛
- دیاگرام وابستگی‌ها یا گروه‌های موازی؛
- فهرست Taskها با مالک، Scope و معیار پذیرش؛
- Agent یا Account Profile ناموجود، غیرفعال یا نامشخص به‌وضوح مشخص شود؛
- تعارض‌های احتمالی Scope و وابستگی بررسی شوند؛
- پذیرش کل، پذیرش انتخابی، رد، درخواست اصلاح، یا تغییر دستی موجود باشد.

فقط عملیات تأییدشده وارد State پروژه شوند. عملیات نامعتبر نباید به‌صورت ساکت نادیده گرفته شوند. اگر کاربر بخشی از پیشنهاد را پذیرفت، وابستگی‌های Taskهای انتخاب‌شده دوباره اعتبارسنجی شوند.

### ۷.۶. برنامه‌ریزی مجدد

مدیر پروژه می‌تواند با `Manager Update` از State فعلی و رویدادهای پس از گزارش قبلی آگاه شود و پیشنهاد Re-plan ارائه کند. Workbench باید:

- نسخه/Revision پایه پیشنهاد را بررسی کند؛
- تغییرات ناسازگار یا مبتنی بر State قدیمی را Stale علامت بزند؛
- Taskهای انجام‌شده را بدون دلیل دوباره باز نکند؛
- پیشنهادهای مربوط به تیم/تخصیص را از اعمال خودکار جدا نگه دارد؛
- دلیل و اثر تغییرات را قبل از قبول نمایش دهد.

## ۸. Account Profile و Chat Binding دستی

### ۸.۱. هدف

کاربر بتواند منابع واقعی‌اش را در UI توصیف کند و تصمیم بگیرد هر Agent برای چه نقشی از کدام حساب و کدام چت دستی استفاده کند؛ بدون اینکه Workbench وارد حساب مدل شود.

### ۸.۲. Account Profile پیشنهادی

فیلدهای حداقلی:

- `account_profile_id` پایدار؛
- نام نمایشی دلخواه کاربر، مانند «GPT Pro کار شخصی»؛
- ارائه‌دهنده/سرویس به‌صورت Label (مثلاً GPT، Gemini، Claude یا «سایر»)؛
- پلن خوداظهاری: رایگان/پولی/سازمانی/نامشخص؛
- توضیح اختیاری محدودیت، ترجیح یا کاربرد؛
- فعال/غیرفعال؛
- برچسب‌های کاربرد مثل planning، coding، review؛
- تاریخ ایجاد/ویرایش.

Workbench نباید گذرواژه، Cookie، Session Token یا API Key مدل را ذخیره کند. مقدار «پولی» فقط ورودی کاربر است، نه سیگنال احراز‌شده از سرویس مدل. اطلاعاتی درباره میزان مصرف/سهمیه، محدودیت واقعی سرویس یا availability زنده نباید جعل شود.

### ۸.۳. Chat Binding پیشنهادی

- `chat_binding_id` پایدار؛
- `agent_id`؛
- `account_profile_id`؛
- نام محلی چت/گفت‌وگو؛
- لینک اختیاری که کاربر دستی ثبت کرده باشد؛
- توضیح برای تشخیص چت؛
- فعال/غیرفعال؛
- آخرین تأیید کاربر که این چت همان نشست موردنظر است.

لینک یا نام چت صرفاً برای کمک به کاربر است؛ Workbench آن را بازبینی نمی‌کند، محتوا را scrape نمی‌کند و از روی آن نمی‌فهمد مدل پاسخ داده است یا نه.

### ۸.۴. قواعد Binding

- نقش/Agent ID از تعویض Account Profile یا Chat Binding تغییر نمی‌کند.
- تعویض حساب مدل تاریخچهٔ Attempt/Handoff قبلی را بازنویسی نمی‌کند.
- استفاده از یک Account Profile برای چند نقش مجاز است، اما چت‌های یکسان/متفاوت باید برای کاربر روشن باشند.
- Agent بی‌Account یا بدون Chat Binding هنوز قابل تعریف است، ولی هنگام آماده‌سازی پرامپت باید یک اقدام روشن برای انتخاب منبع نمایش داده شود.
- اگر Account Profile غیرفعال شد، Taskهای قدیمی حذف یا Done نشوند؛ تخصیص‌های آینده نیازمند انتخاب جایگزین باشند.
- مشخصات حساب نباید به GitHub منتشر شوند؛ Snapshot فقط داده‌های حداقلی پروژه و Task را منتشر کند.

## ۹. وضعیت گردش‌کار هر Agent و Task

### ۹.۱. مدل وضعیت

Workbench باید وضعیت داخلی خودش را در قالب مرحله‌های قابل‌اثبات نگه دارد. پیشنهاد اولیه برای Attempt/تعامل دستی:

1. `planned` — کار برنامه‌ریزی شده، پرامپتی هنوز آماده نشده است.
2. `ready_to_prepare` — وابستگی‌ها و ورودی‌های لازم آماده‌اند.
3. `prompt_prepared` — پرامپت در Workbench ساخته شده است.
4. `prompt_copied` — کپی در Clipboard انجام شده؛ این به معنی ارسال به مدل نیست.
5. `user_confirmed_sent` — کاربر به‌صورت صریح تأیید کرده که آن را به چت فرستاده است.
6. `waiting_for_response` — Workbench پاسخ ثبت‌شده‌ای ندارد و منتظر ورود دستی پاسخ است.
7. `response_received` — پاسخ وارد شده و خام آن ذخیره شده است.
8. `parse_failed` — پاسخ ذخیره شده، اما Parser/Validator نتوانسته آن را به شکل مورد انتظار تبدیل کند.
9. `partial_response` — بخشی از تحویل قابل بازیابی است و بخش‌هایی ناقص/گم‌شده‌اند.
10. `needs_user_review` — پاسخ parse شده و منتظر بازبینی/تأیید است.
11. `repair_ready` — پرامپت اصلاحی آماده است.
12. `context_request_pending` — مدل زمینه خواسته و Workbench درخواست را بررسی می‌کند.
13. `context_prepared` — Text Context یا ZIP تولید شده، اما لزوماً به چت ارسال نشده است.
14. `blocked` — کار به وابستگی، فایل، تصمیم یا منبعی نیاز دارد که موجود نیست.
15. `stale` — پاسخ بر اساس Revision/Attempt قدیمی است و نیازمند Reconcile است.
16. `validation_pending` — تغییر پذیرفته شده، اما تست/Build لازم انجام نشده است.
17. `verified_done` — معیار پذیرش و Evidence لازم طبق سیاست Task پاس شده است.
18. `rejected` / `abandoned` — خروجی رد شده یا Attempt کنار گذاشته شده است؛ تاریخچه حفظ می‌شود.

این‌ها حالت‌های مفهومی‌اند. لازم نیست همه دقیقاً به شکل یک Status جدید در ماشین موجود کپی شوند؛ در فاز پیاده‌سازی باید میان وضعیت Task، Attempt، Handoff، ارسال دستی و نمایش UI مرزبندی شود تا ماشین وضعیت ناسازگار نسازیم.

### ۹.۲. ابهام‌زدایی وضعیت‌های بیرونی

- دکمه `Copy prompt` فقط ثبت کند که پرامپت کپی شده، اگر رویداد فعلی آن را ثبت می‌کند؛ نباید ارسال را ادعا کند.
- کاربر می‌تواند پس از ارسال از طریق دکمه/چک‌باکس `I sent this prompt` تأیید کند. این رویداد خوداظهاری کاربر است و باید در همین حد گزارش شود.
- اگر کاربر تأیید ارسال نکند، برنامه وضعیت «در انتظار تأیید ارسال» را نشان دهد، نه «مدل در حال کار».
- Workbench زمان واقعی ارسال در وب‌سایت مدل را نمی‌داند؛ Timestamp ارسال بر اساس زمان تأیید کاربر ذخیره می‌شود.
- پاسخ فقط زمانی `response_received` است که در Workbench وارد شده باشد.
- `verified_done` فقط از سیاست پذیرش و Evidence حاصل شود، نه از یک متن مدل یا کلیک «پاسخ خوب است» مگر سیاست Task به‌طور روشن Manual Review باشد.

### ۹.۳. جلوگیری از تداخل و خروجی‌های دیررس

- پاسخ هر Attempt به همان `attempt_id` و `task_id/task_revision` متصل شود.
- Attempt قدیمی حفظ شود، اما خودکار Active Attempt جدیدتر را جایگزین نکند.
- اگر دو Agent یک فایل/Scope را تغییر داده‌اند، خروجی‌ها ابتدا به‌صورت Candidate مستقل بمانند.
- پاسخ یک Task نباید اشتباهاً به Task دیگری import شود.
- اگر State/Scope از زمان ساخت پرامپت تغییر کرده، stale check و Reconcile لازم باشد.
- هر بازکاری با `parent_attempt_id` به Attempt قبلی وصل شود؛ چرخهٔ Repair بی‌نهایت مجاز نباشد.

## ۱۰. Dashboard تیم و صف اقدام‌های موردنیاز

### ۱۰.۱. هدف

برای پروژه با ۴ تا ۱۰ Agent، کاربر نباید مجبور شود تک‌تک چت‌ها و پنل‌ها را باز کند تا وضعیت کلی را بفهمد. Team Dashboard باید مهم‌ترین اطلاعات را جمع کند و Items نیازمند اقدام را جلوتر نشان دهد.

### ۱۰.۲. اجزای داشبورد

- نوار وضعیت پروژه: تعداد Taskهای تأییدشده، درحال کار، در انتظار پاسخ، مسدود و نیازمند اقدام.
- فهرست Agentها: نقش، Account Profile/Chat Binding منتخب، Taskهای مالکیت‌یافته، آخرین Event، وضعیت گردش‌کار و تعداد موارد نیازمند توجه.
- صف `Needs Attention`: پاسخ‌های نامعتبر/ناقص، Handoffهای stale، تصمیم‌های باز، Context Requestهای نیازمند فایل، Build/Test شکست‌خورده، Publication خطادار و موارد منتظر تأیید.
- نمای Taskهای موازی و Taskهای مسدود با علت.
- پنل آخرین فعالیت با رویدادهای واقعی و لینک به جزئیات.
- فیلتر بر اساس نقش، وضعیت، Account Profile، Task، اولویت، ریسک و Milestone.
- عمل‌های سریع زمینه‌ای مانند «بازکردن پاسخ»، «آماده‌سازی Repair Prompt»، «ساخت Context Pack»، «بازبینی Handoff»، «تغییر چت» یا «گزارش به مدیر پروژه»؛ فقط وقتی برای مورد انتخاب‌شده معتبر باشند.

### ۱۰.۳. الگوریتم اولویت‌دهی

صف اقدام‌ها باید از منابع قطعی موجود شروع کند:

1. موارد مسدودکننده/نیازمند تصمیم انسانی؛
2. خروجی‌های stale یا پاسخ مربوط به Task اشتباه؛
3. پاسخ خراب/ناقص که مسیر اصلاح دارد؛
4. Handoff/Proposal منتظر بازبینی؛
5. Task آمادهٔ شروع که نیاز به تخصیص یا ساخت پرامپت دارد؛
6. انتشار وضعیت/اعتبارسنجی معوق؛
7. اطلاعات غیرضروری و اطلاع‌رسانی.

قواعد اولویت باید قطعی و توضیح‌پذیر باشد. داشبورد باید بگوید چرا یک مورد بالا آمده است؛ رتبه‌بندی opaque یا امتیازدهی بی‌توضیح پذیرفته نیست.

### ۱۰.۴. کنترل شلوغی در پروژه‌های بزرگ

- با ۱ تا ۳ Agent: کارت‌های ساده و خلاصه کافی باشد.
- با ۴ تا ۶ Agent: فیلتر، گروه‌بندی نقش و خلاصه‌های وضعیت لازم است.
- با ۷ تا ۱۰ Agent: فهرست فشرده، گروه‌بندی/جست‌وجو و صف اقدام‌های اولویت‌دار پیش‌فرض شود؛ همهٔ پنل‌ها باز نباشند.
- این اعداد قواعد UX پیشنهادی‌اند، نه محدودیت فنی تعداد Agentها.
- Dashboard نباید برای هر رویداد یا هر Agent popup بزند. فقط خطای Blocking می‌تواند هشدار برجسته بگیرد؛ بقیه در صف جمع شوند.
- کاربر باید بتواند اعلان‌ها را خلاصه کند، فیلتر کند یا خوانده‌شده علامت بزند، بدون اینکه رویداد تاریخی حذف شود.

## ۱۱. موازی‌سازی، Scope و تخصیص کار

### ۱۱.۱. معیار موازی‌سازی

Task فقط زمانی برای شروع موازی پیشنهاد شود که:

- تمام وابستگی‌های ضروری آن آماده‌اند؛
- محدوده‌های فایل/ماژول با Task هم‌زمان تداخل ندارند یا قرارداد مرزی مشخص است؛
- تصمیمات لازم پذیرفته شده‌اند؛
- خروجی و Acceptance Criteria مشخص است؛
- در صورت اشتراک فایل، برنامهٔ بازبینی/ادغام مشخص وجود دارد.

سرویس موجود `parallel_candidates()` و `scopes_overlap()` نقطهٔ شروع‌اند، نه تضمین کامل تشخیص تداخل. تطبیق glob و Scope ممکن است محافظه‌کارانه یا ناقص باشد؛ Roadmap باید مرزها را با تست آشکار کند و هر مورد نامطمئن را «نیازمند بررسی» بداند.

### ۱۱.۲. تخصیص Task

- هر Task یک `owner_agent_id` مشخص داشته باشد یا صریحاً `unassigned` باشد.
- `reviewer_agent_ids` برای بازبینی قابل تعیین باشند.
- تخصیص پیشنهادی مدیر پروژه از تخصیص پذیرفته‌شده جدا باشد.
- Workbench قبل از ساخت پرامپت، فعال بودن Agent، Account Profile و Chat Binding لازم را بررسی کند.
- تغییر مالک Task باید Event بسازد و تاریخچه Attempts قبلی را دست‌نخورده نگه دارد.
- Agent غیرفعال یا Account Profile از دسترس خارج شده، Task را خودکار تکمیل/لغو نکند؛ مورد در صف نیازمند تخصیص جدید بیاید.

### ۱۱.۳. محدودیت موازی‌سازی دستی

با توجه به کپی/پیست، «موازی» در Workbench یعنی چند Task مستقل می‌توانند هم‌زمان وضعیت `waiting_for_response` یا `ready` داشته باشند؛ نه اینکه Workbench واقعاً چند درخواست مدل را هم‌زمان ارسال کرده باشد. UI باید این تفاوت را نشان دهد و کاربر بتواند صف دستی خود را مدیریت کند.

### ۱۱.۴. جلوگیری از تولید پرامپت‌های تکراری

- یک Task/Attempt فعال باید شناسه و نسخهٔ واضح داشته باشد.
- دکمهٔ تولید مجدد باید بگوید «ساخت Attempt جدید»، «بازسازی پرامپت فعلی» یا «اصلاح پاسخ»، نه اینکه همه را یک کار کند.
- اگر Task در انتظار پاسخ است و کاربر دوباره Start می‌زند، برنامه هشدار دهد و انتخاب مشخص بخواهد.
- تغییر Prompt/Task revision باید ارتباط با Attempt پایه را حفظ کند.
- پرامپت یک Agent نباید بدون دلیل با Prompt Agent دیگری یکی شود؛ برای هر Agent، نقش، مأموریت و فرمت تحویل مرتبط در Prompt مشخص باشد.

## ۱۲. ادغام با جریان‌های فعلی: شروع، اصلاح، توسعه و Context Request

این بخش برای حل سردرگمی اصلی کاربر ضروری است و باید از ابتدا در طراحی GUI لحاظ شود.

### ۱۲.۱. ساخت پروژه

در آغاز، کاربر نباید با فهرستی طولانی از تنظیمات فنی روبه‌رو شود. یک جریان مرحله‌ای کوتاه ارائه شود:

1. «می‌خواهی چه چیزی بسازی یا تغییر دهی؟»
2. موفقیت پروژه از نظر کاربر چیست؟
3. محدودیت‌های مهم و پلتفرم/فناوری در صورت معلوم بودن.
4. Account Profileها و سقف چت‌های هم‌زمان (اختیاری در شروع؛ قابل تکمیل بعداً).
5. انتخاب یا پیشنهاد مدیر پروژه.
6. ساخت Planning Prompt و توضیح اینکه اکنون باید آن را به چت مدیر پروژه بدهی.

فیلدهای فنی پیشرفته در «Project details» باشند و کاربر بتواند آن‌ها را بعداً تکمیل کند. اطلاعاتی که برای شروع ضروری نیستند، آغاز کار را متوقف نکنند.

### ۱۲.۲. اصلاح خروجی همین Task

اگر پاسخ خراب/ناقص است، مسیر اصلی باید به Response Inbox و Repair هدایت کند. UI باید مشخص کند:

- چه پاسخ/Attemptی دریافت شده؛
- چه چیزهایی سالم‌اند و حفظ می‌شوند؛
- چه چیزهایی گم‌شده/نامعتبرند؛
- آیا پاسخ متعلق به Task جاری است؛
- آیا State قدیمی شده؛
- پرامپت اصلاحی کجاست و چه کاری را باید دوباره به مدل بدهی.

Repair باید Attempt جدیدِ مرتبط ایجاد کند و فایل‌های سالم را بی‌دلیل دوباره درخواست نکند.

### ۱۲.۳. توسعه قابلیت جدید

وقتی کاربر می‌گوید «خروجی خوب است، حالا این قابلیت را اضافه کن»، UI باید مسیر انتخابی روشن بدهد:

- **گسترش Task جاری:** اگر در محدوده و معیارهای همین Task است، Revision جدید بسازد و اثر روی Attemptهای قبلی را مشخص کند.
- **Task جدید:** اگر هدف یا تحویل مستقل است، Task جدید بسازد و وابستگی‌ها را روشن کند.
- **درخواست Re-plan از مدیر پروژه:** اگر تغییر بر معماری، چند Task یا Scope کلی اثر می‌گذارد.

Workbench می‌تواند بر اساس متن کاربر پیشنهاد دهد کدام مسیر مناسب‌تر است، اما در موارد مبهم یک سؤال کوتاه بپرسد یا انتخاب را شفاف کند؛ نباید با حدس بی‌صدا Task جاری را تغییر دهد.

### ۱۲.۴. پاسخ مدل درخواست زمینه دارد

- `AIWB_CONTEXT_REQUEST` باید از مسیر موجود تشخیص داده شود.
- UI با زبان روشن بگوید مدل چه فایل/خط/نمادی را درخواست کرده و علت اعلام‌شده چیست.
- مسیرها و اندازه‌ها اعتبارسنجی شوند؛ فایل‌های حساس به‌طور پیش‌فرض مستثنا باشند.
- متن inline یا ZIP آماده شود؛ Manifest شامل فایل‌ها، روش استخراج، محدودهٔ خطوط و Hashهای لازم باشد.
- UI کاملاً واضح بگوید «آماده شد؛ هنوز به چت ارسال نشده است».
- پس از تأیید کاربر، فقط وضعیت خوداظهاری «ارسال شد» ثبت شود.
- درخواست آزاد متنی مدل را می‌توان با Heuristic تشخیص داد، اما قبل از آماده‌سازی باید در موارد مبهم تأیید کاربر خواسته شود.

### ۱۲.۵. چت جدید/Agent جدید

یک عمل واحد مانند «Prepare handoff / آماده‌سازی انتقال» باید:

- هدف Task، معیار پذیرش، تصمیمات قبول‌شده، خروجی‌های موردنیاز و وضعیت قبلی را جمع کند؛
- Attempt/Handoff تازه با شناسه پایدار بسازد؛
- وضعیت خواندن Project State از GitHub را از ادعای مدل جدا کند؛
- اگر Snapshot/فایل‌های موردنیاز در دسترس نیستند، خلاصهٔ جایگزین یا Context Pack فراهم کند؛
- توضیح دهد کدام متن را باید در چت مقصد بفرستی و کدام فایل‌ها را باید ضمیمه کنی.

## ۱۳. Simple/Advanced و نمایش تدریجی جزئیات

### ۱۳.۱. تصمیم طراحی

پیشنهاد می‌شود «حالت ساده» و «حالت پیشرفته» دو رابط متفاوت با مسیرهای متفاوت نباشند. یک Workspace و یک منبع داده/منطق مشترک داشته باشیم که جزئیات بر اساس نیاز آشکار شوند.

- **Default / Focused:** برای کار روزمره؛ وضعیت پروژه، Next Action، Taskهای مهم و پنل منتخب.
- **Advanced Details:** برای مشاهدهٔ Revision، Agent ID، Attempt/Handoff ID، Evidence، Proposal، State Revision و Publish History.
- **Expert tools:** عملیات Git/Build/داده‌های تشخیصی در بخش ابزارهای تخصصی، نه جلوی چشم همیشه.

تنظیم نمای کاربر می‌تواند ذخیره شود؛ تغییر View نباید State پروژه، Revision یا Publish ایجاد کند.

### ۱۳.۲. قواعد UX

- هر نمای اصلی یک هدف روشن و یک اقدام اولیه داشته باشد.
- دکمه‌های کم‌کاربرد به منو/overflow منتقل شوند.
- برچسب دکمه باید فعل + نتیجه داشته باشد؛ «Import answer» بهتر است در Context مناسب با توضیح «بررسی و ثبت پاسخ» همراه شود.
- وضعیت‌ها فقط با رنگ نشان داده نشوند؛ متن و نشانه/آیکون هم استفاده شوند.
- خطا باید علت، اثر، آنچه حفظ شده و قدم بعدی را نشان دهد.
- Confirm Dialog برای خطر واقعی لازم است، نه هر کلیک کوچک.
- کنترل‌هایی که در وضعیت فعلی قابل استفاده نیستند، غیرفعال با دلیل یا اصلاً مخفی باشند.
- اصطلاحات تخصصی مثل Attempt/Handoff/State Revision در UI پیش‌فرض ترجمه/شرح ساده داشته باشند؛ در Advanced جزئیات فنی موجود بماند.
- ترجمهٔ فارسی باید RTL، ترتیب آیکون و متن، اعداد/شناسه‌ها و کنترل ترکیبی فارسی/انگلیسی را درست مدیریت کند.

### ۱۳.۳. زبان و تم

- فارسی و انگلیسی به‌عنوان زبان‌های پشتیبانی‌شده حفظ شوند.
- مسیر RTL در فارسی به شکل واقعی آزمایش شود، نه فقط ترجمه متن.
- Light/Dark Theme می‌تواند در Scope این Roadmap باشد، مشروط بر آنکه کنتراست، خوانایی وضعیت‌ها و رفتار نمودارها در هر دو درست باشد.
- رنگ تنها حامل معنا نباشد؛ وضعیت موفق/شکست/در انتظار باید متن و نشانه داشته باشد.
- از انیمیشن‌های تزئینی سنگین و افکت‌هایی که عملکرد/خوانایی را کم می‌کنند اجتناب شود.

## ۱۵. انتخاب فناوری UI: تصمیم با آزمایش، نه سلیقه

GUI فعلی Tkinter است. برای محیط کاری گرافیکی پیچیده‌تر، PySide6/Qt Widgets نامزد جدی بررسی است، اما این Roadmap مهاجرت قطعی یا بازنویسی یکباره را از ابتدا تحمیل نمی‌کند.

### ۱۵.۱. فناوری‌هایی که باید مقایسه شوند

- **Tkinter/ttk ارتقایافته:** حفظ Python و حجم/پیچیدگی کمتر، با بازطراحی Layout، تم، Sidebar، Inspector و Canvas/Timeline سفارشی.
- **PySide6 / Qt Widgets:** ابزارهای قوی‌تر برای Dockable Panels، Model/View، Layout، DPI و گرافیک سفارشی، با هزینهٔ بسته‌بندی و مهاجرت بیشتر.

### ۱۵.۲. مرحلهٔ Spike اجباری

پیش از انتخاب، یک نمونهٔ کوچک اما واقعی ساخته شود که شامل این اجزا باشد:

- پوسته با Sidebar، Central Workspace و Inspector؛
- یک Timeline با حداقل چند ده Event، انتخاب Event و فیلتر؛
- یک فهرست Task/Agent؛
- نمایش فارسی RTL و انگلیسی؛
- پنجره با Resize و DPI Scaling؛
- اجرای مستقیم از سورس و بسته‌بندی نمونه در Installer آزمایشی.

### ۱۵.۳. معیارهای تصمیم

| معیار | روش بررسی |
|---|---|
| زمان Cold Start و Open Project | اندازه‌گیری روی یک دستگاه مرجع با شرایط ثبت‌شده |
| مصرف حافظه در Idle و پروژه بزرگ | اندازه‌گیری و مقایسه با نسخه فعلی |
| اندازه بسته نصب | اندازه‌گیری Installer/Payload و میزان تغییر نسبت به فعلی |
| کیفیت Layout/DPI/RTL | اجرای سناریوهای ماتریس Section 14 |
| ساخت Timeline و تعاملات زیاد | انتخاب/فیلتر/اسکرول با دیتای آزمایشی حجیم |
| دشواری حفظ سازگاری | بررسی اینکه منطق سرویس‌ها بدون تغییر قابل استفاده است |
| CI، نصب، ارتقا و Rollback | PoC در Windows CI/Runner و تست Installer |
| نگهداری آینده | پیچیدگی UI، تست‌پذیری، کیفیت ساختار کامپوننت‌ها |

تصمیم باید در ADR ثبت شود. اگر Qt ارزش محسوس و مستند ایجاد نکرد، Tkinter را می‌توان نگه داشت. اگر Qt انتخاب شد، فقط لایهٔ GUI مرحله‌ای عوض شود؛ Task/V2/Inbox/GitHub/Companion از نو نوشته نشوند.

## ۱۶. معماری پیشنهادی و مرزهای ماژول

### ۱۶.۱. ساختار منطقی

- **Domain/Services موجود:** V2 Models/Store، Agent Registry، Task Service، Proposal Service، Handoff Service، Evidence/Decision، Response Inbox، Context Request، Publisher و GitHub/Build.
- **Workspace Application Controller:** ارائهٔ Read Model مشترک به UI؛ تجمیع `next_actions`, task rows, team summary, timeline query, progress metrics و warning queue. این Controller نباید منطق دامنه را دوباره پیاده کند.
- **Presentation Shell:** Navigation، Workspace، Inspector، Status/Activity و Dialogهای زمینه‌ای.
- **Timeline Query/Projection:** خواندن Event Ledger، فیلتر، گروه‌بندی و ارائهٔ نقاط؛ بدون نوشتن داده از طریق View.
- **Team Planner Adapter:** ساخت Planning Prompt و اعتبارسنجی Team Proposal؛ استفاده از Proposal Service فعلی و قرارداد نسخه‌دار.
- **Account/Chat Registry:** ثبت محلی منابع و Bindingها؛ بدون اعتبارنامهٔ سرویس مدل.
- **Workflow State Projection:** نمایش دقیق وضعیت هر Attempt/Agent از State داخلی Workbench.

### ۱۶.۲. اصول مرز ماژول‌ها

- UI مستقیماً فایل State یا JSONهای پروژه را دستکاری نکند؛ فقط Services/Controllers مرکزی.
- تمام تغییرات State از Transaction/Migration نسخه‌دار استفاده کنند.
- UI یک منطق جدا برای Done/Progress نسازد.
- Actionهایی که در Next Action موجودند باید از همان منطق استفاده کنند یا با دلیل مستند گسترش یابند.
- Timeline نباید منبع حقیقت دوم برای وضعیت جاری بسازد؛ Event Ledger تاریخچه است، Current State از Store/Services موجود می‌آید.
- Read Modelهای داشبورد باید ترکیبی و قابل تست باشند.
- عملیات IO شبکه، GitHub، Build، ZIP حجیم و پردازش طولانی در Thread/Task پس‌زمینه انجام شود؛ تغییر UI با Dispatch امن به Thread UI انجام گیرد.
- شکست خواندن Timeline یا یک History نباید State اصلی پروژه را پاک یا بازنویسی کند.

### ۱۶.۳. مهاجرت داده

- هر فیلد/Collection جدید Schema Version داشته باشد.
- Migration قبل از تغییر Backup بسازد، idempotent باشد و دادهٔ ناشناختهٔ موجود را حفظ کند.
- `preferred_model_label` قدیمی به‌عنوان Label legacy حفظ شود؛ تبدیل آن به Account Profile فقط با Migration روشن و قابل بازگشت/بررسی باشد.
- پروژه‌هایی که Account Profile تعریف نکرده‌اند همچنان باز شوند و مسیر قبلی Prompt/Response کار کند.
- Taskهای قدیمی باید بتوانند بدون Agent/Chat Binding به‌صورت legacy نمایش داده شوند.
- Eventهای قبلی را نباید با ساخت تاریخ‌های تخمینی به Timeline جدید تبدیل کرد؛ موارد بدون Event دقیق می‌توانند در بخش Legacy History با برچسب منبع/زمان نامشخص نمایش داده شوند.
- Rollback نسخهٔ جدید نباید دادهٔ ساخته‌شده را بی‌صدا حذف کند؛ سیاست downgrade باید مستند باشد.

## ۱۷. Performance و حفظ سبکی برنامه

### ۱۷.۱. اصل کلی

ظاهر مدرن نباید به معنی انیمیشن دائمی، مرورگر داخلی حجیم، بارگذاری تمام تاریخچه هنگام هر کلیک یا قفل‌شدن UI شود. در ابتدا بودجه عملکرد نسخه فعلی روی دستگاه مرجع اندازه‌گیری شود و آستانه‌های نهایی با شواهد تعیین شوند.

### ۱۷.۲. اهداف اولیه پیشنهادی برای PoC

این اهداف باید بعد از اندازه‌گیری Baseline بازبینی شوند و تا قبل از تصویب به‌عنوان ضمانت قطعی تبلیغ نشوند:

- تعاملات معمول محلی (تعویض نما، انتخاب Task، باز/بسته‌کردن Inspector) در حالت عادی بدون مکث محسوس؛ هدف اولیه P95 زیر 100ms برای بخش synchronous UI، بدون احتساب کار شبکه/IO.
- Open Project معمولی، با اندازهٔ مرجع ثبت‌شده، هدف اولیه زیر 1 ثانیه پس از آغاز بارگذاری؛ اگر روی سخت‌افزار مرجع واقع‌بینانه نبود، هدف نهایی با Baseline عددگذاری شود.
- Timeline در پروژه بزرگ، ابتدا فقط محدوده/صفحهٔ لازم را render کند؛ هدف اولیه نمایش 200 Event قابل‌مشاهده در کمتر از 500ms روی دستگاه مرجع، سپس بهینه‌سازی براساس اندازه‌گیری.
- ساخت Prompt محلی باید از پاسخ‌گرفتن از مدل مستقل باشد؛ Workbench نباید برای تولید متن Prompt منتظر ChatGPT/Gemini بماند.
- انتشار وضعیت GitHub، بررسی remote، Build و عملیات حجیم، UI thread را متوقف نکنند.
- بازخورد فوری پس از کلیک: Loading/Running/Waiting/Failed واضح باشد و عملیات طولانی قابل لغو باشد، جایی که لغو واقعی ممکن است.

### ۱۷.۳. اقدامات فنی

- محاسبه فیلتر/Projection سنگین خارج از UI thread انجام شود.
- Timeline با Pagination/Virtualization یا Windowing طراحی شود؛ تمام Eventها هم‌زمان در Widget ایجاد نشوند.
- Cache فقط برای Read Modelهایی استفاده شود که Invalidation آن‌ها روشن است.
- از Polling داخلی برای مدل‌ها خودداری شود؛ چنین دسترسی‌ای وجود ندارد. فقط وضعیت‌هایی مثل Publisher موجود و عملیات محلی قابل‌پایش‌اند.
- لاگ/رویدادهای زیاد در GUI با batching افزوده شوند.
- از ساخت‌های سنگین Theme/Canvas در هر Refresh اجتناب شود.
- مصرف حافظه/زمان و حجم بستهٔ نصب در هر Release Candidate مقایسه شود.

## ۱۸. مراحل اجرایی پیشنهادی

**شماره نسخه‌ها صرفاً پیشنهاد است.** بعد از بررسی نسخهٔ فعلی و تصویب ADR، برنامه‌نویس می‌تواند آن‌ها را با شماره‌های release در Roadmap اصلی هم‌تراز کند. بهتر است هر مرحله یک مسیر انتهابه‌انتها و Gate واضح داشته باشد؛ نه اینکه چند زیرسیستم بزرگ بدون سنجش میان آن‌ها با هم بازنویسی شوند.

### مرحله 0 — Discovery، UX Flow و ADR

**هدف:** به توافق رسیدن بر سر معماری UX، منابع، معنای Status و فناوری GUI قبل از پیاده‌سازی گسترده.

**کارها:**

- اجرای Audit کد فعلی `main` و ثبت فایل‌ها/سرویس‌هایی که reuse می‌شوند.
- ساخت نقشهٔ جریان فعلی از ایجاد پروژه تا Planning، Task، Prompt، پاسخ، Repair، Context Request، Review و Version.
- تعریف ۵ سناریوی کاربر: پروژه تازه، پاسخ ناقص، گسترش قابلیت، چت جدید/زمینه، پروژه چند Agent.
- وایرفریم Low-Fi برای Overview، Timeline، Task Inspector، Team Dashboard و Team Planner.
- تعریف مدل مفهومی Agent/Account/Chat/Task/Attempt/Milestone/Version و وضعیت ارسال دستی.
- اندازه‌گیری Performance Baseline و حجم Installer فعلی.
- ایجاد ADR برای انتخاب فناوری GUI و مدل Timeline/Event Ledger.

**Deliverables:**

- ADR ثبت‌شده؛
- نقشه جریان UX و وایرفریم؛
- جدول موجود/جدید/حذف‌شدنی برای UI فعلی؛
- گزارش Baseline عملکرد و بسته‌بندی؛
- تصمیم درباره event history و مهاجرت داده.

**معیار پذیرش:**

- هیچ کد هسته‌ای قبل از تصمیم دربارهٔ reuse و Migration دوباره نوشته نشود.
- همه وضعیت‌های UI تعریف روشن داشته باشند.
- تعامل دستی با مدل‌ها و نبود API به‌عنوان شرط طراحی ثبت شده باشد.
- برنامه‌نویس و مالک محصول درباره نسخه‌های اولیه و Gateها توافق کرده باشند.

### مرحله 1 — UI Technology Spike و Design System

**هدف:** انتخاب فناوری با تست واقعی، نه حدس.

**کارها:**

- ساخت PoC یک Workspace با Sidebar، Timeline کوچک، Task list و Inspector.
- مقایسهٔ Tkinter/ttk ارتقایافته و PySide6 در صورت توجیه.
- طراحی Design Tokens: رنگ، فونت، فاصله، radius، اندازه آیکون، وضعیت و Severity.
- بررسی Light/Dark، RTL فارسی، LTR انگلیسی و DPI.
- اندازه‌گیری start time، memory، Installer Size و عملکرد Timeline آزمایشی.

**Deliverables:** PoC قابل اجرا، گزارش مقایسه، Design System اولیه و ADR نهایی GUI.

**معیار پذیرش:**

- انتخاب فناوری مستدل و ثبت‌شده باشد.
- PoC در اندازه‌های آزمون خارج از کادر نرود.
- اگر Qt انتخاب شد، اثبات شود بسته‌بندی و نصب ویندوز قابل نگهداری است.
- UI نهایی از منطق دامنه فعلی جدا بماند.

### مرحله 2 — مدل دادهٔ Event، Account Profile و Chat Binding

**هدف:** ایجاد پایه داده‌ای برای Timeline و مدیریت منابع بدون شکستن پروژه‌های موجود.

**کارها:**

- تصمیم و پیاده‌سازی Event model نسخه‌دار و نگهداری پایدار.
- ثبت Eventهای حوزه Task/Attempt/Handoff/Decision/Evidence/Publish که در سرویس‌های موجود رخ می‌دهند.
- Account Profile و Chat Binding schema/service.
- ارتباط Chat Binding و Account Profile به Agent/Attempt در حد لازم.
- Migration از `preferred_model_label` و دادهٔ قدیمی بدون حذف/حدس.
- Redaction و عدم ذخیره Credential یا Prompt خام غیرضروری در Event Log.
- تست event idempotency و مرزبندی State/Event.

**Deliverables:** schema/migration، سرویس‌های داده، قراردادهای تست و مستندات فیلدها.

**معیار پذیرش:**

- پروژه‌های قدیمی بدون Account Profile باز شوند.
- وضعیت Task از Event Log محاسبه و overwrite نشود؛ Current State همان Store اصلی بماند.
- تغییر تنظیم رابط Event پروژه نسازد.
- هیچ رمز، token، Cookie یا key مدل در Account Profile/Chat Binding قرار نگیرد.
- رویداد فقط پس از عملیات/تأیید واقعی ثبت شود.

### مرحله 3 — پوستهٔ اصلی و Responsive Workspace

**هدف:** ساخت قاب اصلی یکپارچه و دسترسی متمرکز به قابلیت‌های موجود.

**کارها:**

- پیاده‌سازی Title/Project Bar، Sidebar، Workspace، Inspector و Next Action.
- ادغام/دسترسی روشن به Projects، Response Inbox، Context Request، GitHub/Build و Versions، به‌جای نشان‌دادن همه کنترل‌ها همیشه.
- Contextual action bar؛ تنها عملیات معتبر در انتخاب جاری نمایش داده شوند.
- منطق Collapse/Expand پنل‌ها و تغییر چیدمان در عرض کم.
- پشتیبانی فارسی RTL و انگلیسی LTR در پوسته.
- نگهداری تنظیم Layout کاربر بدون تغییر Project State.

**Deliverables:** Workspace قابل اجرا با Navigation و اتصال به Controller/Services موجود.

**معیار پذیرش:**

- مسیرهای موجود از دسترس خارج یا دوباره‌پیاده‌سازی نشده باشند.
- تغییر نما داده پروژه را تغییر ندهد.
- در حداقل ماتریس اندازه/DPI مرحله 0، همه اقدامات اصلی قابل دسترسی باشند.
- برنامه از نظر زمان پاسخ به تعاملات محلی از Baseline بدتر نشود مگر با دلیل و مصوبه ADR.

### مرحله 4 — Team Planner و تخصیص Agent/Account/Chat

**هدف:** مدیر پروژه یک پیشنهاد تیم واقعی بر اساس منابع واردشده بسازد و کاربر بتواند آن را بررسی کند.

**کارها:**

- افزودن Account Profile manager UI و Chat Binding UI.
- انتخاب/ویرایش مدیر پروژه؛ مدیر می‌تواند به مدل مورداعتمادتر کاربر اختصاص داده شود.
- افزودن به Planning Prompt اطلاعات منابع و سؤال صریح دربارهٔ تعداد/نقش Agentها و برنامهٔ موازی.
- گسترش قرارداد Team Proposal: تعداد، نقش‌ها، Taskها، تخصیص‌ها، Scope، وابستگی، گروه‌های موازی، ریسک‌ها و توضیح اندازه تیم.
- اعتبارسنجی Proposal با نقش‌ها/Agentهای واقعی و منابع ثبت‌شده.
- Review UI برای پذیرش کل/انتخابی، رد، تغییر و درخواست اصلاح.
- تعیین حداکثر چت‌های هم‌زمان مورد نظر کاربر.

**Deliverables:** Team Planner، schema Proposal به‌روز، Account/Chat Registry و تست‌های سازگاری.

**معیار پذیرش:**

- مدیر پروژه نمی‌تواند از خودش Account Profile ناموجود بسازد و آن را به‌عنوان منبع واقعی معرفی کند.
- تعداد Agentها و اینکه PM شمرده شده یا نه، صریح باشد.
- پیشنهاد Task شامل Owner/Scope/Acceptance Criteria/Dependencies باشد یا موارد ناقص روشن باشند.
- هیچ Proposal بدون Review کاربر روی State اعمال نشود.
- اگر از منابع فقط یک Account Profile در دسترس است یا تعداد چت‌های موازی محدود است، پیشنهاد تیم این محدودیت را لحاظ کند.
- قرارداد قدیمی Proposal و پروژه‌های فعلی با Migration/test سازگار بمانند.

### مرحله 5 — Workflow Tracking و عملیات دستی چند Agent

**هدف:** وضعیت گردش‌کار هر Agent/Attempt از روی رویدادهای واقعی Workbench قابل پیگیری شود.

**کارها:**

- تعریف انتقال وضعیت‌های ارسال دستی، پاسخ، Repair، Context Pack، Review و Validation.
- اتصال Attempt/Handoff به Agent، Account Profile و Chat Binding مناسب.
- `Copy prompt` از `User confirmed sent` جدا شود.
- UI برای «ارسال را تأیید کن»، «پاسخ را وارد کن»، «پاسخ ناقص است»، «Repair آماده کن»، «Context آماده کن» و «تغییر چت» در Context مناسب.
- جلوگیری از Start تکراری در Attempt فعال بدون هشدار و انتخاب صریح.
- حفظ پاسخ دیررس/stale و عدم اتصال آن به Task اشتباه.
- اتصال همه پاسخ‌ها به Response Inbox موجود.

**Deliverables:** Workflow state service/projection، عملیات دستی روشن و تست‌ها.

**معیار پذیرش:**

- Workbench هرگز صرف کپی‌شدن Prompt را ارسال قطعی تلقی نکند.
- وضعیت داخلی مدل را ادعا نکند.
- Attemptهای تکراری/پاسخ قدیمی به صورت قابل trace نگهداری شوند.
- پاسخ خراب به صف اقدام‌ها و مسیر Repair هدایت شود.
- Context آماده‌شده با Context ارسال‌شده متفاوت باقی بماند.

### مرحله 6 — Timeline، Task Lanes و Project Overview

**هدف:** مشاهدهٔ گذشته، وضعیت اکنون و برنامهٔ آینده در یک نمای روشن.

**کارها:**

- Timeline از Event Ledger با فیلتر و گروه‌بندی.
- نمای خطی ساده؛ نمای پیشرفته با Laneهای Agent/جریان کار در صورت مفید بودن.
- بازکردن جزئیات Task/Attempt/Handoff/Evidence از Event منتخب.
- Milestone و Version به‌عنوان موجودیت‌های مستقل و قابل‌پیگیری.
- نمایش Commit/Build/Artifact/Release وقتی واقعاً وجود دارند.
- پیشرفت مبتنی بر Taskهای تأییدشده و متریک‌های توضیح‌پذیر.
- مدیریت Eventهای legacy با برچسب صریح دادهٔ قدیمی/نامعلوم.
- فیلتر بر اساس بازه زمانی، Agent، Task، Status، Milestone، Version و Evidence.

**Deliverables:** Timeline، Project Overview و اتصال داده‌ها به Milestone/Version.

**معیار پذیرش:**

- Timestamp یا وضعیت تخمینی به‌عنوان رویداد واقعی جعل نشود.
- Task، Attempt، Milestone و Version با هم قاطی نشوند.
- پیشرفت Task بر اساس Status/Evidence محاسبه شود، نه گزارش متنی مدل.
- تغییر رابط/فیلتر Event تاریخی جدید نسازد.
- در Dataset بزرگ، UI با Virtualization/Pagination پاسخ‌گو بماند.

### مرحله 7 — Team Operations Dashboard و Needs Attention Queue

**هدف:** کم‌کردن کار دستی کاربر در پروژهٔ چند Agent.

**کارها:**

- جمع‌بندی وضعیت همهٔ Agentها و Taskها.
- صف اولویت‌بندی‌شدهٔ خطا/نیاز به تصمیم/پاسخ ناقص/کار stale/Context Request/Review/Validation/Publish.
- فیلتر گروهی و جست‌وجو در پروژه با ۱ تا ۱۰ Agent.
- خلاصه کردن رویدادهای تکراری و جلوگیری از Notification Storm.
- Actionهای مستقیم برای رفع مشکل، با باز کردن همان Inspector/Inbox item.
- نمایش دلیل اولویت و آنچه از کاربر لازم است.
- ارتباط Team Laneها با Timeline و Task Board.

**Deliverables:** Team Dashboard، صف اقدام‌ها و Read Model/Controllerهای قابل تست.

**معیار پذیرش:**

- کاربر با نگاه به Dashboard بفهمد کدام موارد واقعاً نیاز به اقدام دارند.
- خطای یک Agent در میان بقیه گم نشود.
- اطلاعات هر Agent/Task قابل trace تا Attempt و Response خام مربوطه باشد.
- با ۱۰ Agent، همه جزئیات به‌زور یکجا نشان داده نشوند.
- وضعیت داشبورد با Store/Controller مشترک همخوان باشد و منطق مستقل دوباره نسازد.

### مرحله 8 — یکپارچه‌سازی مسیر قدیمی و جدید و UI Polish

**هدف:** از بین بردن احساس دو برنامه جدا و ساده‌کردن سفر کاربر.

**کارها:**

- یکی‌کردن نقاط ورود برای ساخت Task، اصلاح پاسخ، گسترش پروژه و Context Request.
- ساخت راهنمای قدم بعدی متناسب با State.
- نمایش واضح مسیر «اصلاح همین Task» در برابر «Task جدید»/«Re-plan».
- استفادهٔ دوباره از Response Inbox/Repair/Context Request/Projects؛ ایجاد راه دوم با داده مستقل ممنوع.
- نهایی کردن تم، تایپوگرافی، آیکون، فاصله، حالات Empty/Loading/Error/Success و Microcopy.
- بازبینی فارسی RTL، انگلیسی LTR، کنتراست، فوکوس کیبورد و Tooltipها.

**Deliverables:** UX یکپارچه و نهایی‌سازی بصری.

**معیار پذیرش:**

- کاربر برای سناریوهای استاندارد از صفحهٔ فعلی مسیر بعدی را پیدا کند، بدون نیاز به شناخت اصطلاحات داخلی.
- ابزار تخصصی وقتی لازم است قابل دسترسی باشد اما همیشه مزاحم نباشد.
- هیچ workflow قدیمی بدون Migration/جایگزین روشن حذف نشود.

### مرحله 9 — Release Gate و Rollout

**هدف:** اثبات کیفیت محصول با سناریوی واقعی، نه فقط ظاهر یا Unit Test.

**کارها:**

- اجرای تست‌های واحد، Integration، GUI smoke و Windows Installer upgrade.
- سنجش عملکرد و مصرف حافظه/حجم Installer نسبت به Baseline.
- اجرای سناریوی End-to-End با حداقل دو مدل/چت مستقل؛ بدون API.
- اجرای Dataset آزمایشی با ۱۰ Agent، شکست‌های ساختگی، پاسخ دیررس و تداخل Scope.
- بررسی Migration، backup، restore و downgrade policy.
- تکمیل Release Checklist و مستندسازی موارد NOT RUN.

**Deliverables:** Release Gate، شواهد CI/GUI، چک‌لیست Windows و تصمیم انتشار.

**معیار پذیرش:** تمام Gates بخش ۲۰ پاس شوند. اگر آزمایش واقعی با سرویس مدل/گوشی/Windows اجرا نشده، صریحاً NOT RUN بماند.

## ۲۰. Release Gates و معیارهای پذیرش انتهابه‌انتها

### Gate A — شروع پروژه و Team Planning

سناریو: کاربر پروژه جدیدی می‌سازد، هدف را کوتاه توصیف می‌کند، چهار Account Profile محلی ثبت می‌کند و حداکثر دو چت هم‌زمان تعیین می‌کند.

قبولی وقتی است که:

- Workbench اطلاعات پروژه را بدون فرم بیش از حد پیچیده می‌گیرد.
- مدیر پروژه تعداد/نقش Agentها و علت پیشنهاد خود را ارائه می‌کند.
- پیشنهاد PM را با منبع‌های ثبت‌شده و محدودیت هم‌زمانی تطبیق می‌دهند.
- تعداد Agent کل و تعداد Workerهای اضافه به‌صورت مبهم شمارش نمی‌شوند.
- کاربر می‌تواند طرح را اصلاح یا بخشی از آن را بپذیرد.
- Taskها، Ownerها، Scopeها، معیارها و Dependencyها در State واقعی ایجاد می‌شوند و Graph معتبر است.

### Gate B — گردش کار چند Agent دستی

سناریو: حداقل دو Agent در دو چت معمولی مدل‌های مستقل کار می‌کنند.

قبولی وقتی است که:

- هر Prompt به Task/Attempt/Agent مشخص متصل است.
- Workbench وضعیت Prompt آماده/کپی‌شده/ارسال تأییدشده را قاطی نمی‌کند.
- دو پاسخ در Taskهای مستقل به مقصد درست وارد می‌شوند.
- پاسخ ناقص حفظ شده و فقط فایل‌های خراب/گم‌شده برای Repair درخواست می‌شوند.
- پاسخ قدیمی یا متعلق به Task دیگر با هشدار/مسیر Reconcile متوقف می‌شود.
- هیچ فایل صرف Import/Parse تغییر نمی‌کند.

### Gate C — ده Agent و Failure Triage

این Gate باید با Dataset ساختگی/آزمایشی پوشش داده شود؛ لازم نیست ده اکانت واقعی در CI وجود داشته باشند.

قبولی وقتی است که:

- داشبورد ۱۰ Agent را بدون شلوغی افراطی گروه‌بندی کند.
- اگر فقط دو مورد نیازمند اقدام هستند، همان دو مورد در صف ظاهر شوند.
- یک Agent با پاسخ ناقص، یک Agent با Handoff stale، یک Agent در انتظار کاربر و چند Agent آماده، قابل تفکیک باشند.
- هر Status دلیل/منبع قابل trace داشته باشد.
- Dashboard هیچ‌گاه وضعیت داخلی نامعلوم مدل را به‌عنوان واقعیت نشان ندهد.

### Gate D — Timeline و Progress Accuracy

قبولی وقتی است که:

- ایجاد Task، پاسخ، Repair، تصمیم، Evidence، Milestone و Version در زمان واقعی رویداد ثبت شود.
- Timestamp رویدادها با منبع معتبر برابر باشد؛ دادهٔ legacy مجهول برچسب داشته باشد.
- تکمیل Task با سیاست پذیرش و Evidence مرتبط محاسبه شود.
- یک Version می‌تواند چند Task را شامل شود و Task جدید به‌صورت خودکار Version نسازد.
- گزارش پیشرفت از تعداد Taskها جدا از وزن تخمینی برچسب بخورد.
- کلیک فیلتر، جابه‌جایی پنل یا تغییر زبان تاریخچهٔ پروژه را تغییر ندهد.

### Gate E — Responsive UI و Windows

قبولی وقتی است که:

- صفحهٔ اصلی و Dialogها در Resolution/DPIهای تعریف‌شده از Work Area بیرون نروند.
- هیچ اقدام اصلی زیر Taskbar یا خارج از قاب نامرئی نشود.
- Sidebar/Inspector در عرض کم قابل جمع‌شدن/تغییر چینش باشد.
- فارسی RTL و انگلیسی LTR از نظر متن، آیکون، شناسه و جدول قابل استفاده باشند.
- نصب تمیز، ارتقای نسخهٔ قبلی و حفظ تنظیمات/State در Windows CI یا محیط تعیین‌شده پاس شود.

### Gate F — Performance و Installer

قبولی وقتی است که:

- معیارهای Performance پس از Baseline ثبت و در Release با همان دستگاه/روش مقایسه شوند.
- UI thread حین IO/Publish/Build/پردازش سنگین قفل نشود.
- Timeline برای دیتاست بزرگ بارگذاری/فیلتر قابل‌قبول داشته باشد.
- مصرف حافظه، شروع برنامه و Installer Size با اعداد واقعی گزارش شوند.
- هر Regression مهم نسبت به Baseline یا اصلاح شده باشد یا با دلیل و پذیرش صریح ثبت شود.

### Gate G — امنیت، حریم خصوصی و داده

قبولی وقتی است که:

- Account Profile هیچ Token یا Credential مدل نداشته باشد.
- Event Ledger و Timeline به‌طور پیش‌فرض Prompt/Response خام و اطلاعات حساس را کپی نکنند.
- اگر Snapshot به GitHub Publish می‌شود، داده‌های منتشرشده Preview/Policy داشته باشند.
- مسیرهای فایل/Context Request همان اعتبارسنجی فعلی را حفظ کنند.
- پاسخ مدل هیچ‌گاه تنها منبع مجاز برای اجرای عمل خطرناک نباشد.
- migration و rollback داده‌های قدیمی را بی‌صدا حذف نکنند.

## ۲۱. برنامه تست و کیفیت

### ۲۱.۱. Unit/Contract Tests

- Account Profile validation، فعال/غیرفعال‌سازی و binding.
- نگاشت Agent ↔ Account/Chat بدون تغییر ID و تاریخچه.
- Proposal team schema، operationهای نامعتبر، Role/Agent ناموجود، forward refs و partial accept.
- Event schema، event idempotency، redaction و revision links.
- ماشین وضعیت Attempt/ارسال دستی و انتقال‌های نامعتبر.
- progress metrics با Taskهای Done/Blocked/Cancelled/Legacy و Evidence انواع مختلف.
- Timeline query: فیلتر، ترتیب زمانی، صفحه‌بندی و Event نامعتبر/قدیمی.
- Parallel candidate، Scope overlap، dependency cycle و conflict.
- migration از Schema قبلی، backup، اجرای دوبارهٔ migration و حفظ unknown fields.

### ۲۱.۲. Integration Tests

- Planning Prompt → Team Proposal → Review/Accept → Task Graph.
- Task → Attempt/Prompt → کپی → تأیید ارسال دستی → ورود پاسخ → Response Inbox → Handoff/Review.
- پاسخ ناقص → salvage → Repair Prompt → پاسخ اصلاحی.
- Context Request → resolve فایل/range/symbol → inline/ZIP → ثبت prepared/not sent.
- دو Task موازی در Scopeهای مستقل و دو Task با Scope مشترک.
- خروجی دیررس و Stale State.
- Milestone/Version → Commit/Build/Evidence linking.
- Timeline event feed ↔ current-state source بدون اختلاف.

### ۲۱.۳. GUI Smoke Tests

- New project flow و راهنمای قدم بعدی.
- باز/بسته‌کردن Sidebar/Inspector، Resize و جابه‌جایی نماها.
- انتخاب Task در Timeline و بازشدن Inspector درست.
- ورود به Agentی که Context Request یا Repair لازم دارد از Dashboard مستقیم.
- تغییر account/chat binding و آماده‌سازی Prompt صحیح.
- پذیرش/رد Team Proposal و دیدن Taskهای ایجادشده.
- رفت‌وبرگشت فارسی RTL و انگلیسی LTR.
- حالت Light/Dark در صورت پیاده‌سازی.
- صفحهٔ کوچک/Scale بالا/متن بلند.
- هیچ عملیات نمایشی نباید تغییر State ناخواسته بسازد.

### ۲۱.۴. Manual Acceptance

حداقل یک آزمون واقعی با دو چت مدل مستقل لازم است. مالک محصول باید این سناریو را اجرا کند:

1. پروژهٔ کوچک جدید.
2. مدیر پروژه یک Team Proposal بسازد.
3. کاربر طرح را اصلاح/تأیید کند.
4. دو Task مستقل با دو چت مختلف ساخته شوند.
5. پاسخ اول سالم و پاسخ دوم ناقص باشد.
6. Workbench پاسخ ناقص را هدایت به Repair کند.
7. کاربر بخواهد قابلیت جدیدی اضافه کند؛ UI فرق Task جدید و اصلاح Task فعلی را روشن کند.
8. چت جدید با Handoff و Context Pack آماده شود.
9. Timeline، Agent Dashboard و Progress یکسان و قابل فهم باشند.
10. کاربر بتواند از هر مرحله به «اقدام بعدی» برسد بدون مراجعه به Roadmap یا دستورالعمل توسعه.

نتیجه آزمون باید شامل نسخهٔ برنامه، مدل/چت‌های استفاده‌شده، موارد PASS/FAIL، Screenshot در صورت مناسب‌بودن و موارد NOT RUN باشد. نیازی به ثبت محتوای حساس چت یا حساب کاربر در GitHub نیست.

## ۲۲. ریسک‌ها و راهکارها

| ریسک | اثر | راهکار پیشنهادی |
|---|---|---|

| مهاجرت Qt Installer را بزرگ/کند کند | تجربهٔ نصب/شروع ضعیف | Technology Spike، اندازه‌گیری بسته و Benchmark پیش از ADR |
| داشبورد مدل را واقعاً Live جلوه دهد | اعتماد کاذب کاربر | وضعیت‌ها مبتنی بر رویدادهای Workbench و عبارت «ارسال تأییدشده توسط کاربر» |
| مدیر پروژه تعداد بیش‌ازحد Agent پیشنهاد دهد | بار مدیریت بیشتر از منفعت | Default تیم کوچک، سقف کاربر، تحلیل وابستگی/Scope و ارائه گزینهٔ ساده‌تر |
| Taskهای موازی یک فایل مشترک را تغییر دهند | تعارض و Merge پرریسک | Scope check، Candidate مستقل، Preview/Review و منع Merge خودکار |

| دو سیستم مدیریت کار در UI باقی بمانند | کاربر سردرگم شود | یک Current State و مسیرهای مشترک به Inbox/Task/Handoff |
| Timeline فقط وضعیت فعلی را به شکل تاریخچه عرضه کند | تاریخ ساختگی/گم‌شدن شواهد | Event Ledger واقعی، legacy واضح، بدون تولید تاریخ حدسی |
| Event Log بزرگ شود | کندی و رشد داده | Pagination/retention سیاست‌مند؛ نگهداری تاریخچه بدون قفل UI؛ تست پروژه حجیم |
| نشر ناخواسته اطلاعات به GitHub | نشت اطلاعات پروژه | Schema عمومی حداقلی، Preview/Publish Policy، Redaction؛ عدم نشر Prompt خام پیش‌فرض |

| پاسخ مدل خارج از قرارداد باشد | ورود داده نادرست | Raw-first Inbox، parser سخت‌گیر، خطای قابل‌فهم و Repair path |

## ۲۳. خارج از محدودهٔ این Roadmap

موارد زیر مگر با ADR جداگانه در محدوده نیستند:

- اتصال مستقیم API به GPT/Gemini/سایر مدل‌ها؛
- ورود خودکار به حساب مدل یا مدیریت Token/Cookie؛
- scraping پیام‌ها یا تشخیص خودکار تکمیل پاسخ در وب‌سایت مدل؛
- ارسال/دریافت خودکار پیام چت بدون تعامل کاربر؛
- اجرای Agent خودمختار پس‌زمینه‌ای که بدون دخالت انسان تصمیم و تغییر انجام دهد؛
- اجرای خودکار کد یا Apply تغییرات بدون بازبینی لازم؛
- Merge خودکار Candidateهای متعارض چند Agent؛
- تضمین کیفیت مدل بر اساس پولی/رایگان بودن حساب؛
- درصد اطمینان یا تخمین زمان/هزینهٔ دقیق بدون دادهٔ اندازه‌گیری‌شده؛
- مهاجرت اجباری به UI وب/Electron یا بازنویسی کامل Python Core؛
- تبدیل هر Task به یک Release؛
- نمایش همه جزئیات و تمام Agentها به شکل ثابت و بدون فیلتر.

## ۲۴. Definition of Done نهایی برای Roadmap

Roadmap فقط زمانی کامل اعلام شود که تمام موارد زیر با شواهد واقعی پاس شده باشند:

- [ ] ADR فناوری GUI، معماری Timeline/Event Ledger و تصمیم‌های Data Model تصویب شده باشد.
- [ ] محیط اصلی پروژه‌محور با Navigation، Workspace، Inspector و Next Action کار کند.
- [ ] Account Profile و Chat Bindingهای دستی بدون اعتبارنامهٔ مدل قابل مدیریت باشند.
- [ ] مدیر پروژه بتواند تیم و تقسیم کار پیشنهاد دهد و کاربر آن را به‌صورت انتخابی بپذیرد.
- [ ] تعداد Agent، تعداد Workerهای اضافی، تعداد Account Profileها و سقف چت هم‌زمان در UI مبهم نباشند.
- [ ] Taskها به Agent مناسب تخصیص یابند و Prompt/Attempt/Handoff/Response قابل trace باشند.
- [ ] وضعیت‌های بیرونی فقط بر اساس عمل/تأیید کاربر یا رویداد واقعی Workbench ثبت شوند.
- [ ] داشبورد تیم و صف اقدام‌های اولویت‌دار در پروژه ۱ تا ۱۰ Agent قابل استفاده باشد.
- [ ] Timeline رویداد واقعی را نشان دهد؛ Task/Milestone/Version/Release از هم جدا باشند.
- [ ] پیشرفت پروژه مبتنی بر Status/Evidence و روش محاسبهٔ آشکار باشد.
- [ ] جریان‌های Repair، Context Request، Handoff، Response Inbox و Prompt/Response کلاسیک در Workspace قابل پیدا کردن و یکپارچه باشند.
- [ ] GUI در رزولوشن‌ها و DPI تعریف‌شده از قاب/Work Area بیرون نرود؛ RTL/LTR پاس شود.
- [ ] Performance و Installer Size در مقایسه با Baseline اندازه‌گیری و گزارش شده باشند.
- [ ] پروژه‌های قدیمی با migration امن و بدون از دست‌دادن State باز شوند.
- [ ] Unit/Integration/GUI/Windows Installer tests پاس شوند.
- [ ] Manual End-to-End با حداقل دو چت مدل مستقل اجرا و نتیجه مستند شده باشد.
- [ ] موارد آزمون‌نشده صریحاً NOT RUN باشند؛ Roadmap صرفاً بر اساس وجود کد/تست سبز کامل اعلام نشود.

## ۲۵. دستورالعمل شروع کار برای برنامه‌نویس

1. این سند را ابتدا به‌عنوان پیشنهاد بخوان؛ آن را بدون ADR مستقیماً در `ROADMAP.md` اصلی ادغام نکن.
2. وضعیت واقعی `main` و ریلیز فعلی را دوباره تأیید کن و مسیرهای فعلی UI را با سناریوهای UX مقایسه کن.
3. ابتدا مرحله 0 را اجرا کن: نقشهٔ UX، Audit، Baseline و ADR. اگر تصمیم معماری روشن نشده، بازنویسی GUI شروع نشود.
4. هر مرحله را با تست، Evidence و Release Gate خودش ببند. نسخهٔ شماره‌دار به‌تنهایی مدرک تکمیل نیست.
5. هستهٔ V2، Inbox، Context Request، GitHub و Companion را تا حد ممکن reuse کن؛ منطق مشابه در UI یا سرویس دوم نساز.
6. در تمام مراحل، الگوی دستی تعامل با چت معمولی مدل‌ها، عدم اتصال به API مدل و تأیید انسانی برای عملیات پرریسک رعایت شود.
7. هر ادعای عملکرد، سازگاری، امنیت، تعداد Agent یا پیشرفت پروژه را با دادهٔ قابل مشاهده پشتیبانی کن. چیزی که نمی‌توانی مشاهده کنی، در UI به‌عنوان واقعیت نشان نده.
8. تغییرات را کوچک و قابل برگشت نگه دار، Migration را نسخه‌دار کن و در گزارش هر مرحله موارد PASS/FAIL/NOT RUN را ثبت کن.

## نتیجه

این Roadmap سه خواستهٔ مرتبط را به یک مسیر توسعه تبدیل می‌کند: محیط کاری مدرن، تاریخچه و پیشرفت قابل‌اعتماد، و تیم چندعاملی قابل مدیریت. شرط موفقیت فقط زیبایی GUI یا اضافه‌شدن داشبورد ده Agent نیست. کاربر باید با نگاه به محیط اصلی بفهمد پروژه کجاست، هر Agent چه کاری را در Workbench ثبت کرده، کدام موارد به اقدام او نیاز دارند و قدم بعدی چیست؛ در عین حال، برنامه نباید وانمود کند به فعالیت داخلی چت‌هایی که به آن وصل نیست دسترسی دارد.

اولویت اجرایی پیشنهادی: **Audit و ADR → انتخاب فناوری با PoC و معیار عملکرد → پوستهٔ واکنش‌گرا → Team Planner و Account/Chat Binding → وضعیت گردش‌کار و Timeline → Dashboard/Needs Attention → یکپارچه‌سازی و Gate انتهابه‌انتها.**
